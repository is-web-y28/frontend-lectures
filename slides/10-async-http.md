<!--
Фраза «JavaScript однопоточный» здесь означает: основной код страницы выполняет один участок за раз, используя один стек. В терминах спецификации мы рассматриваем один агент — единицу независимого выполнения JS. Обработчик клика не запускает второй JS-поток для своего таймера. Если он надолго займёт поток вычислением, другой обработчик не сможет одновременно изменить тот же интерфейс. Пока не усложняем картину несколькими окнами и агентами: это граница нашей модели.

Однопоточность JS не означает, что весь браузер — один поток. Сеть, таймеры и другие подсистемы могут продвигать работу вне нашего вызова. Web Worker — отдельный контекст исполнения со своим агентом и event loop; он общается с главным потоком сообщениями и не получает прямой доступ к DOM. Здесь Worker обозначает границу модели, а не обязательный способ загрузить заявки.

Возникает практический вопрос: как обрабатывать сеть и пользовательский ввод, если исполнять JS можем только по очереди? Не держать поток в ожидании: завершить текущий вызов, а готовую работу выполнить позже. Это и связывает однопоточное выполнение со следующим разбором задач и цикла событий. Event loop организует такую передачу управления; он не создаёт параллельное исполнение наших обработчиков. Сначала проследим короткий таймер и обычный стек.

title: "В callback hell трудно проследить шаги и ошибки"
kicker: "Проблема композиции"
notes: ["Каждая операция принимает функции успеха и ошибки.", "Следующий шаг вложен в успешный callback предыдущего.", "Обработка отказов повторяется на каждом уровне."]
---
```js
readMeetup('frontend', meetup => {
  readRegistrations(meetup.id, rows => {
    createReport(rows, report => {
      showReport(report)
    }, showError)
  }, showError)
}, showError)
```
<!--
Здесь показан учебный договор трёх асинхронных операций для Frontend Meetup: каждая принимает свои аргументы, затем onSuccess и onError. Это обозначения API источника, а не существующие методы браузера и не готовый fetch. Сначала readMeetup находит событие по имени frontend. Его результат даёт id для readRegistrations. Такую растущую вложенность называют callback hell, или «адом обратных вызовов». Трудность не только в отступах: порядок зависимых действий распределён между вложенными функциями, а showError приходится передавать на каждом уровне. Внешний синхронный try/catch не охватывает будущий callback.

Это не доказательство, что callback плох сам по себе: обработчик клика остаётся уместным. Именованные функции тоже могут уменьшить вложенность. Нам нужен единый договор будущего значения или отказа, который удобно соединяет шаги и распространяет ошибки. Его даст Promise. Позже перепишем именно этот отчёт сначала цепочкой then, затем через await. Пока важно прочитать зависимости, а не выучить имена условного API.

```js
  .then(meetup => {
    return readRegistrations(meetup.id)

  })
  .then(report => showReport(report))
  .catch(showError)
```
<!--
Вернёмся к отчёту из callback hell. В этой версии договор источников изменён: readMeetup, readRegistrations и createReport возвращают Promise вместо приёма onSuccess и onError. Само добавление then к старому callback API не переписывает его автоматически; источник должен поддерживать новый договор или иметь адаптер на границе, как наш таймер через new Promise.

Каждый return связывает следующий асинхронный шаг с общей цепочкой. Первый обработчик возвращает Promise заявок; второй запускается после его успешного завершения и возвращает Promise отчёта. Отказ любого из этих шагов пропускает последующие успешные обработчики и доходит до общего catch. Туда же попадёт исключение, брошенное внутри then, включая showReport.

Если забыть return перед readRegistrations или createReport, обработчик вернёт undefined и цепочка потеряет связь с запущенной операцией. Эти же Promise-функции оставим для варианта с await; вычисления не стали параллельными от изменения записи.

-->

---
layout: "code-explain"
title: "Тот же отчёт записывается через <code>await</code>"
kicker: "Callback → Promise → async/await"
notes: ["Используем те же функции, возвращающие <code>Promise</code>.", "Зависимости сохраняются: событие → заявки → отчёт.", "<code>try/catch</code> охватывает ожидаемые шаги."]
---
```js
async function showMeetupReport() {
  try {
    const meetup = await readMeetup('frontend')
    const rows = await readRegistrations(meetup.id)
    const report = await createReport(rows)
    showReport(report)
  } catch (error) {
    showError(error)
  }
}
```
<!--
Это третья запись одного сценария. Берём ровно те функции, которые в предыдущем варианте возвращали Promise, и читаем зависимости сверху вниз. Внешняя программа может продолжать работу, когда поток освобождён.

try/catch здесь заменяет общий catch цепочки: отказ в любом из трёх await становится исключением в продолжении функции, и успешный путь обрывается. showReport находится в том же try, поэтому его синхронное исключение тоже попадёт в catch. Вызов showMeetupReport сам возвращает Promise; это не синхронная функция, несмотря на последовательный вид тела.

Таким образом, callback hell объясняет потребность в более удобной композиции, Promise задаёт договор будущего результата, а async/await упрощает запись этой композиции. Очереди и один JS-поток от выбора записи не меняются. Теперь на минимальном doubledCount уточним границы try/catch, finally и потерянного Promise: наличие catch рядом с запуском ещё не означает, что он ожидает отказ.
-->

title: "Добавим отмену к защищённому поиску"
kicker: "Защищённый поиск"
notes: ["Отмена направлена прошлой операции.", "Номер по-прежнему защищает каждый <code>commit</code>."]

```js
let controller
async function search(query) {
  const id = ++latest
  commit({ phase: 'loading', errorText: '' })
  controller?.abort()
  controller = new AbortController()
  try {
    const nextRows = await loadRegistrations(
      query, controller.signal,
    )
    if (id !== latest) return
    commit({ rows: nextRows, phase: 'success' })
  } catch {
    if (id !== latest) return
    commit({ errorText: 'Ошибка загрузки', phase: 'error' })
  }
}
```
<!--
Перед новым вызовом отменяем прошлый контроллер и создаём новый. Номер увеличивается раньше отмены: когда отказ старого запроса дойдёт до catch, его id уже не совпадёт с latest. Поэтому прежняя отмена не станет ошибкой нового поиска.

Обновляем те же поля rows, errorText и phase объекта state, что в одиночной загрузке. Здесь отменяется предыдущая операция, номер которой уже устарел, поэтому её отказ не трогает текущий экран. Очистка state.errorText в начале не даёт прежней ошибке появиться после успешного нового ответа. Здесь показано добавление отмены к существующей защите; оно не заменяет проверку номера.
-->

title: "Сначала проверяем одну запись"
kicker: "Предикат одной записи"
notes: ["<code>unknown</code> заставляет проверить вход.", "Предикат связывает runtime-проверку и тип."]
---
```ts
type Registration = {
  id: string
  name: string
  count: number
}
function isRegistration(
  x: unknown,
): x is Registration {
  return typeof x === 'object' && x !== null
    && 'id' in x && typeof x.id === 'string'
    && x.id.length > 0
    && 'name' in x && typeof x.name === 'string'
    && !!x.name.trim()
    && 'count' in x
    && typeof x.count === 'number'
    && Number.isInteger(x.count)
    && x.count >= 1 && x.count <= 5
}
```
<!--
Сначала исключаем null, затем проверяем наличие и тип каждого поля. Ограничение от одного до пяти мест — бизнес-правило Frontend Meetup, а не правило JSON. Проверка не меняет строку в число и не исправляет вход молча.

Предикат типа сообщает TypeScript о проверке, которую реально выполняет тело функции. Компилятор доверяет нашей формулировке, поэтому сам предикат нужно писать честно. В локальном Vue-примере 09 id был числом; здесь договор API задаёт строковый id. Его задача прежняя — устойчиво различать заявки, арифметику с ним не выполняем. Поля email в этой краткой записи нет: читаем список имён и мест, а не полную форму из 07.
-->

title: "Затем проверяем коллекцию и идентичность"
kicker: "Проверка коллекции"
notes: ["Пустой массив допустим.", "Повтор <code>id</code> — ошибка договора."]
---
```ts
function parseRegistrations(
  value: unknown,
): Registration[] {
  if (!Array.isArray(value)
      || !value.every(isRegistration)) {
    throw new Error('Неверные поля заявки')
  }
  const ids = new Set(
    value.map(item => item.id),
  )
  if (ids.size !== value.length) {
    throw new Error('Повтор id')
  }
  return value
}
```
<!--
Проверки одной записи недостаточно: сервер мог вернуть объект вместо массива или две записи с одним id. В 09 ключ связывал элемент списка с идентичностью данных, поэтому повторяющийся id нарушает уже знакомую гарантию интерфейса.

Пустой массив проходит проверку и означает успешный пустой результат. Мы не подменяем повреждённый ответ пустым массивом, иначе пользователь увидит ложное «заявок нет». В обоих работающих примерах используется одна и та же функция из registration-client.js.
-->

Подписка второго then существует сразу, но его входной Promise пока не завершён: он зависит от первого обработчика. Поэтому первоначально в очереди P1 и явно поставленная M. После P1 следующий Promise завершается, и P2 добавляется в хвост после M.

Здесь обработчики возвращают обычные значения, а не дополнительные thenable; более сложное усвоение Promise может добавлять шаги. Не учим правило «вся цепочка then выполняется одним куском»: каждый готовый обработчик планируется отдельно. Это тот же механизм, который дальше позволит понять await.
