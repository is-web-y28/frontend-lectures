<!--
Сначала спросите: «Какие из этих кнопок занимают место? Какие попадут под Tab?» Затем дайте пройти по слайду с клавиатуры. В исходном состоянии между «До» и «После» нет `display: none` и элемента с `hidden`: они исключены из рендеринга. Для `visibility: hidden` остаётся пустое место, но сама кнопка не принимает фокус и действие.

Теперь Tab дойдёт до невидимой кнопки с `opacity: 0`. Контур появляется именно при фокусе, а Enter обновляет строку результата. Прозрачность меняет только отрисовку: геометрия, обработчик и семантика кнопки сохраняются. Поэтому прозрачный интерактивный элемент не является способом «спрятать» управление.

Последняя кнопка показывает другой случай: её текст визуально скрыт по устойчивому паттерну, но сама кнопка и её доступное имя «Открыть расписание» остаются. Это нужно для иконки без видимой подписи, а не для общего скрытия содержания. `hidden` — семантическое состояние HTML; не пишем правило вроде `[hidden] { display: block }`, а удаляем атрибут, когда содержание действительно надо показать.

До свойств размера договоримся о словаре. В привычной горизонтальной записи `inline` идёт слева направо по строке, поэтому `inline-size` похож на `width`; `block` идёт сверху вниз, поэтому `block-size` похож на `height`. Это соответствие, а не определение свойств.

Наконец выберите `auto` и нажмите «Прокрутить область»: область получает реальную прокрутку, а зелёная sticky-полоса остаётся у её верхнего края.

Обсудите не «победителя», а причины. Sticky не ищет самый высокий элемент страницы: он ограничен ближайшим предком с overflow. Поэтому случайное `overflow: hidden` на обёртке может изменить место, где sticky перестаёт следовать за прокруткой документа. Демо намеренно оставляет длинный текст: решение — выбрать поведение для содержания, а не удалить его ради аккуратной карточки.
-->

title: Grid — строки, колонки и пространство
---
<!--
Grid задаёт строки и колонки контейнера и размещает элементы по двум осям одновременно.

Grid позволяет задавать количество колонок, их ширину и промежутки между ними. Элементы размещаются по очереди в ячейках сетки, а разработчик решает: занимает элемент одну ячейку или несколько.
-->
---
layout: code-explain
kicker: Треки
title: grid-template-columns задаёт колонки контейнера
notes:
  - "12rem — фиксированная ширина"
  - "1fr — доля свободного пространства"
---
```css
.schedule {
  display: grid;
  grid-template-columns: 12rem 1fr;
  gap: 1rem;
}
```

<!-- Первая колонка фиксирована. Вторая растягивается на оставшееся пространство. -->
<!--
Прочитайте объявление слева направо: расписанию выделено устойчивое место `12rem`, затем `gap`, а только остаток получает второй трек. Это хороший каркас «навигация + содержание», когда ширина навигации действительно известна.

Не обещайте, что `1fr` всегда ведёт себя как простая арифметическая доля всей ширины. На следующем слайде добавляем минимальный размер трека и увидим, почему длинное содержимое способно изменить результат.
-->
---
layout: code-explain
kicker: Автоматический минимум Grid
title: <code>1fr</code> делит остаток, но трек тоже слышит содержимое
notes:
  - "`1fr` — гибкий максимум, не обязательно нулевой минимум."
  - "Длинный min-content потомка может расширить трек."
  - "`minmax(0, 1fr)` явно разрешает треку сжаться."
---
```css
.schedule {
  grid-template-columns: 12rem minmax(0, 1fr);
}
```
<!--
`fr` делит свободное пространство после фиксированных размеров и `gap`, но у Grid есть ещё минимальный размер трека. У записи `1fr` автоматический минимум может учитывать min-content потомка. Поэтому длинная неразрывная строка способна раздвинуть вторую колонку вместо ожидаемого сжатия.

`minmax(0, 1fr)` говорит две независимые вещи: минимум трека — ноль, максимум — одна доля свободного пространства. Теперь доступная ширина действительно ограничивает трек. Это не отменяет необходимость решить судьбу текста внутри: перенести URL, обрезать его с осознанным доступным названием или дать ему прокрутку — отдельный выбор. Так мы связываем «не хватает места» с автоматическими минимумами и в Flexbox, и в Grid.
-->
---
layout: two-cols
kicker: Повторение треков
title: repeat() сокращает описание одинаковых колонок
---
```css
.cards {
  grid-template-columns: repeat(3, 1fr);
}
```

::right::

- `repeat(3, 1fr)` = `1fr 1fr 1fr`

<!-- Три одинаковые колонки — одна строка вместо трёх. -->
<!--
`repeat()` ничего не меняет в алгоритме Grid: это только читаемая запись для одинаковых треков. Поэтому `repeat(3, 1fr)` и три подряд записанных `1fr` дают одну и ту же геометрию.

Когда у одинаковых колонок есть риск длинного содержимого, внутрь `repeat()` так же можно поместить `minmax(0, 1fr)`. Сначала выбираем правило минимума, затем сокращаем повторение — не наоборот.
-->

layout: default
kicker: Автоматическое размещение
title: Grid расставляет элементы по очереди
---
```html
<div class="gallery">
  <section>1</section>
  <section>2</section>
  <section>3</section>
  <section>4</section>
  <section>5</section>
  <section>6</section>
</div>
```
<!-- Grid размещает элементы по очереди: слева направо, сверху вниз. Добавленная карточка появляется после предыдущей — без ручного изменения CSS. -->
<!--
Если позиции элементов не заданы явно, Grid расставляет их по очереди: слева направо, сверху вниз. Это означает, что для галереи из шести карточек не нужно назначать координаты каждой: Grid делает это сам.

Изменение количества карточек сдвигает сетку без поломки раскладки: добавленная карточка появляется после предыдущей, а новые строки формируются автоматически.
-->
---
layout: code-explain
kicker: span и линии
title: Элемент может занять несколько треков
notes:
  - "span — занять N колонок"
  - "1 / 3 — от линии 1 до линии 3"
---
```css
.featured {
  grid-column: span 2;   /* или "1 / 3" */
}
```

<!-- Первый элемент занимает две колонки. Остальные размещаются после него автоматически. -->
<!--
`span 2` выражает отношение к текущей сетке: карточка занимает два соседних трека, а не абсолютную координату на странице. После неё алгоритм автоматического размещения продолжает раскладывать остальные элементы в свободные ячейки.

Форма `1 / 3` полезна, когда важны именно линии сетки, но для карточки, которая должна быть «шире соседей», `span 2` обычно лучше передаёт намерение. Не смешивайте этот локальный акцент с именованными областями следующего слайда: области нужны для стабильного каркаса целой страницы.
-->
---
layout: code-explain
kicker: Именованные области
title: Описать каркас страницы в одном месте
notes:
  - "Каждая строка в кавычках описывает одну строку сетки"
  - "grid-area привязывает элемент к имени"
---
```css
.page {
  display: grid;
  grid-template-areas:
    "header header"
    "nav    main"
    "footer footer";
}

.page__header { grid-area: header; }
.page__nav    { grid-area: nav; }
.page__main   { grid-area: main; }
.page__footer { grid-area: footer; }
```

<!-- Когда структура стабильна и двумерна, области дают читаемую карту. Не использовать для каждой карточки. -->
<!--
Именованные области — способ описать схему всей страницы в одном месте. Когда структура стабильна и действительно двумерна, области дают читаемую карту.

Не использовать области для каждой карточки: там достаточно автоматического размещения или `span`.
-->

layout: code-explain
kicker: Приложение · диагностика
title: Схлопывание margin — правило normal flow, не причина перейти на Flexbox
notes:
  - "Соседние блочные vertical margins в normal flow могут схлопнуться."
  - "Временный `display: flow-root` создаёт новый block formatting context."
  - "После диагностики выбираем структурное решение, а не добавляем float."
---
```css
.section { margin-block-start: 2rem; }

/* Проверка гипотезы о collapse */
.parent { display: flow-root; }
```
<!--
Если ожидаемый вертикальный отступ оказался меньше суммы двух `margin`, не спешите добавлять ещё один. У соседних блочных элементов в normal flow, а также у родителя с первым или последним ребёнком, вертикальные margins могут схлопнуться. Это не происходит между flex/grid items, поэтому смена модели иногда маскирует причину вместо объяснения.

Для диагностики временно сделайте предполагаемого родителя `flow-root`. Он создаёт новый block formatting context и отделяет отступы родителя от отступов его детей; соседние margins внутри этого контейнера всё ещё могут схлопываться. Если расстояние изменилось, проверяем именно границу родителя и ребёнка. Затем возвращаемся к структуре: возможно, пространство должно принадлежать контейнеру как `padding`, либо отступ должен быть только с одной стороны. Мы не превращаем это в курс о float: `flow-root` здесь инструмент наблюдения, а не новая основная раскладка.
-->

layout: two-cols
kicker: Приложение · направление письма
title: Логические свойства сохраняют намерение в RTL и vertical writing
---
```html
<article dir="rtl" class="notice">
  التسجيل مفتوح
</article>
```

```css
.notice {
  padding-inline-start: 1rem;
  border-inline-start: 4px solid currentColor;
}
```

::right::

```css
.vertical {
  writing-mode: vertical-rl;
  inline-size: 12rem;
  margin-block-end: 1rem;
}
```

<!--
В RTL начало строки находится справа, поэтому `padding-inline-start` и `border-inline-start` переедут вместе с текстом. Если бы мы написали `padding-left`, декоративная граница осталась бы физически слева и перестала бы выражать «начало сообщения».

Во втором фрагменте `vertical-rl` меняет ориентацию строк: `inline-size` уже не равен физической ширине, а `margin-block-end` не означает просто «снизу». Не нужно немедленно переписывать весь CSS логическими свойствами; достаточно узнавать ситуации, где направление текста или writing mode делает физические `left`/`width` неверным описанием намерения.
-->
