layout: code-explain
kicker: Шаг 1 · relevance
title: Нерелевантное правило не может победить
notes:
  - "@media (min-width: 60rem) проверяется до специфичности."
  - "Если условие ложно, селектор не участвует в конкурсе."
  - "Сначала проверяем окружение, затем сам компонент."
---
```css
.event-card {
  background: white;
}

@media (min-width: 60rem) {
  .event-card {
    background: lime;
  }
}
```
<!--
Спросите: почему на узком экране зелёное правило не зачёркнуто как проигравшее? Потому что его нет среди релевантных кандидатов. В большом окне оно появляется, и только тогда мы обсуждаем остальные этапы. Эта привычка особенно важна для media queries и container queries.
-->
---
layout: code-explain
kicker: Шаг 2 · origin и importance
title: Источник важнее красивой теории специфичности
notes:
  - "Обычный author CSS сильнее обычного user-agent CSS."
  - "Анимации и transitions имеют отдельные позиции в порядке."
  - "!important меняет порядок; это не универсальная кнопка силы."
---
```css
/* user stylesheet */
#event-card { color: black; }

/* author stylesheet */
.event-card { color: teal; }
```
<!--
Здесь менее специфичный author rule выигрывает у более специфичного user rule. Не надо запоминать таблицу как заклинание: сначала определяем источник и важность, и только после этого считаем селекторы. Если студент показывает #event-card и говорит «он сильнее», возвращаем его на шаг выше.
-->
---
layout: code-explain
kicker: Шаг 3 · specificity
title: Специфичность — счётчик, а не архитектура
notes:
  - "ID, class/attribute/pseudo-class и type образуют три группы счёта."
  - "Сравниваем группы слева направо, а не складываем всё в одно число."
  - "Низкая специфичность оставляет компонент переопределяемым."
---
```css
#event-card.card { color: tomato; } /* 1-1-0 */
.event-card { color: teal; }        /* 0-1-0 */
```
<!--
Покажите, что первое правило действительно победит внутри одного origin и слоя. Но именно поэтому ID в стилях компонентов создаёт долг. Следующее изменение потребует ещё более тяжёлого селектора или important. Хорошая организация CSS не пытается выиграть каждый локальный конфликт — она не создаёт такие конфликты.
-->
---
layout: code-explain
kicker: Шаг 4–5 · proximity и order
title: Последний шанс — близость и порядок
notes:
  - "@scope может дать преимущество ближайшей области при равной специфичности."
  - "Без этого остаётся порядок появления."
  - "Перестановка импортов тогда становится изменением поведения."
---
```css
.event-card { border-color: slateblue; }
.event-card { border-color: tomato; } /* победит */
```
<!--
Последняя строка выигрывает не потому, что она «важнее», а потому что все предыдущие этапы равны. Это объясняет многие эффекты после перестановки файлов. Важно назвать цену: если порядок случайный, сборка становится скрытой частью API.
-->
---
layout: default
kicker: Каскадные слои
title: @layer превращает порядок в именованный контракт
---
```css
@layer reset, base, components, utilities;

@layer components {
  .event-card { color: teal; }
}

@layer utilities {
  .text-muted { color: gray; }
}
```
<Callout title="Идея">
Сначала объявляем порядок слоёв. Потом файлы могут подключаться в любом порядке — место правила определяется его слоем.
</Callout>
<!--
Слой — это не namespace и не область видимости. Это позиция в каскаде. Явно объявленный порядок делает намерение читаемым для команды. Для обычных деклараций правило вне слоя выше всех авторских слоёв; поэтому «вынести временный фикс в конец файла» опаснее, чем добавить его в согласованный слой.
-->
