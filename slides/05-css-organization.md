Произнесём это как алгоритм, а не как пять новых терминов. Сначала остаются правила, подходящие элементу и действующим условиям. Затем учитываются источник и важность деклараций; на этом уровне имеет значение и порядок каскадных слоёв. Не нужно на каждом примере доходить до последнего шага. Как только более ранний этап определил приоритет, более поздний его не отменяет. Это и объясняет результат предыдущей демонстрации: до specificity дошли бы только правила с одинаковым положением на предыдущих уровнях.

kicker: Шаг 1 · relevance
title: Нерелевантное правило не может победить
notes:
  - "@media (min-width: 60rem) проверяется до специфичности."
  - "Если условие ложно, селектор не участвует в конкурсе."
  - "Сначала проверяем окружение, затем сам компонент."
---
```css
.event-card {
  background: white;
}

@media (min-width: 60rem) {
  .event-card {
    background: lime;
  }
}
```
<!--
Здесь оба селектора одинаковы, поэтому внимание нужно направить не на их вес, а на условие. При ширине viewport меньше `60rem` зелёное правило не участвует в выборе значения. Его нельзя сделать победителем, дописав ID или `!important`, пока условие остаётся ложным.

Если разбираем пример в DevTools, смотрим не только на зачёркнутые декларации, но и на состояние `@media`. Интерфейс инструментов может показывать неактивное правило отдельно; важна причина его неучастия, а не способ отображения. В широком окне правило становится релевантным, и при равенстве остальных условий более поздняя декларация задаёт зелёный фон.

Связь с прошлой лекцией прямая: прежде чем менять оформление карточки, проверяем владельца условия. `@media` смотрит на среду страницы, а запрос к контейнеру — на конкретный контейнер. Ошибка в выборе окружения не исправляется специфичностью.
-->

layout: code-explain
kicker: Шаг 2 · origin и importance
title: Источник важнее красивой теории специфичности
notes:
  - "Обычный author CSS сильнее обычного user-agent CSS."
  - "Анимации и transitions имеют отдельные позиции в порядке."
  - "!important меняет порядок; это не универсальная кнопка силы."
---
```css
/* user stylesheet */
#event-card { color: black; }

/* author stylesheet */
.event-card { color: teal; }
```
<!--
Здесь менее специфичная обычная декларация автора выигрывает у более специфичной обычной декларации пользователя. Комментарии обозначают два разных источника стилей: это не два блока, которые можно вставить в один авторский `<style>` и получить тот же эксперимент.

Источником определяется место декларации в каскаде. Сначала различаем стили браузера, пользователя и автора, затем важность. Для важных деклараций приоритет источников меняется: пользовательское `!important` может сохранять нужное пользователю оформление вопреки авторским правилам.

Анимации и активные transitions тоже занимают свои позиции в каскаде; считать их ещё одним обычным селектором нельзя. Полную таблицу сейчас не заучиваем. Нам нужна привычка: если студент показывает `#event-card` и говорит «он сильнее», сначала уточняем источник и важность обеих деклараций.
-->

layout: code-explain
kicker: Шаг 3 · specificity
title: Специфичность — счётчик, а не архитектура
notes:
  - "ID, class/attribute/pseudo-class и type образуют три группы счёта."
  - "Сравниваем группы слева направо, а не складываем всё в одно число."
  - "Низкая специфичность оставляет компонент переопределяемым."
---
```css
#event-card.card { color: tomato; } /* 1-1-0 */
.event-card { color: teal; }        /* 0-1-0 */
```
<!--
Для этих двух правил предполагаем одинаковые источник, важность и слой. Теперь действительно сравниваем специфичность: у первого селектора есть ID и класс, у второго — только класс. Сравнение идёт по группам слева направо; это не сумма, которую можно набрать достаточным количеством классов.

Попросите объяснить, что изменится, если добавить второму селектору ещё один класс. Его вес станет `0-2-0`, но ID в первой группе всё ещё определит результат. Так видно, почему попытка «немного усилить» правило может превратиться в гонку селекторов.

ID не запрещён в HTML: он нужен, например, для связи подписи с полем или для якоря. Речь о цене его использования в стилях переиспользуемого компонента. Низкая специфичность не гарантирует хорошую архитектуру, но оставляет возможность выразить следующий вариант без борьбы с базовым правилом.
-->

kicker: Шаг 4–5 · proximity и order
title: Последний шанс — близость и порядок
notes:
  - "@scope может дать преимущество ближайшей области при равной специфичности."
  - "Без этого остаётся порядок появления."
  - "Перестановка импортов тогда становится изменением поведения."
---
```css
.event-card { border-color: slateblue; }
.event-card { border-color: tomato; } /* победит */
```
<!--
В показанном коде нет `@scope`: обе декларации относятся к одному элементу, задают одно свойство и имеют одинаковый вес. При равенстве предыдущих этапов побеждает более поздний `border-color: tomato`. Именно поэтому перестановка подключаемых файлов иногда меняет оформление без изменения самих селекторов.

Близость области учитывается раньше порядка объявления, когда в сравнении участвуют правила с `@scope`. При равенстве специфичности более близкий корень области может определить результат; это не правило «любой ближайший родитель всегда сильнее». Подробный пример оставлен в дополнительном материале.

Спросите: если всё исправилось после переноса строки в конец файла, что мы узнали? Пока только то, что порядок оказался значимым. Теперь нужно решить, должен ли он быть частью договорённости, а не оставаться случайным следствием сборки.
-->

kicker: Каскадные слои
title: @layer превращает порядок в именованный контракт
---
```css
@layer reset, base, components, utilities;

@layer components {
  .event-card { color: teal; }
}

@layer utilities {
  .text-muted { color: gray; }
}
```
<Callout title="Идея">
Сначала объявляем порядок слоёв. Потом файлы могут подключаться в любом порядке — место правила определяется его слоем.
</Callout>
<!--
Слой — это не namespace и не область видимости. Селектор `.event-card` по-прежнему может совпасть с любой подходящей карточкой; `@layer` меняет приоритет декларации, а не набор элементов. Здесь заранее названы позиции `reset`, `base`, `components` и `utilities`.

Для обычных деклараций более поздний слой имеет приоритет над более ранним. Если к одной карточке применились оформление из `components` и утилита из `utilities`, решение сначала определяется слоями, а не весом их селекторов. Внутри одного слоя порядок и специфичность по-прежнему работают.

Важное ограничение: обычная авторская декларация вне слоёв выше обычных деклараций во всех этих слоях. Поэтому вынести временный фикс за `@layer` — не нейтральная перестановка. Явный список слоёв стабилизирует их взаимный приоритет, но не отменяет конкуренцию правил внутри каждого слоя.
-->

До этого мы объясняли, как браузер выбирает значение. Теперь меняется вопрос: какие правила команда вообще должна создавать? Даже полностью понятный каскад не спасёт карточку, если её оформление зависит от случайного родителя.

Вернёмся к двум местам использования — расписанию и боковой колонке. Содержание и действие карточки остаются теми же, поэтому её базовая роль не должна исчезать при переносе. Окружение может размещать компонент по-разному, но это отдельная ответственность.

Обратите внимание на расположение `@import`: импорты идут до обычных правил; декларация порядка слоёв перед ними допустима. Способ обработки зависит от сборщика и поддержки браузеров. Проверяем, что итоговая сборка сохраняет задуманную структуру, а не только что исходник выглядит правильно.

Обычные авторские декларации вне слоя остаются выше обычных деклараций в слоях. Кроме того, порядок файлов внутри одного слоя всё ещё может определить результат при равенстве остальных условий. Именованные слои стабилизируют один уровень порядка, а не делают подключение любых файлов безразличным.

title: Что именно делают Sass и PostCSS?
subtitle: Один изменяет язык до CSS, другой прогоняет CSS через плагины
---
<!--
Здесь начинается разговор о преобразованиях на пути к браузеру, а не о новой архитектуре компонентов. Sass расширяет исходный язык: модули, переменные и mixin работают при компиляции. Браузер получает обычный CSS и Sass не выполняет.

PostCSS получает CSS и пропускает его через выбранные плагины. Один плагин добавляет префиксы, другой обрабатывает определённый синтаксис; сам PostCSS не принимает архитектурных решений. Оба инструмента могут быть в одной сборке.

Дальше каждый пример читаем в три шага: что написал автор, какая трансформация настроена и что получилось в артефакте. Удобство исходника не должно подменять проверку результата.
-->

Один дизайн-токен иногда существует в обоих мирах, но по разным причинам. Не заменяем синтаксис механически: сначала спрашиваем, должно ли значение изменяться после сборки и зависеть от места использования компонента.

```scss
}
```
<!--
`@use` делает зависимость явной: модуль токенов доступен как `t`, набор повторяемых деклараций — как `m`. В локальном `source/meetup.scss` подключены именно `tokens` и `mixins`; `m.panel` собирает общую поверхность панели. Сравните пример с этими двумя файлами, не превращая показ в изучение всего Sass.

`@include` разворачивается при компиляции в обычные декларации на каждом месте использования. Браузер не получает runtime-объект Sass. Компактная запись источника не отменяет необходимости посмотреть, сколько CSS она породила и каких потребителей затронет правка общего миксина.

Абстракция оправдана, если стабилизирует повторяющуюся идею — например, поверхность панели или фокусное кольцо. Если mixin прячет несколько случайных строк и требует отдельного условия для каждого потребителя, связанность лишь переехала в другой файл.
-->

Префикс не является универсальным полифилом поведения. Плагин автоматизирует конкретную работу, но не понимает границу компонента и не исправляет конфликт `.agenda .card` с `.event-card`. Для этого сначала нужен осмысленный исходный CSS.

<!--
Featured — вариант оформления. Expanded — состояние взаимодействия. Они могут существовать одновременно и не должны превращаться в десяток комбинированных классов вроде featured-expanded-loading.

Для недоступной настоящей кнопки начнём с нативного disabled. CSS может читать :disabled, а браузер уже обеспечивает базовое поведение. Если нужно сохранить кнопку доступной для фокуса и использовать aria-disabled, придётся отдельно реализовать запрет действия. Один атрибут ARIA этого не делает.

Для раскрывающего элемента состояние отражается в aria-expanded на управляющей кнопке, а видимость панели — в hidden. Это две разные обязанности, которые обработчик обновляет согласованно. Не добавляем третью копию того же состояния в .is-expanded.

Для внутреннего этапа загрузки может пригодиться data-status. Но data-атрибут ничего не сообщает программе чтения с экрана сам по себе. aria-busy, уведомление о результате и блокировка повторного действия выбираются по поведению конкретного интерфейса.

Модификаторы не запрещены для состояний. Мы просто не дублируем уже существующий подходящий источник без причины.
-->

<!--
Попросите найти в разметке три разных вещи: управляющий элемент, связь с панелью и текущее состояние. aria-controls ссылается на ID панели, aria-expanded сообщает о раскрытии, а hidden действительно скрывает панель.

CSS читает aria-expanded и усиливает начертание кнопки. Ему не нужен отдельный .is-expanded. Само поведение реализует обработчик; на следующей лекции мы разберём его подробнее. Для проверки этого примера достаточно:

```js
const toggle = document.querySelector('.event-card__toggle')
const panel = document.getElementById(toggle.getAttribute('aria-controls'))
toggle.addEventListener('click', () => {
  const expanded = toggle.getAttribute('aria-expanded') !== 'true'
  toggle.setAttribute('aria-expanded', String(expanded))
  panel.hidden = !expanded
})
```

Это пример одной карточки. При повторении карточек ID панелей должны быть уникальны, а обработчик — связан с каждой соответствующей кнопкой. Нельзя скопировать один event-details на весь список.

Проверьте мышью и клавиатурой: Enter и Space активируют настоящую кнопку, панель появляется, атрибут становится true. Повторная активация возвращает всё назад. Фокус остаётся на кнопке. Не добавляйте CSS, который насильно показывает элемент с hidden.

[MDN: aria-expanded](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-expanded).
