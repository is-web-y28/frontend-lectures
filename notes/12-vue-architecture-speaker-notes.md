## Вступление

### Слайд 1. Архитектура Vue‑приложения

В прошлый раз форма Frontend Meetup отправляла событие, владелец обновлял коллекцию, а отдельный composable управлял поиском. Сегодня у той же задачи три экрана: расписание, карточка события с формой и список заявок по HTTP. Первое требование звучит как обычная просьба: «Пришли ссылку прямо на нужный список».

К этому добавим второе требование. Ту же форму регистрации теперь хотят открывать и из расписания. Сначала спроектируем границы Frontend Meetup. Выясним, что принадлежит странице, что переиспользуется и какие связи можно менять безопасно. Затем проверим эти решения на ссылке, сводке заявок и новом формате ответа. Тот же порядок пригодится при проектировании ЛР 5.

### Слайд 3. Архитектура задаёт *владельцев* и границы

У нас уже три разных ожидания. Адрес открывает нужный экран в новой вкладке. Незавершённый ввод относится к текущей форме. Принятую заявку пользователь ожидает видеть в сводке и после перехода в расписание. Из требований можно вывести, кому нужны эти данные, кто их меняет и сколько они должны жить.

Теперь добавим регистрацию в расписание. Если обе страницы скопируют форму, одна может разрешать пять мест, а другая шесть. Общее правило должно жить в одном месте вместе с операцией регистрации. Так появляется граница в коде. Дальше выберем место для формы и публичный вход, через который её получат страницы, а затем определим срок жизни черновика при навигации.

### Слайд 4. От схемы приложения к рабочим сценариям

Сначала нанесём на схему страницы, форму регистрации и общую рамку. С помощью Feature-Sliced Design выберем, чему место в странице, что выделять для нескольких потребителей и какие импорты разрешить. Тут же проверим границу на переносе файла формы. Откроем в редакторе реэкспорт и импорт страницы, чтобы увидеть, где закончилась правка.

Затем воплотим схему в работающих сценариях. Откроем нужную страницу по ссылке и сохраним заявку при смене экрана. В главе о загрузке подменим клиент, отменим чтение для прошлого события и приспособим клиент к новому JSON. При смене языка увидим прежний отбор с новыми подписями. В финале сведём результаты к их владельцам — адресу, модели, клиенту и представлению.

## Глава 01. Где проходят границы приложения?

### Слайд 5. Где проходят границы приложения?

В прошлой лекции мы выделили форму, список и рамку в компоненты. Теперь та же форма нужна в карточке и в расписании. При двух параллельных изменениях, подключении формы на новом экране и обновлении проверки числа мест, расположение кода должно подсказывать разработчикам, где находится общая форма и кто владеет правилом.

Начнём с трёх экранов и задачи регистрации. Найдём код, который принадлежит одному экрану, и код, который нужен обоим. Затем зададим направление импортов и вход для общего модуля. По такой схеме дальше решим, кто читает адрес, кто хранит заявки и кто получает ответ по HTTP.

### Слайд 6. Feature-Sliced Design (FSD)

Разработчик получил задачу изменить регистрацию. Ему надо быстро найти форму, правило числа мест и код запроса. Чтобы использовать форму на странице события, ему также понадобится знать, какие части модуля доступны снаружи. Feature-Sliced Design даёт команде договорённость о размещении такого кода и правилах импортов.

На слайде A2 приложения к лекции 5 мы уже видели эту идею на примере Frontend Meetup, когда выбирали место для стилей карточки. Теперь применим её ко всему модулю регистрации. Возьмём те части структуры, для которых в примере есть понятная задача, и разложим их по трём уровням.

### Слайд 7. Как читать путь в проекте FSD

Прочитаем путь к форме из схемы Frontend Meetup слева направо. Мы находим features, слой пользовательских действий. У других частей приложения есть свои слои: pages собирает экраны, app запускает приложение, shared даёт общий фундамент. На слайде пока видна схема проекта, а папку registrations дальше сравним с рабочим стендом.

[click] registrations — слайс. Это имя знакомой части продукта, поэтому по нему можно искать форму и её поведение. event — слайс слоя pages. В app и shared сразу идут сегменты, потому что там код уровня всего приложения или общий фундамент.

[click] Сегмент уточняет назначение кода. ui содержит форму, model — правила и состояние, api — клиент. index.ts находится в корне слайса и служит входом для остальных модулей. В пути features/registrations/ui мы читаем слой действий, слайс регистрации и сегмент интерфейса. Теперь найдём место для остальных частей приложения в общей схеме.

### Слайд 8. Слой отвечает за роль кода в приложении

Пройдём снизу вверх. BasePanel продолжает идею MeetupPanel из прошлой лекции и подходит общему UI: он даёт секцию и слот. Событие с названием и временем начала — часть предметной области, которую при необходимости выделяем в entities/event. Отправка регистрации — действие пользователя. Самостоятельный блок с несколькими частями интерфейса может стать виджетом. Страница собирает всё для своего адреса, а точка входа запускает приложение и связывает его общие части. Конкретный код подключения увидим по мере реализации.

Это действующие слои FSD. В старых проектах может встретиться processes — устаревший слой для многостраничных сценариев. Для Frontend Meetup выбираем слои по задачам. Чтобы понять, какие нужны первыми, пройдём по адресам приложения.

### Слайд 9. Начинаем со страниц и выносим общее по необходимости

Возьмём простой первый вариант. Выпишем три страницы Frontend Meetup. Это расписание, карточка события и опубликованный список. Если только карточка использует форму, достаточно держать её и правила в слайсе этой страницы. BasePanel помогает разместить произвольное содержимое на нескольких экранах, поэтому он идёт в shared. Такой старт со страниц и их потребностей называют pages-first.

Теперь предположим, что по требованиям зарегистрироваться можно и из расписания. Правила проверки и саму форму тогда стоит вынести ниже, в слайс пользовательского действия. Опубликованный список может остаться в своей странице, пока другой сценарий его не использует. Мы двигаем код по потребителям и изменениям, а не распределяем все файлы по полному набору папок заранее.

### Слайд 10. Событие, регистрация и блок расписания решают разные задачи

У события есть идентификатор, заголовок и время начала. Эти сведения могут использоваться в расписании и карточке. Поэтому общий код о событии можно выделить как сущность. Фича отвечает на вопрос, что может сделать пользователь. Ввести имя и подать заявку — цель, для которой нужны форма и правила. Виджет — готовый блок интерфейса. Например, программа мероприятия объединяет карточки событий и доступные действия.

Если программа используется и в расписании, и на главном экране проекта, отдельный виджет помогает собирать обе страницы. Если программа целиком составляет содержимое одного экрана, её удобно держать при нём. BasePanel предоставляет общий интерфейс со слотами, поэтому он живёт в shared/ui и подходит блокам с разным содержимым.

### Слайд 11. Сегмент подсказывает, за что отвечает файл

На схеме нашли папку features/registrations. В рабочем слайсе RegistrationForm и LocalRegistrationList живут в ui. В model есть правила и состояние регистрации. Позже увидим там хранилище и логику загрузки. В api лежит код, который знает адрес ресурса и формат сетевого ответа. Перестановку полей начинаем в ui. Изменение допустимого числа мест начинаем с правила в model, затем проверяем, как форма объясняет его пользователю.

lib и config имеют смысл, когда в слайсе появляется соответствующий код. Например, вспомогательная функция расчёта относится к конкретному сценарию, а конфигурация может хранить доступный режим регистрации. В app и shared сегменты лежат прямо внутри слоя. Теперь можно читать связи между модулями, у которых уже определена ответственность.

### Слайд 12. Между слайсами зависимости направлены вниз

Стрелка идёт от того, кто импортирует, к тому, кого он использует. Из слайса можно импортировать другие слайсы строго ниже. Поэтому страница сразу обращается к features и shared. Соседняя страница на том же слое. Если ей понадобился экран расписания ради одного общего блока, выделяем подходящий нижний модуль и используем его с обеих страниц.

При открытии CSS Workshop именно страница получает выбранное событие и передаёт его eventId при вызове действия. Форма отдаёт черновик через submit, как в прошлой лекции. Внутри одного слайса его файлы могут обращаться друг к другу. Сегменты App могут импортировать другие сегменты App. Та же свобода действует внутри Shared. Между слоями App и Shared направление по-прежнему сверху вниз.

### Слайд 13. Слайс объявляет, чем может пользоваться страница

В рабочем стенде index.ts перечисляет, какие имена могут импортировать внешние модули. Здесь показаны форма и список, с которыми уже работали в прошлой лекции. В список экспортов включаем то, что требуется потребителям. Если открыть все файлы через export *, внутренняя вспомогательная функция может случайно стать частью договора.

[click] Страница получает форму через одну точку. Она рассчитывает на имя RegistrationForm и её поведение: после проверки ввода форма отправляет submit. Если меняется внутренний путь, достаточно поправить один реэкспорт. Если меняется само событие формы, это уже изменение контракта с потребителями.

### Слайд 14. Путь импорта показывает, какую границу мы пересекаем

Форма обращается к Draft из своего сегмента model по короткому относительному пути. Это внутренний импорт. Если бы она обращалась к собственному index.ts, который уже реэкспортирует форму, легко получить циклическую связь.

[click] Путь со страницы начинается с @. В примере алиас указывает на src и описан в конфигурации Vite и TypeScript. Затем по пути видно слой, слайс и его публичный вход. Сам алиас только разрешает путь. Соблюдение границы проверяем при ревью или линтером.

### Слайд 15. На ревью проверяем границу по импорту

На ревью импорт показывает, от чего зависит файл. Если одна страница импортирует RegistrationsPage ради таблицы, такая зависимость идёт между соседями на слое pages. Общую таблицу без логики регистрации можно выделить в shared/ui. Законченный блок со своей логикой чтения может стать виджетом. Тогда обе страницы обращаются к одному модулю через публичный вход нижнего слоя.

Можно автоматизировать проверку направления и точек входа, например Steiger, а видимое поведение проверить тестом сценария. Дальше разберём тот же принцип на форме регистрации, которую используют две страницы.

### Слайд 16. Карточка и расписание используют одну форму

В проектном варианте форма из расписания откроется в диалоге после выбора мероприятия. Состояние диалога принадлежит странице расписания. Карточка выводит форму сразу, поэтому ей такое состояние не нужно. В обоих случаях форма собирает имя и число мест и отдаёт черновик. Страница, которой известно выбранное событие, передаёт его eventId в операцию добавления. Так правила регистрации остаются общими для обеих страниц.

RegistrationForm и операция добавления лежат в features/registrations. Страницы получают нужные имена через index.ts. Теперь найдём эти файлы в рабочем стенде со стороны карточки и проследим, что произойдёт с импортом, когда форма переедет в ui.

### Слайд 17. Публичный вход и файл формы видны в дереве

Это часть дерева рабочего стенда. EventPage.vue использует форму через корень features/registrations. Внутри слайса index.ts открывает её имя, а ui/RegistrationForm.vue содержит реализацию. Рядом в model/localModel.ts определена форма данных черновика. api/registrationsApi.ts относится к отдельной задаче внутри слайса — чтению опубликованных записей.

BasePanel лежит в shared/ui. Он оформляет рамку, а страница выбирает содержимое, поэтому одна рамка подходит и форме, и опубликованному списку. Дальше сравним две версии дерева. Сначала введём index.ts, затем поместим форму в ui, как в рабочем коде.

### Слайд 18. Перенос формы меняет реэкспорт

Начальный ход полезно разделить на два маленьких изменения. Сначала вводим точку входа и переключаем на неё страницу. Пусть index.ts реэкспортирует форму по старому расположению. С этого момента потребитель обращается к фиче по имени.

[click] Переносим файл в ui. На слайде видна строка, которая меняется в публичном входе. В рабочей версии также обновлён внутренний относительный импорт из формы в model.

[click] Импорт страницы совпадает с результатом первого шага. Он указывает на тот же слайс и имя. Проверим и поведение. Если импорт или обработка submit сломались, форма не откроется или итог в шапке не обновится.

[В редакторе открыть index.ts и перейти из реэкспорта в ui/RegistrationForm.vue. Затем показать импорт формы в EventPage.vue.]

В редакторе видно, что импорт страницы ведёт на публичное имя, а новый путь указан в реэкспорте. Рабочую отправку из этой формы увидим в главе об общем состоянии. Пока соберём вход в саму карточку. Страница знает, для какого события отправлять заявку. Осталось связать этот выбор с адресом, который можно отправить другой вкладке.

## Глава 02. Что должен восстанавливать адрес?

### Слайд 19. Что должен восстанавливать адрес?

Мы уже выбрали страницы и договорились, что нужный идентификатор передаёт страница. По присланной ссылке на заявки CSS Workshop приложение должно выбрать и экран списка, и событие. В первом опыте адрес оставался прежним, а выбор хранился в ref. Теперь сделаем адрес входом в сценарий страницы.

Для этого подключим Vue Router. Он свяжет путь с экраном. Затем добавим условие просмотра списка в адрес и проверим, восстанавливает ли его кнопка «Назад».

### Слайд 20. Каждому экрану нужен адрес

Теперь у трёх страниц из первой главы появились конкретные адреса. В расписании пользователь выбирает событие, карточка показывает дату и даёт локальную форму, третий экран показывает опубликованный список. В опытах с адресом форму временно скрываем, чтобы сосредоточиться на смене страницы. Двоеточие на карте отмечает место для идентификатора. В рабочем адресе там будет, например, frontend-meetup.

Поиск по имени из лекции 11 здесь сокращаем до одного порога в опубликованном списке. На переключателе проще увидеть, как выбранное условие представлено в адресе. На первых опытах с навигацией у списка заранее заданные записи. Так при переходе меняется одна интересующая нас вещь — адрес. Когда договор о маршруте станет понятен, подключим сетевой источник.

### Слайд 21. Запись маршрута связывает путь и компонент

Возьмём только расписание. У записи есть путь /schedule, имя schedule и компонент SchedulePage. Когда адрес соответствует пути, роутер выбирает этот компонент. Имя пригодится для ссылки: если написание пути изменится, такая ссылка по-прежнему укажет на нужную запись.

[click] Создаём роутер с этой таблицей. В учебном стенде createWebHashHistory читает маршрут после знака #. Поэтому в адресной строке видим #/schedule, а в таблице пишем /schedule. Уточним роль сервера в конце главы.

[click] app.use(router) подключает экземпляр к приложению. Теперь можно показать выбранный экран в RouterView и построить ссылку через RouterLink.

### Слайд 22. `RouterView` задаёт место для экрана

На предыдущем слайде запись /schedule указала на SchedulePage. Здесь RouterView — место, где Vue монтирует выбранный компонент. Когда открываем карточку, в пределах main на месте SchedulePage появляется EventPage. В App.vue остаётся header, поэтому навигация видна на обоих экранах.

При уходе с карточки локальный черновик исчезнет вместе с её формой. Шапка при этом может продолжать показывать общую сумму, если исходная коллекция создана за пределами карточки. Этот срок жизни проверим после того, как научимся строить ссылку к нужному экрану.

### Слайд 23. `RouterLink` даёт браузеру ссылку

В to указываем имя schedule. RouterLink находит путь /schedule в таблице, а выбранный режим истории добавляет к нему #. Так значение из конфигурации становится адресом, по которому может перейти браузер.

[click] Браузер получает обычный элемент a с href. Его можно открыть клавишей Enter, скопировать или открыть в новой вкладке. При обычном клике переходом управляет Vue Router. В новой вкладке приложение запускается заново и читает путь из адреса. Оба способа проверим на живом списке.

### Слайд 24. `params` выбирают событие

Один экран карточки подходит двум событиям. В записи event путь содержит :eventId. Это имя обязательного сегмента пути. Ключ будет одним и тем же, а значение зависит от выбранного события.

[click] В списке расписания передаём имя маршрута и event.id под ключом eventId. Получаем /events/frontend-meetup или /events/css-workshop. Значение подставляется в сегмент после /events/. На следующем шаге прочитаем его при переходе в карточку.

### Слайд 25. Маршрут передаёт `eventId` странице

После перехода Vue Router разобрал путь и положил значение сегмента в route.params.eventId. Функция eventProps подготавливает объект для передачи. Проверка typeof уточняет форму входа и гарантирует, что prop будет строкой.

[click] Добавляем eventRoute в таблицу маршрутов. Запись связывает EventPage с eventProps: роутер вызывает функцию и передаёт полученный eventId как обычный prop.

[click] Страница ищет значение в каталоге через findEvent. Для /events/missing строка подходит как параметр маршрута, а события с таким ID в каталоге нет. computed повторит поиск при смене prop у уже существующей страницы.

### Слайд 26. При смене события экземпляр страницы может сохраниться

[На карточке Frontend Meetup показать ID и «изменений prop после setup: 0». Нажать «CSS Workshop» в шапке и отметить новые заголовок и счётчик.]

Заголовок показывает CSS Workshop, счётчик становится равен 1. Меняется только параметр одной записи маршрута. Vue повторно использует EventPage, передаёт ему новый eventId, а computed находит новое событие. При возврате по ссылке «Frontend Meetup» счётчик станет равен 2. Кнопка «Начать заново» заново загрузит стенд по первоначальному адресу и создаст экземпляр со счётчиком 0.

Это наблюдение пригодится для загрузки. Если один раз прочитать eventId в onMounted, запрос для второго события из такого перехода сам не начнётся. Поэтому в главе о чтении будем наблюдать за идентификатором. Параметр пути отвечает за выбор события, а теперь добавим отдельное условие для его списка.

### Слайд 27. `query` описывает настройку списка

Добавим к адресу списка ?minSeats=2. Путь по-прежнему выбирает экран заявок Frontend Meetup, а параметр после вопросительного знака описывает условие просмотра. useRoute даёт реактивный текущий маршрут, у которого можно прочитать обе части.

В примере route.query.minSeats даёт строку '2'. Без параметра значение будет undefined, а вручную введённый текст может оказаться произвольной строкой. Перед фильтрацией сопоставим все эти входы с одним порогом по правилу на следующем слайде.

### Слайд 28. У параметра из адреса есть допустимые значения

Адрес может написать пользователь. Для minSeats получим строку, null при ключе без значения, массив при повторе параметра или undefined при его отсутствии. На слайде Value — сокращённое имя для LocationQueryValue из Vue Router, то есть строки или null. Договор переключателя принимает строго строку '2', остальные значения дают порог 1.

[click] Первый computed переводит вход из адреса в порог. Второй применяет его к полной коллекции. В источнике count всегда от 1 до 5, поэтому порог 1 показывает все заявки. При ?minSeats=abc получаем другую строку, а при ?minSeats=2&minSeats=2 — массив. Ни один вход не равен строке '2', поэтому в обоих случаях видны все записи.

### Слайд 29. Переключатель записывает новое условие в URL

Когда пользователь меняет флажок, обработчик получает true или false. Текущий маршрут читаем через useRoute. Команды перехода даёт useRouter. Сначала копируем query, затем записываем строку '2' или удаляем ключ minSeats. Остальные параметры берём из копии.

[click] push добавляет новый адрес в историю. Когда адрес меняется, checked и видимые строки снова выводятся из minSeats. Поэтому «Назад» возвращает прежний порог. Для автоматического исправления опечатки подошёл бы replace, который заменяет текущую запись истории. В стенде опечатка уже имеет безопасное значение по умолчанию, так что этот вариант рассматриваем как отдельное решение.

### Слайд 30. Один список в двух адресах

[Нажать «Открыть отдельно», чтобы история вкладки стенда была видна в браузере. На Frontend Meetup с тремя строками включить «От двух мест». При включённом фильтре виден Борис, у которого в опубликованном наборе два места. В другой вкладке открывается тот же отбор, потому что флажок и список вычисляются из адреса. «Назад» снимает флажок и восстанавливает Анну, Бориса и Веру. «Вперёд» снова оставляет Бориса. Условие minSeats=2 находится после # и относится к маршруту. Параметр demo перед # выбирает учебный режим стенда. Если удалить только minSeats, экран и событие останутся прежними. Поэтому порог читаем отдельно от пути.

Для /unknown роутер доходит до общего маршрута «Страница не найдена». Причину видно в таблице маршрутов. Для /events/missing путь подходит под /events/:eventId. Компонент карточки получает missing, ищет его в каталоге и выводит «Событие не найдено». В обоих случаях приложение уже загрузилось. Следующее требование звучит иначе. Когда локально добавили заявку и вышли в расписание, шапка должна учесть заявку. В адресе есть описание выбора экрана. Покажем отдельно время жизни коллекции.

## Глава 03. Кто владеет состоянием между экранами?

### Слайд 34. Кто владеет состоянием между экранами?

Страница теперь получает событие из адреса. На схеме FSD мы уже выбрали, где хранить код формы и её правил. Созданные этими модулями значения имеют разные сроки жизни. Черновик нужен только текущей форме, а принятую заявку должна учесть сводка на другом экране.

Сначала оставим коллекцию внутри страницы и проверим, сколько она живёт. По результату выберем владельца, который переживает смену экрана. Pinia даст карточке и шапке доступ к этому общему состоянию. Место модуля в дереве и срок жизни конкретного экземпляра теперь можно объяснить по отдельности.

### Слайд 35. Почему пропадает локальная заявка после перехода?

[На карточке Frontend Meetup показать Анну и Бориса и итог «3 места». Ввести «Вера» в «Имя» и 2 в «Число мест», нажать «Добавить». Показать пять мест. Перейти в «Расписание» и открыть Frontend Meetup заново.]

После возвращения у карточки снова три места, а в списке только Анна и Борис. В режиме page-state начальные записи создаются в setup страницы. При переходе в расписание экземпляр размонтирован. Вернувшись, мы создаём новый экземпляр и заново получаем начальный набор. App продолжает существовать, поэтому там можно было бы хранить общую коллекцию. Сначала отделим от неё черновик, который должен исчезать вместе с формой.

### Слайд 36. Черновик принадлежит форме

До отправки имя и число мест описывают текущий ввод. Когда форма отправляет проверенные данные, владелец коллекции создаёт новую запись. Такой путь мы уже использовали в лекции 11.

Здесь key получает eventId. Даже когда при смене параметра Vue сохраняет EventPage, у вложенной RegistrationForm меняется ключ, поэтому Vue создаёт новый экземпляр формы. В CSS Workshop поле «Имя» будет пустым, «Число мест» начнётся с 1. Уже принятые записи лежат у владельца коллекции и остаются там при смене ключа формы.

### Слайд 37. Коллекцию можно поднять к общему родителю

В лекции 11 форма и список были соседями. Страница принимала событие submit, меняла свои строки и передавала их списку. Это всё ещё удобная модель для значений, которые нужны только на одной странице.

Шапка находится в App, выше страницы. Можно поднять коллекцию в App и передавать её страницам как props, а действия — как обработчики через RouterView. Коллекция тогда проживёт столько же, сколько приложение. В нашем проекте подключим Pinia, чтобы шапка и страницы получали одну коллекцию по имени хранилища. В composable из лекции 11 каждый вызов создавал своё состояние. Здесь двум потребителям нужен один экземпляр хранилища в приложении.

### Слайд 38. Хранилище связывает потребителей одной коллекции

На этой схеме изменяемое значение одно — локальная коллекция. Число мест в шапке и строки карточки выводятся из неё, поэтому один успешный submit даёт два согласованных результата. Правило допустимого числа мест проверяется в операции записи, а форма сообщает об ограничении во время ввода.

Проследите два чтения после добавления Веры. Из коллекции карточка получает новую строку, а шапка — новую сумму. Если хранить сумму отдельным изменяемым числом, при удалении придётся синхронно обновлять и строки, и сумму. Здесь сумма пересчитывается из строк, поэтому достаточно одной операции удаления. Черновик остаётся в экземпляре формы, а фильтр списка приходит из URL. Они уже имеют владельцев с нужным сроком жизни.

### Слайд 39. Pinia подключается при сборке приложения

В точке входа добавляем одну строку рядом с подключением роутера. createPinia создаёт экземпляр Pinia, а app.use связывает его с Vue-приложением до запуска компонентов. Хранилища будут создаваться в контексте этого экземпляра приложения.

Порядок в main.ts важен. Сначала подключаем плагины, потом монтируем App. Когда setup в App и в карточке обратится к хранилищу, нужный контекст уже будет доступен. Если открыть тот же адрес в двух вкладках, каждая выполнит main.ts и получит свой экземпляр Pinia. Теперь посмотрим, как два вызова в одной вкладке находят общую коллекцию.

### Слайд 40. `defineStore` возвращает функцию доступа

В defineStore передаём идентификатор local-registrations и знакомую setup-функцию. В сокращённой версии она создаёт ref и возвращает его как поле хранилища. Что лежит в ref, посмотрим на следующем слайде.

[click] В шапке и в карточке вызываем одну функцию доступа. При первом обращении Pinia создаёт хранилище, при следующем находит его по идентификатору в том же экземпляре Pinia. Обе части читают одну коллекцию. Свяжите это наблюдение с двумя независимыми счётчиками из предыдущего примера.

### Слайд 41. Данные хранятся по идентификаторам событий

initialRows возвращает начальный объект для ref из предыдущего слайда. Если открыть CSS Workshop, страница возьмёт пустой пока массив по его ключу. Запись Бориса относится к Frontend Meetup и лежит в другом массиве. Для удаления нужны сначала ключ события, затем id заявки внутри выбранной коллекции.

Проведите пальцем по двум уровням. Если удалить Бориса, сначала ищем массив frontend-meetup, потом запись по её id. Позиция Бориса среди видимых строк могла измениться. Если в CSS Workshop пока пусто, его массив существует и первая запись попадёт именно туда. Для сводки в шапке понадобится пройти по обоим массивам и сложить число мест из записей.

### Слайд 42. Сводка вычисляется из заявок

Object.values даёт массивы двух событий, totalIn складывает count каждой коллекции, reduce суммирует промежуточные итоги. Сначала у Анны два места, у Бориса одно, CSS Workshop пуст. Поэтому в сводке три места. Когда действие добавит Веру на два места в реактивный массив, computed пересчитается и даст пять.

Если после добавления Веры удалить Бориса, у Анны и Веры останется по два места. Сумма будет равна четырём. totalIn читает count у оставшихся записей, а computed повторит вычисление при изменении массива. При переходе в CSS Workshop сводка всё ещё покажет четыре места, потому что getter складывает записи всех событий.

### Слайд 43. Действие хранилища оформляет правила добавления

В EventPage обработчик submit вызывает store.add(eventId, draft). Событие формы даёт имя и число мест, а страница знает, для какого события их использовать. Действие сначала находит нужный массив и приводит имя к ожидаемой форме.

[click] Форма уже проверила ввод ради обратной связи пользователю. Здесь проверка относится к операции добавления: любой потребитель этого действия получает те же условия. Разрешаем непустое имя и целое число от одного до пяти в существующей коллекции.

[click] После проверки выдаём устойчивый id и добавляем запись. Следующий id увеличится только после успешного ввода. Удаление тоже проходит через действие: страница передаёт eventId и id из списка. Pinia допускает прямую запись, а действия дают проекту понятное место для проверки и изменения данных.

### Слайд 44. Как читать сводку и сохранить реактивность

В шаблоне можно обращаться прямо к store.totalSeats. Если извлечь значение обычной деструктуризацией, snapshot получит текущее число. При старте это три. После добавления Веры на два места свойство store.totalSeats уже покажет пять, а переменная snapshot сохранит три.

[click] В шапке применяем storeToRefs и деструктурируем объект с реактивными ссылками. После добавления totalSeats.value в script и totalSeats в шаблоне показывают пять. Оба варианта чтения в шаблоне, прямой store.totalSeats и ссылка из storeToRefs, используют текущее значение. Действие вызовем через store.add. В следующем опыте покажем сводку после перехода.

### Слайд 45. Одна заявка видна на разных экранах

[Открыть карточку Frontend Meetup с итогом «Локальные заявки: 3 места». Через поля «Имя» и «Число мест» добавить Веру на два места. В rowsByEventId меняется массив frontend-meetup, итог считается из его строк. Если перезагрузить документ, коллекция начнётся с исходных записей. [Для короткой проверки черновика после удаления Веры ввести имя без отправки и перейти по ссылке «CSS Workshop» в шапке. Новая форма откроется с пустым именем, а общая сводка покажет три места по Frontend Meetup.]

Ссылка читается роутером и восстанавливает порог. Для более долгого хранения нужен отдельный механизм, подобный тому, который мы разбирали в лекции 07.

Следующий список приходит извне. Для него нужен свой срок актуальности, даже когда локальная сводка продолжает работать.

## Глава 04. Кто отвечает за получение данных?

### Слайд 47. Кто отвечает за получение данных?

Наше хранилище отвечает за локальные заявки этой вкладки. У опубликованного списка другой владелец данных — внешний API. Вернёмся к границе между страницей и сегментом api из первой главы. Вспомните переход с Frontend Meetup на CSS Workshop, при котором сохранялся экземпляр страницы, а eventId изменился.

Возьмём знакомые fetch и проверку ответа из лекции 10. Через provide/inject точка входа передаст странице подходящий клиент. Это выбор реализации, которую получит уже собранный сценарий. Загрузку и её отмену свяжем с текущим событием. Затем проверим договор страницы при подмене клиента.

### Слайд 48. У двух списков разные источники

На карточке Борис занимает одно место, а в опубликованном образце два. Это разные учебные коллекции. Левая показывает работу формы и общего состояния. Правая имитирует опубликованные данные: их источник определяет, какие записи мы получим для события. Поэтому при локальном добавлении меняется сводка Pinia. В списке из API появится то, что вернул клиент.

Сводка нужна на нескольких экранах, а опубликованные записи сейчас нужны одной странице. Страница управляет сроком жизни чтения. Дальше описываем договор клиента — его вход и результат, которым сможет воспользоваться страница.

### Слайд 49. Клиент обещает проверенные записи

Начнём с результата. Страница хочет строки со знакомыми полями id, name и count. Это данные, из которых получится список и его фильтр.

[click] Метод list принимает идентификатор события и сигнал отмены. Успешный Promise даёт проверенные строки. В HTTP-реализации sourceByEvent сопоставляет знакомый eventId с URL. Для Frontend Meetup читаем ресурс с тремя заявками, для CSS Workshop — ресурс с пустым массивом. Формат проверяет знакомый loadRegistrations из лекции 10. По тому же договору list можно подключить и клиент, который вернёт готовый массив. Теперь разделим, откуда страница получает событие и откуда получает саму реализацию list.

### Слайд 50. Клиент страницы приходит из дерева Vue

У страницы два разных входа. Через props она получает eventId, то есть событие, заявки которого нужно показать. На обычном маршруте идентификатор приходит из URL. На учебном маршруте его явно передаёт обёртка DependencyPage. В обоих показах это frontend-meetup.

Второй вход — клиент, который умеет выполнить list. Точка сборки создаёт HTTP-клиент и предоставляет его под общим ключом. Потомок читает значение по этому ключу через inject. Промежуточным компонентам достаточно отобразить своё поддерево. Если предок предоставит под тем же ключом учебный клиент, страница вызовет тот же list для того же события и получит другой результат. Так можно проверить пустой список для Frontend Meetup или подать заранее известные данные в тесте. Дальше посмотрим, как обе стороны используют один ключ.

### Слайд 51. `provide` связывает ключ с конкретным клиентом

registrationsApiKey создаём один раз и импортируем в обоих местах. Это Symbol, по которому Vue найдёт значение. Два Symbol с одним и тем же описанием дадут разные ключи. InjectionKey связывает этот ключ с типом RegistrationsApi, поэтому TypeScript может проверить, какой объект мы предоставляем и какую форму получаем при чтении.

[click] В main.ts создаём конкретный HTTP-клиент. В app.provide первый аргумент — ключ, второй — уже созданный объект с методом list. Vue делает этот объект доступным в дереве приложения. Под этим же ключом конкретный компонент сможет задать другой объект для своих потомков. Теперь увидим, какой вариант получит страница.

### Слайд 52. `inject` ищет ключ по цепочке предков

На обоих маршрутах RegistrationsPage в setup вызывает useRegistrationsApi. Внутри этой функции inject смотрит на предков компонента, начиная с ближайшего. На маршруте «HTTP» ключа у предков нет, поэтому находится клиент, который предоставило приложение. Если ключ вообще нигде не задан, inject возвращает undefined и проверка сразу обнаруживает ошибку сборки. С полученным объектом страница может вызвать list.

[click] На маршруте «Подмена клиента» DependencyPage оборачивает ту же RegistrationsPage. Он предоставляет emptyRegistrationsApi под тем же registrationsApiKey. Vue находит ключ ближе к странице и берёт этот клиент. У остальных веток приложения по-прежнему свой путь поиска. На показе будет видно, как смена поставщика влияет на список при одном eventId.

[Открыть стенд отдельно на маршруте «Подмена клиента». Показать заголовок Frontend Meetup и подпись про ближайшего поставщика. В Network очистить журнал, включить Fetch/XHR и перезагрузить вкладку. На обоих маршрутах открыт Frontend Meetup, поэтому eventId одинаковый. В поддереве DependencyPage страница получает учебный клиент, list которого возвращает пустой массив. На маршруте «HTTP» Vue находит клиент приложения. В Network виден JSON, а на странице — Анна, Борис и Вера. Метод для страницы в обоих случаях называется list. Выбор реализации принадлежит поставщику, а запуск чтения и отображение результата — странице. Дальше свяжем запуск чтения уже со сменой самого события.

### Слайд 54. Страница связывает событие, клиент и загрузку

В RegistrationsPage начинаем с проверенного события. Без совпадения в каталоге экран покажет «Событие не найдено», а composable получит отсутствие идентификатора и не начнёт работу.

[click] Затем передаём идентификатор и клиента в composable. Клиент приходит из useRegistrationsApi, который читает ближайшее предоставленное значение. Composable вызывает его метод list и управляет отменой и обработкой ответа. Наружу он отдаёт строки, фазу и команду refresh. report в примере — сокращённое имя функции для журнала стенда.

[click] На странице остаются порог из URL и выбор сообщения в шаблоне. Порог меняет отображаемые строки, а смена события требует нового чтения. На следующем слайде увидим, какие значения наблюдает загрузчик и когда он отменяет предыдущую работу.

### Слайд 55. Загрузка следует за выбранным событием

watch наблюдает за двумя входами. eventId меняется при переходе на другое известное событие. revision — счётчик ручных обновлений. С immediate первое чтение начинается и при открытии прямой ссылки. Фильтр применяется к полученным строкам отдельно. Его query не входит в этот watch.

[click] Для каждого запуска создаём контроллер и до await регистрируем очистку. Когда вход меняется или экран размонтируется, onCleanup вызывает abort для прежней операции.

[click] Клиент получает сигнал. Даже если источник вернёт результат после отмены, проверка signal.aborted защитит текущий экран. applyResult на слайде сокращает запись результата с его eventId и смену фазы загрузки.

[click] Отмена может отклонить Promise. catch ловит этот исход, и проверка сигнала пропускает ошибки отменённой операции. В рабочем коде отмену записываем в журнал, а applyError здесь обозначает переход в фазу ошибки только для актуального запроса. Посмотрим, как эти фазы выглядят на странице.

### Слайд 56. Экран объясняет результат запроса

При первом чтении видим «Загрузка…». hasData становится истинным после успешного результата, в том числе после получения пустого массива. Для CSS Workshop это значит «Заявок пока нет». Если в проекте список содержит только заявки на одно место, то включение «От двух мест» даст другой случай: rows есть, а visible пуст. Тогда можно сообщить «По этому фильтру заявок нет» и предложить снять флажок.

При обновлении того же события уже есть проверенный результат. Оставляем его на экране, пока статус сообщает «Обновляем список…». При ошибке рядом появятся объяснение и кнопка «Повторить». При смене события прежние строки относятся к другому идентификатору. Экран CSS Workshop покажет своё состояние загрузки, иначе заявки Frontend Meetup выглядели бы как заявки на CSS Workshop. Это видно в следующем показе.

Даже если клиент проигнорирует сигнал и вернёт старые записи, проверка signal.aborted остановит их применение. Отмена завершает прежнюю работу, а проверка сигнала защищает экран от результата этой операции.

Страница управляет сроком жизни запроса. Дальше посмотрим на другую границу: клиент может сменить способ чтения ответа, пока страница продолжает работать со знакомыми строками.

[click] При чтении новой версии ответа клиент передаёт новый парсер третьим аргументом. HTTP-запрос и проверка статуса остаются в loadRegistrations, а результат метода list всё так же массив записей. Проверим это на следующем слайде одним изменением.

## Глава 05. Где живёт язык интерфейса?

### Слайд 60. Где живёт язык интерфейса?

Подпись фильтра хорошо показывает новую обязанность. Мы знаем правило minSeats и место, где оно применяется. Пользователь хочет прочитать ту же команду на другом языке. Язык нужен всем экранам, поэтому его выбор относится к приложению. Каждая страница знает, какое сообщение показать, в том числе имя элемента для вспомогательных технологий.

Vue I18n поможет выбирать сообщения и форматы по текущему языку. Начнём с одной подписи, затем разберём параметры, формы слов и сообщения об ошибке.

### Слайд 61. Перевод начинается с целого сообщения

Один ключ обозначает смысл команды, а словарь даёт целое выражение на каждом языке. Переводчик может подобрать порядок слов и формулировку. Так же оформим сообщение об ошибке и подсказку поля.

Название minSeats встречали в URL. В адресе его значение '2' задаёт порог. В словаре ключ с таким же именем выбирает подпись. Чтобы заменить подпись на «Два места и больше», достаточно исправить сообщение в словаре. Правило readMinSeats и ссылки с minSeats=2 продолжают работать. Если меняется сам порог, пересматриваем это правило и сверяем с ним формулировки в обоих языках.

### Слайд 62. `createI18n` подключает словари и начальный язык

Здесь основа makeI18n. messages связывает ru и en с их словарями. locale задаёт русский при запуске. fallbackLocale определяет запасной язык для отсутствующего сообщения. После выбора English Vue I18n сперва ищет сообщение в en и обращается к ru, когда ключ пропущен. legacy: false включает режим Composition API, которым воспользуемся в компонентах.

[click] В точке входа подключаем i18n через app.use до монтирования, как делали с роутером и Pinia. Компоненты шапки и списка получат переводчик для общей локали. Следующий слайд показывает один такой вызов и параметр, который сохранит имя участника в полной фразе.

### Слайд 63. `t` возвращает сообщение текущего языка

Из useI18n берём t для общей локали. В первой строке шаблона t читает подпись minSeats из текущего словаря и возвращает готовый текст.

[click] Ключ removeNamed даёт целую фразу с местом для параметра name. Например, «Удалить заявку: Анна» и «Remove registration: Анна». Видимые подписи кнопок совпадают, а доступные имена указывают на разные заявки. Теперь посмотрим, как сменить локаль, которую читает t.

### Слайд 64. Переключатель меняет общую `locale`

В App селект связан через v-model с общей locale. Выбор English записывает en. Все компоненты, читающие сообщения из общего словаря, обновляют представление.

[click] Watcher переносит выбранный язык в атрибут html lang для вспомогательных технологий. Благодаря immediate язык документа указан и при первом запуске. В этом стенде каждый запуск начинается с ru, а сохранение предпочтения можно добавить в проекте. Сначала посмотрим, как выбранный язык влияет не только на подписи, но и на форму сообщений с числами.

### Слайд 65. Число определяет форму слова

В t передаём числовой count. Ключ seats содержит три варианта целого сообщения, разделённых вертикальной чертой. В «1 место» и «21 место» нужна одна форма слова. Условие count === 1 охватило бы только первый случай.

[click] Настройка pluralRules.ru передаётся в createI18n вместе со словарями. Для числа мест Intl.PluralRules определяет категорию русского языка. Переводим one, few и many в индексы 0, 1 и 2. Например, 21 даёт one и форму «21 место», 11 даёт many и «11 мест», 22 даёт few и «22 места». Для дробных значений понадобилась бы отдельная проверка набора форм.

### Слайд 66. Дата и число получают формат при выводе

На расписании d получает дату начала события и настройки schedule для текущей локали. У ru и en стенд использует один часовой пояс Europe/Moscow. Поэтому 4 декабря и December 4 описывают тот же момент. Меняются порядок частей даты и формат времени.

[click] n форматирует число для вывода. В строке API форматированное значение подставляется в сообщение, а числовой count по-прежнему выбирает множественную форму. На небольшом числе разделители могут не отличаться. Для показа в консоли можно сравнить Intl.NumberFormat('ru').format(12345.67) и тот же вызов для en.

### Слайд 67. Ошибка получает пользовательский текст на странице

При имитации 503 composable выставляет фазу unavailable. Страница читает t('unavailable'), показывает «Источник временно недоступен» и даёт кнопку «Повторить». Если пришли неверные поля, она читает t('loadError'). Техническая причина остаётся в журнале. Для ошибки используется role="alert", поэтому доступный текст тоже должен соответствовать языку пользователя.

Если выбрать English при уже видимой ошибке, текст и имя кнопки изменятся. computed заново прочитает t для той же фазы. Чтение списка запускается от eventId и refresh, поэтому смена языка сохраняет текущий результат запроса. Меняется способ объяснения ошибки, а её причина и действие пользователя остаются прежними.

[Нажать «Открыть отдельно». Показать /events/frontend-meetup/registrations?minSeats=2 после #. Дождаться строки «Борис · 2 места» и показать включённый флажок «От двух мест». Выбрать English в поле «Язык» и сопоставить новую строку списка с подписью флажка.]

На входе адрес выбирает экран и порог, а чтение по HTTP даёт строки. После выбора English заголовок «API registrations» и строка «Борис · 2 seats» подтверждают смену языка. Флажок всё ещё включён и подписан по-русски: переводчик нашёл ключ в fallbackLocale: 'ru'. В этом опыте подпись помечена lang="ru", чтобы вспомогательная технология могла произнести её на нужном языке.

Отбор сохранился благодаря query. Строка появилась из проверенного ответа HTTP. Русский текст пришёл из запасного словаря, потому что из английского словаря удалён ключ minSeats. В режиме разработки Vue I18n также сообщает о пропущенном ключе. Чтобы исправить подпись, добавляем minSeats в messages.en. Код отбора уже даёт нужный результат.

## Диагностика и итог

### Слайд 69. Диагностика начинается с владельца результата

Если скопированная ссылка открывает список без фильтра, начнём с query и проверки minSeats. Если пропала уже принятая заявка, найдём место создания коллекции и проверим, не создаётся ли она снова при переходе. Если после перехода видны записи прошлого события, проверим его идентификатор в результате и отмену прежнего чтения. Если после переноса формы редактор не находит старый путь, найдём импорт и сверим его с публичным входом. Если одна подпись осталась на русском, начнём со словаря и резервного языка.

В каждом случае идём от наблюдаемого результата к входу, от которого он зависит. Место, где значение перестаёт соответствовать договору, показывает, какой модуль или состояние нужно менять.

### Слайд 70. Границы приложения дают проверяемые договоры

Вернёмся к просьбе из начала лекции — прислать ссылку на нужный список. В новой вкладке Vue Router выбирает экран Frontend Meetup, страница читает minSeats=2, а клиент возвращает записи. Поэтому включённый фильтр оставляет Бориса. Если источник недоступен, страница показывает «Источник временно недоступен» и даёт кнопку «Повторить». Так у каждого ожидаемого результата есть вход и владелец.

Такие сценарии помогают описать поведение проекта в ЛР 5. На следующей лекции превратим их в тесты. Проверку строки из URL можно закрепить тестом функции, поведение формы — тестом компонента, работу ссылки и истории — тестом в браузере.

## Приложение A. Маршрутизация

### Слайд 71. Дополнительно · как усложняется маршрутизация?

Этот дополнительный раздел стоит выбрать, если в проекте несколько экранов одного события. Родительский URL может представлять событие, а дочерние маршруты — вкладки или подробности. Общая рамка остаётся на месте при смене дочернего экрана.

Во вложенном варианте у записи /events/:eventId появляются children, а внутри EventShell — свой RouterView. Дочерняя запись с пустым путём покажет карточку по /events/frontend-meetup, а относительный путь registrations даст прежний URL списка. Шапка EventShell с датой события будет общей для этих двух экранов.

EventShell может владеть состоянием, которое должно пережить переключение между карточкой и списком одного события. Переход к другому eventId всё ещё требует реакции на новый параметр. Вложенная структура оправдана, когда у дочерних экранов есть общий интерфейс или состояние.

### Слайд 72. Как выбрать режим истории для хостинга?

Откроем одну карточку двумя адресами. Для /events/frontend-meetup браузер запрашивает этот путь у сервера, поэтому хост должен вернуть HTML приложения. Для адреса с # браузер запрашивает документ по пути до #. В обоих случаях после загрузки Vue Router выбирает EventPage, но сервер получает разные запросы.

[Открыть собранный стенд и отдельный dev-сервер стенда с --mode history. На обоих открыть карточку Frontend Meetup напрямую. В Network найти первый запрос типа Document и сравнить Request URL.]

Для статического хоста без настройки выдачи index.html по произвольным путям подходит hash-режим. Если хост поддерживает такую выдачу для маршрутов приложения, можно обойтись без #. Запросы к файлам и API при этом должны сохранять собственные адреса и статусы.

### Слайд 73. Проверка перед уходом со страницы с черновиком

Это дополнительный механизм для маршрутов с существенным черновиком. Пользователь ввёл длинный ответ и нажал ссылку «Расписание». dirty.value показывает, есть ли несохранённый ввод. Когда он истинен, обработчик возвращает ответ диалога. Если человек выбрал «Отмена», false прерывает переход и он остаётся на форме со своим вводом. Если dirty ложно или пользователь подтвердил уход, переход может продолжиться.

Frontend Meetup и CSS Workshop открываются по одной записи маршрута. Смена eventId может сохранить компонент страницы. Если при такой смене тоже нужно подтверждение, его добавляют через onBeforeRouteUpdate. Перезагрузка документа относится к событиям браузера. На слайде проектный фрагмент для длинного черновика. В стенде короткая форма сбрасывается по ключу события, как в основном показе.

### Слайд 74. Код экрана можно загрузить при первом открытии

Поле component здесь получает функцию. При открытии маршрута Vue Router вызовет её, а import вернёт обещание модуля страницы. После загрузки компонента запустится setup и только тогда watcher вызовет клиент для чтения JSON. В Network это два ресурса с разными причинами запроса.

Для такого показа нужен вариант с отложенной загрузкой обычного маршрута и DependencyPage. В стенде DependencyPage статически импортирует RegistrationsPage, поэтому при изменении только одной записи код уже может быть в начальной загрузке. При первом переходе из расписания загружается модуль страницы. При повторном переходе он уже доступен, а чтение данных при новом монтировании по-прежнему запускает watcher. По Network можно различить запрос модуля и запрос данных.

## Приложение B. Состояние

### Слайд 75. Дополнительно · как расширить срок жизни общего состояния?

В основном маршруте Pinia хранит данные одного запущенного приложения. Бывает, что значение нужно только внутри одной ветки интерфейса. Например, общий блок расписания и его фильтры могут читать выбранное событие от ближайшего поставщика.

Поставщик может передать пару из readonly(selectedEvent) и selectEvent. Потомки читают значение и вызывают операцию, а изменение выполняется в поставщике. Два поставщика с одинаковым ключом обслуживают разные поддеревья. На следующем слайде проследим, когда состояние всего приложения может пережить переход, а когда начинается заново.

### Слайд 76. Общее состояние и сохранение дают разные наблюдения

[В стенде со слайда 45 добавить Веру на два места. Перейти в расписание, открыть адрес карточки в новой вкладке, затем перезагрузить исходную вкладку. Сопоставить итоги шапки.]

После перехода в расписание в шапке по-прежнему пять мест, потому что работает тот же экземпляр Pinia. В новой вкладке и после перезагрузки исходной вкладки снова три места. В обоих случаях приложение запускается заново и создаёт исходную коллекцию.

Если заявки должны переживать перезагрузку, при старте приложения читаем сохранённый снимок. Этот сценарий хранения разобран в лекции 07.

## Приложение C. Локализация

### Слайд 77. Дополнительно · как развивать локализацию в проекте?

Основная версия начинает с русского языка. При выборе языка на старте приложение может сначала прочитать явное решение пользователя, затем найти подходящий язык браузера и в последнюю очередь взять значение по умолчанию. Неподдерживаемый вариант нужно привести к поддерживаемому до показа интерфейса.

Пользователь вчера явно выбрал English, а сегодня браузер предлагает ru-RU. При описанном порядке открываем интерфейс на английском. Если явного выбора нет, ищем локаль из поддерживаемых, например сопоставляем ru-RU с ru. Язык по умолчанию нужен для последнего шага выбора. Поиск отдельной пропущенной фразы в запасном словаре, как на слайде 68, происходит уже после выбора активной локали.

### Слайд 78. Словарь можно загрузить при выборе языка

Допустим, английский словарь стал большим и его решили загружать после выбора English. Пока модуль в пути, можно показать ожидание в переключателе и оставить читаемый русский интерфейс. После успешной загрузки подключаем сообщения и только потом меняем активную locale. Если поменять операции местами, компоненты попытаются читать ещё недоступные сообщения и могут временно показать запасные подписи.

Если человек выбрал English и сразу вернулся на «Русский», запоздавший модуль можно сохранить для будущего выбора. Активная локаль при этом остаётся русской. Если загрузка завершилась ошибкой, сохраняем текущую локаль и даём возможность повторить. В стенде оба небольших словаря доступны при запуске, а отложенная загрузка остаётся проектным вариантом.

### Слайд 79. Перевод нужен доступным именам и сообщениям

[Открыть полный режим примера по адресу с ?demo=full перед #. Из «Расписания» открыть Frontend Meetup. В дереве доступности найти кнопку «Удалить» в строке Анны. Выбрать English и проверить её имя снова.]

В карточке видны «Удалить» и «Remove» после переключения. Доступное имя содержит ещё имя участника, например «Удалить заявку: Анна» и «Remove registration: Анна». Спрашиваем, сможет ли человек выбрать нужную заявку, если услышит только короткое название кнопки. Здесь ключ removeNamed подставляет имя в полную фразу.

[Перейти по «API registrations», раскрыть «Условия демонстрации API», выбрать «Имитация 503» и нажать «Refresh». Когда появится ошибка, выбрать «Русский» в поле «Language».]

Оповещение стало русским, а кнопка «Retry» теперь называется «Повторить». Подпись кнопки и текст ошибки берутся из словаря. Такой показ выявляет жёстко заданные строки, которые не видны на скриншоте успешного списка.

### Слайд 80. Длинная подпись проверяет адаптивность

[В отдельной вкладке полного режима открыть «Заявки из API» для Frontend Meetup и сузить окно примерно до 360 CSS-пикселей. Выбрать English. Клавишей Tab пройти от шапки к флажку «Two seats or more» и кнопке «Refresh». Нажать Space на флажке.]

После переключения флажок остаётся доступен с клавиатуры, виден Борис, а строка адреса при необходимости переносится. Подпись читается целиком без горизонтальной прокрутки. При ошибке кнопка «Retry» должна оставаться доступной рядом с сообщением. Перекрытый текст указывает на проблему раскладки или длины подписи. Если элемент виден, а клавиатурой до него дойти нельзя, проверяем разметку и порядок фокуса. Этот показ связывает локализацию с адаптивностью из ранних лекций.

## Приложение D. FSD

### Слайд 81. Дополнительно · как проверить границы FSD?

Когда в проекте несколько слайсов, становится труднее читать дерево и отслеживать зависимости. В основной главе мы проверили публичный вход регистрации. Теперь у Frontend Meetup появились несколько групп экранов, а модели события и регистрации выросли отдельно.

Группировка слайсов помогает найти нужную страницу в дереве. Специальная точка входа делает связь сущностей явной. Дальше покажем, как ошибочный импорт через собственный публичный вход может замкнуть цикл и как линтер проверяет направление зависимостей. Каждый пример можно показать отдельно.

### Слайд 82. Группа помогает найти слайсы в дереве

В дополнительном варианте проект вырос. В pages удобно найти страницы мероприятия в папке meetup. Это группа для навигации по дереву. event и schedule остаются отдельными слайсами со своими входами. Импорт страницы из соседнего слайса по-прежнему нарушает правило слоя.

Если обеим страницам нужен блок с датой и местом, папка meetup/common сократит путь, но оставит неясным владельца кода. По назначению блока выбираем нижний слой, например entities/event для представления данных события. Тогда зависимость каждой страницы будет направлена вниз.

### Слайд 83. Сущность может явно открыть связь для другой сущности

Допустим, в большом проекте возникли две сущности — событие и регистрация. Тип регистрации хранит ссылку на событие. Если даже тип этой ссылки входит в модель события и связь важна для предметной области, FSD допускает для сущностей специальный публичный вход @x. Слайс event явно объявляет, какие имена он отдаёт слайсу registration.

[click] Путь в модели показывает, кто согласился на эту связь. Если для сценария достаточно обычного идентификатора или объекты связывает страница, дополнительный вход можно не вводить. Это исключение для сущностей. Переносить тот же приём на соседние страницы или фичи не следует.

### Слайд 84. Цикл можно найти по цепочке импортов

Если RegistrationForm берёт функцию расчёта из собственного index.ts, получается цикл. index.ts реэкспортирует форму, а форма импортирует index.ts. При загрузке модулей значение может ещё не успеть инициализироваться. Достаточно направить импорт формы прямо в файл model и оставить index.ts для потребителей снаружи.

У большого общего входа shared/ui другая проблема. За одним путём могут оказаться десятки несвязанных компонентов и их зависимостей. Для BasePanel удобен собственный вход shared/ui/base-panel. По пути видно, какой общий модуль нужен странице.

### Слайд 85. Линтер проверяет направление и точки входа

Steiger можно добавить в проект как архитектурный линтер. После подключения набора правил FSD команда npx steiger src проверит исходники. В учебном примере страница нарушает границу и импортирует features/registrations/ui/RegistrationForm.vue напрямую. Исправление начинается с публичного имени формы. Затем страница импортирует это имя через вход слайса.

Архитектурный линтер проверяет структуру файлов и зависимости. Чтобы убедиться, что после отправки формы итог вырос с трёх до пяти мест, проверяем страницу или пишем тест поведения. Стенд лекции даёт один перенесённый слайс для наблюдения. Для проверки всего проекта понадобилось бы закончить его перевод на выбранные правила.
