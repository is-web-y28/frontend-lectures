# Лекция 4. Современный CSS

> **Продолжительность основного занятия:** 90 минут.
>
> **Факультативный модуль:** 60 минут после основного занятия или отдельная дополнительная пара.
>
> **Цель:** научить студентов сохранять читаемую и управляемую раскладку при изменении условий: доступной ширины, пользовательских предпочтений и состояния интерфейса. Студент должен уметь выбирать между intrinsic-адаптивностью и media query, именовать повторяющиеся CSS-решения custom properties и добавлять безопасную motion-обратную связь.
>
> Текст рассчитан на произнесение. Пометки вида **[Слайд …]** обозначают переключение слайда; пометки в квадратных скобках — действия преподавателя и работа аудитории. Они включены в тайминг.

## Границы темы

Лекция продолжает лекцию 3. Там мы выбрали модель раскладки: normal flow, Flexbox, Grid или positioning. Здесь мы не заменяем эти механизмы новыми, а задаём условия, в которых они меняются.

В ядро входят responsive design, media queries, гибкие размеры, CSS custom properties, `transform`, `transition`, простые `@keyframes` и `prefers-reduced-motion`.

Сознательно не разбираем здесь:

- методологии именования, системное устройство токенов, nesting, cascade layers, Sass, PostCSS и utility-first — это лекция 5;
- `matchMedia()`, ручное переключение темы, `classList`, события `transitionend` и `animationend` — это JavaScript начиная с лекции 6;
- анимацию, управляемую React state, и глобальную тему через Context — это лекции 8 и 11;
- profiling, принципы layout/paint/composite и полный accessibility-аудит motion — это лекция 16.

`prefers-reduced-motion` остаётся в лекции 4: если мы учим создавать движение, то сразу должны показать, как не навязывать его пользователю.

## 0:00–0:07. От раскладки к условиям

**[Слайд 1 — «Современный CSS: интерфейс меняется вместе с условиями»]**

На прошлой лекции мы научились собирать страницу: normal flow задаёт естественный порядок, Flexbox строит одну ось, Grid — строки и колонки, positioning накладывает независимый элемент. У нас уже есть страница Frontend Meetup: программа, карточки событий, регистрация, кнопки и бейджи.

Но раскладка не существует в одном снимке экрана. Текст может стать длиннее. Ширина доступного пространства может уменьшиться. Пользователь может увеличить системный шрифт. Один и тот же компонент может оказаться в узкой боковой колонке и в широком основном содержимом.

Сегодня не будем рисовать отдельную страницу для каждого телефона. Мы опишем правила, которые сохраняют смысл и читаемость, когда условия меняются.

**[Слайд 2 — «Раскладка — это отношения, adaptive CSS — условия их сохранения»]**

В лекции 3 мы задавали отношения: «кнопки образуют группу», «карточки образуют сетку», «бейдж находится в углу карточки». В лекции 4 появляется ещё один вопрос:

> При каком условии это отношение надо изменить?

Например, блок регистрации и расписание могут быть рядом, пока у обоих остаётся полезная ширина. Когда её уже нет, они должны перейти один под другой. Это не ошибка Flexbox или Grid. Это новое условие для уже выбранной модели.

**[Слайд 3 — «Четыре условия современного CSS»]**

Сегодня рассмотрим четыре источника изменений:

1. доступное пространство;
2. пользовательские предпочтения;
3. состояние элемента;
4. повторяющиеся дизайнерские решения.

Доступное пространство обрабатывают гибкие размеры и media queries. Предпочтение меньшего движения — `prefers-reduced-motion`. Состояние элемента — псевдоклассы, `transition` и `animation`. Повторяющиеся решения получают имя через CSS custom properties.

**[Слайд 4 — «Одна страница, разные условия»]**

[Открыть пример Frontend Meetup. Сначала показать широкую раскладку, затем сузить viewport. Увеличить масштаб браузера до 200%.]

Не нужно пока называть свойство. Спросите аудиторию: что именно перестало работать? Ответ должен быть наблюдаемым: «текст в колонке слишком узкий», «кнопки не помещаются», «изображение выходит за границу». Формулировка «нужен breakpoint для планшета» ничего не объясняет.

## 0:07–0:20. Компонент, доступное пространство и mobile-first

**[Слайд 5 — «Не устройства ломаются — ломаются компоненты»]**

Устройства не образуют стабильный список. У одного телефона может быть широкое окно браузера, у ноутбука — узкая панель, а пользователь может увеличить масштаб. Поэтому мы не проектируем правила вида «это iPhone», «это iPad», «это ноутбук».

Мы наблюдаем компонент. Если карточка перестала иметь место для текста и действия, это и есть причина менять её раскладку.

Breakpoint — не марка устройства и не число, найденное в чужом шаблоне. Breakpoint — ширина, на которой текущая композиция перестала выполнять задачу.

**[Слайд 6 — «Mobile-first — базовое правило для малого пространства»]**

Начинаем с небольшой доступной ширины:

```css
.schedule {
  display: grid;
  gap: 1rem;
}
```

Здесь у Grid одна колонка по умолчанию. Это не «упрощённый мобильный макет». Это содержательная базовая версия: сначала программа, затем регистрация; текст получает всю доступную ширину; ничего не зависит от догадки о размере экрана.

Когда свободного пространства стало достаточно, мы добавим вторую колонку. Базовое правило не отменяется: широкая версия является дополнительной возможностью.

**[Слайд 7 — «Сначала содержание, затем декоративная композиция»]**

Mobile-first полезен не только для узких экранов. Он заставляет проверить, может ли документ существовать без горизонтальной композиции. Если при одной колонке порядок содержания стал непонятным, проблема не в media query. Нужно исправить HTML-структуру или порядок разделов.

В нашем примере пользователь должен сначала увидеть название и содержание события, затем действие регистрации. CSS может расположить блоки рядом, но не должен прятать смысл документа.

**[Слайд 8 — «Условие нужно наблюдать»]**

[Показать три ситуации и попросить аудиторию назвать проблему, а не свойство:]

- две карточки стали слишком узкими для заголовка;
- изображение стало шире карточки;
- две кнопки перестали помещаться в одну строку.

Ожидаемые ответы: «недостаточно ширины для двух колонок», «медиа не ограничено контейнером», «группа действий больше не помещается на основной оси». Только после этого выбираем CSS-механизм.

**[Слайд 9 — «Три проверки перед новым breakpoint»]**

Перед тем как написать media query, проверить:

1. можно ли оставить normal flow — одна колонка уже читаема;
2. может ли Flexbox перенести или перестроить группу;
3. может ли Grid самостоятельно выбрать число колонок через `minmax()` и `auto-fit`.

Media query нужен, когда дизайн действительно меняет правило: направление, число смысловых зон, размер отступа, порядок или видимость вспомогательного материала. Он не должен исправлять каждый случай переполнения отдельно.

## 0:20–0:35. Media queries

**[Слайд 10 — «Media query: правило при выполненном условии»]**

Media query добавляет правило только при выполнении условия. Базовые стили остаются обычным CSS:

```css
.schedule {
  display: grid;
  gap: 1rem;
}

@media (min-width: 48rem) {
  .schedule {
    grid-template-columns: repeat(2, 1fr);
  }
}
```

До `48rem` у `.schedule` одна колонка. Начиная с `48rem` Grid получает две одинаковые колонки. `repeat(2, 1fr)` — короткая запись для `1fr 1fr`: число повторений и размер каждого трека видны сразу.

Значение `48rem` не является универсальной рекомендацией. Оно выбрано потому, что в данном примере на этой ширине обе зоны сохраняют читабельность. В другом компоненте условие будет другим.

**[Слайд 11 — «Почему min-width, а не каталог max-width»]**

В mobile-first подходе мы добавляем возможности:

```css
.actions {
  display: flex;
  flex-direction: column;
  gap: 0.75rem;
}

@media (min-width: 36rem) {
  .actions {
    align-items: center;
    flex-direction: row;
  }
}
```

Базово действия расположены вертикально: у каждой кнопки есть место. При достаточной ширине они переходят в строку. Такой код читается как история интерфейса: сначала безопасная версия, затем условное улучшение.

Цепочка `max-width: 375px`, `max-width: 414px`, `max-width: 768px` часто превращает CSS в перечень случайных исключений. Она не отвечает, зачем каждое число существует.

**[Слайд 12 — «Breakpoint измеряет пространство, не класс устройства»]**

Почему здесь уместен `rem`, а не набор пикселей устройства? `rem` связывает условие с размером текста. Если пользователь увеличил базовый шрифт, breakpoint срабатывает раньше — в момент, когда тексту действительно нужно больше места.

Это не запрет на `px`. `px` подходит, когда нужен конкретный физический размер: например, граница в один CSS-пиксель. Но для условий, которые зависят от читаемости текста, `rem` часто выражает зависимость лучше.

**[Слайд 13 — «Проверка: один компонент, один повод изменить правило»]**

[Открыть DevTools, сужать viewport и остановиться там, где две зоны события начинают конфликтовать. Затем добавить media query.]

После изменения спросите: что стало другим?

- Grid не исчез;
- HTML не изменился;
- порядок документа не переставлен;
- изменилось только количество колонок при понятном условии.

Это ожидаемая адаптивность: один документ, одна семантика, несколько подходящих представлений.

**[Слайд 14 — «Не скрываем основное содержание ради ширины»]**

Плохой ответ на узкий экран:

```css
@media (max-width: 40rem) {
  .schedule {
    display: none;
  }
}
```

Если расписание нужно пользователю, его нельзя убрать только потому, что поменялась ширина. Меняем раскладку, размер второстепенного декора или плотность отступов, но не прячем основной смысл.

Скрывать можно дублирующую декоративную иллюстрацию или необязательный визуальный фон. Но если элемент нужен для задачи, он остаётся доступен и при узкой ширине.

**[Слайд 15 — «Попробуйте сами: когда группе действий стать строкой?»]**

[Дать две кнопки «Зарегистрироваться» и «Программа». Сначала студентам нужно сделать вертикальную группу, затем самостоятельно выбрать ширину, на которой переход в строку перестаёт сжимать подписи.]

Проверка решения:

- базовая версия работает без media query;
- правило меняет именно `flex-direction` или другое объяснимое отношение;
- у breakpoint есть наблюдаемая причина;
- кнопка сохраняет видимый `:focus-visible`.

## 0:35–0:48. Адаптивность без media query

**[Слайд 16 — «Не каждый responsive-случай требует условия»]**

Иногда браузер уже умеет выбрать устойчивую геометрию. Перед новым media query сначала выразим ограничение напрямую.

Для изображения обычно не нужен breakpoint:

```css
.event-card img {
  display: block;
  height: auto;
  max-width: 100%;
}
```

`max-width: 100%` означает: изображение может быть меньше естественного размера, но не выходит за ширину карточки. `height: auto` сохраняет пропорции.

**[Слайд 17 — «Grid может выбрать число колонок сам»]**

```css
.cards {
  display: grid;
  gap: 1rem;
  grid-template-columns: repeat(auto-fit, minmax(16rem, 1fr));
}
```

`minmax(16rem, 1fr)` задаёт границы одной колонки: она не уже `16rem`, но может получить долю свободного пространства. `auto-fit` подбирает столько таких колонок, сколько помещается в контейнер.

Это пример из лекции 3: Grid уже умеет сохранить полезную ширину карточки без условия по viewport. Такой вариант подходит для независимых карточек одинакового уровня.

**[Слайд 18 — «clamp() задаёт допустимый диапазон, а не один размер»]**

```css
.page-title {
  font-size: clamp(2rem, 5vw, 4rem);
}
```

`clamp(минимум, гибкое значение, максимум)` ограничивает изменение. Заголовок не станет меньше `2rem`, увеличивается вместе с viewport в средней области и не превысит `4rem`.

Не применяйте `vw` к основному тексту без ограничений. Для абзаца важнее стабильная читаемость и уважение к настройкам шрифта пользователя. `clamp()` уместнее для заметного заголовка или пространства между крупными секциями.

**[Слайд 19 — «Прогноз: media query или ограничение?»]**

[Показать три задачи. Попросить сначала выбрать механизм.]

1. Фото не должно выходить за карточку. — `max-width: 100%`.
2. Независимые карточки должны добавлять колонки только при полезной ширине. — `auto-fit` и `minmax()`.
3. Расписание и регистрация должны стать двумя неравными зонами. — media query и явная grid-схема.

Правильный ответ важнее синтаксиса: назвать отношение и ограничение, которое нужно сохранить.

**[Слайд 20 — «Адаптивная раскладка: сначала ограничение, затем условие»]**

Рабочая последовательность:

1. оставить содержимое в нормальном потоке;
2. дать медиа и коробкам гибкие размеры;
3. использовать Flexbox или Grid как механизм раскладки;
4. добавить media query только для реальной смены композиции;
5. проверить широкий, узкий и увеличенный текст.

[Попросить каждого открыть адаптивный режим DevTools и проверить свой пример в трёх ширинах.]

## 0:48–1:01. CSS custom properties

**[Слайд 21 — «Повторяющееся решение заслуживает имени»]**

В коде Frontend Meetup повторяются расстояния, границы и цвета. Если четыре карточки используют одинаковый отступ, это не четыре независимых числа. Это одно решение: внутренний отступ карточки.

CSS custom property даёт решению имя:

```css
:root {
  --space-2: 0.5rem;
  --space-4: 1rem;
  --surface: #ffffff;
  --border: #e7e1d6;
  --accent: #ee5a36;
}
```

Значение читается через `var()`:

```css
.event-card {
  background: var(--surface);
  border: 1px solid var(--border);
  padding: var(--space-4);
}
```

Не нужно выносить абсолютно каждое значение. Переменная полезна, когда значение повторяется, имеет роль или ожидаемо меняется вместе с другими правилами.

**[Слайд 22 — «Custom properties наследуются»]**

Custom properties принадлежат элементу и наследуются потомками:

```css
.event-card {
  --accent: #ee5a36;
}

.event-card__badge {
  background: var(--accent);
}
```

Теперь конкретная карточка может изменить accent, не затрагивая соседей:

```css
.workshop-card {
  --accent: #16827a;
}
```

`--accent` внутри `.workshop-card` переопределяет значение для самой карточки и её потомков. Это не JavaScript-переменная и не текстовый шаблон: браузер вычисляет значение для каждого элемента с учётом наследования и каскада.

**[Слайд 23 — «Область переменной — часть её смысла»]**

Размещаем переменную в ближайшем общем предке потребителей:

- `:root` — значение действительно общее для страницы;
- `.event-card` — решение относится к одной карточке и её потомкам;
- `.button` — значение нужно только конкретному компоненту.

Не нужно создавать огромный глобальный список `--blue-1`, `--blue-2`, `--blue-3` без ролей. Полная система дизайн-токенов, правила именования и тематические слои будут в лекции 5. Сейчас важна простая идея: одно решение получает имя там, где живёт его смысл.

**[Слайд 24 — «Fallback — запасное значение, а не способ скрыть ошибку»]**

```css
padding: var(--card-padding, 1rem);
```

`1rem` будет использован, если `--card-padding` не определён. Это полезно, когда переменная действительно необязательна: компонент может получить внешний отступ, но имеет безопасное значение по умолчанию.

Если `--card-padding` обязателен по контракту компонента, fallback может скрыть опечатку. В таком случае лучше определить переменную явно и увидеть проблему в DevTools.

**[Слайд 25 — «Практика: четыре числа — не четыре решения»]**

[Показать фрагмент с повторяющимися `#ee5a36`, `1rem` и `0.5rem`. Попросить студентов выделить значения, которые выражают одну роль, и заменить только их.]

После замены спросите:

- какое решение теперь можно изменить в одном месте?
- у какого предка должна находиться переменная?
- не стал ли код хуже из-за переменной для единичного значения?

## 1:01–1:14. Transform и transition

**[Слайд 26 — «Визуально сдвинуть — не значит переложить»]**

`transform` меняет визуальное представление элемента. Он не делает новый расчёт normal flow и не освобождает место для соседей.

```css
.event-card:hover {
  transform: translateY(-0.25rem);
}
```

Карточка выглядит чуть выше, но соседняя карточка остаётся на прежнем месте. Это другое поведение, чем у `margin-top` или изменения высоты.

Связь с лекцией 3 прямая: transform не заменяет Flexbox, Grid, margin и positioning. Он подходит для краткой визуальной обратной связи, а не для основной геометрии страницы.

**[Слайд 27 — «Document flow и transform отвечают на разные вопросы»]**

Сравним:

```css
/* меняет место в раскладке, соседи реагируют */
.event-card:hover {
  margin-top: -0.25rem;
}

/* меняет только визуальное представление */
.event-card:hover {
  transform: translateY(-0.25rem);
}
```

[В DevTools по очереди включить оба правила. Попросить аудиторию заметить, сдвинулись ли соседние карточки.]

Для hover-эффекта второй вариант обычно точнее: пользователь получил ответ на действие, но структура сетки не дрожит.

**[Слайд 28 — «Transition описывает переход между состояниями»]**

Без `transition` браузер переключает значение сразу. `transition` задаёт, как значения совместимых свойств меняются между состояниями:

```css
.event-card {
  transition:
    box-shadow 180ms ease,
    transform 180ms ease;
}

.event-card:hover,
.event-card:focus-within {
  box-shadow: 0 16px 32px rgba(0, 0, 0, 0.12);
  transform: translateY(-0.25rem);
}
```

Свойство transition находится в базовом состоянии, чтобы переход работал и при входе в hover, и при выходе из него. Мы перечисляем ровно те свойства, которые хотим анимировать, вместо бессодержательного `transition: all`.

**[Слайд 29 — «Мышь — не единственный способ попасть в состояние»]**

`hover` доступен не всем: пользователь может работать с клавиатурой, сенсорным экраном или вспомогательной технологией. Если эффект сообщает об интерактивности карточки, клавиатурный фокус должен получить сопоставимую обратную связь.

В примере использован `:focus-within`: карточка реагирует, когда фокус находится на ссылке или кнопке внутри неё. Для отдельной кнопки чаще подходит `:focus-visible`, потому что фокусное кольцо должно оставаться различимым, а не заменяться тенью.

Motion не заменяет семантику, контраст и видимый фокус. Она только усиливает уже понятное состояние.

**[Слайд 30 — «Проверка: что должно анимироваться?»]**

[Предложить четыре варианта и попросить выбрать безопасные для карточки:]

- `transform: translateY()` — да, краткая обратная связь;
- `box-shadow` — допустимо для небольшого компонента;
- постоянное движение карточки без действия пользователя — нет, если оно не передаёт новую информацию;
- `height: auto` ради визуального эффекта — не использовать как первый выбор: сначала проверить, не нужна ли другая структура или явный размер.

Критерий не в том, можно ли записать CSS. Критерий — сообщает ли движение об изменении состояния и остаётся ли интерфейс устойчивым без него.

## 1:14–1:24. Keyframes и сниженное движение

**[Слайд 31 — «Keyframes описывает несколько состояний эффекта»]**

Transition знает начальное и конечное значение, которые уже существуют в CSS-состояниях. `@keyframes` полезен, когда нужно описать явную последовательность:

```css
@keyframes reveal {
  from {
    opacity: 0;
    transform: translateY(0.5rem);
  }

  to {
    opacity: 1;
    transform: translateY(0);
  }
}

.notice {
  animation: reveal 240ms ease-out both;
}
```

`from` и `to` — два кадра. Ключевое слово `both` сохраняет значения первого и последнего кадра на нужных этапах проигрывания. В этом примере сообщение плавно появляется, но текст доступен в документе независимо от эффекта.

**[Слайд 32 — «Анимация не должна быть единственным носителем смысла»]**

Нельзя передавать важный результат только движением. Если форма сохранилась, нужен текст «Сохранено» или другое доступное подтверждение. Если поле ошибочно, нужны сообщение, связь с полем и понятный цвет/контур; краткая тряска не заменяет ошибку.

Хорошее назначение анимации: мягко показать появление уже понятного уведомления, ответить на нажатие кнопки, показать смену интерактивного состояния. Плохое назначение: заставить пользователя ждать появления содержания или непрерывно отвлекать его движением.

**[Слайд 33 — «Пользователь может попросить меньше движения»]**

ОС и браузер передают предпочтение через media feature:

```css
@media (prefers-reduced-motion: reduce) {
  .event-card {
    transition: none;
  }

  .notice {
    animation: none;
  }
}
```

В reduced-motion режиме мы не скрываем `.notice` и не отключаем кнопку. Исчезает только декоративное изменение. Содержание, фокус, контраст и порядок остаются.

В демонстрационном приложении можно отключать анимации у конкретных компонентов. Не добавляйте глобальный reset с `!important`, пока не понимаете границы приложения и эффекты для сторонних виджетов.

**[Слайд 34 — «Проверка движения: обычный и reduced-motion режимы»]**

[В DevTools включить эмуляцию `prefers-reduced-motion: reduce`. Открыть уведомление и навести курсор на карточку.]

Спросить аудиторию:

- можно ли понять, что карточка интерактивна, без подъёма?
- можно ли прочитать уведомление без entrance-эффекта?
- не исчез ли фокус при клавиатурной навигации?

Если ответ на любой вопрос «нет», анимация взяла на себя чужую ответственность.

## 0:04–0:26. Container queries

**[Слайд 40 — «Viewport не всегда знает ширину компонента»]**

Media query смотрит на viewport. Это правильно для структуры страницы: например, одна или две основные зоны сайта. Но компонент может жить в разных местах той же страницы: в широком `main`, в узком `aside`, в модальном окне или внутри сетки.

Одна и та же ширина окна не гарантирует одну ширину карточки. Если правило относится к карточке, условием должна быть ширина её контейнера.

**[Слайд 41 — «Сначала объявляем контейнер»]**

```css
.event-card {
  container-type: inline-size;
}

.event-card__body {
  display: grid;
  gap: 1rem;
}
```

`container-type: inline-size` разрешает потомкам запрашивать ширину карточки. Название `inline-size` — термин API container queries; в обычном горизонтальном документе здесь измеряется ширина.

Важно: container query применяется к потомкам контейнера. Нельзя использовать условие ширины `.event-card`, чтобы внутри этого же условия менять размер самой `.event-card`: это могло бы создать цикл. Поэтому перестраиваем `.event-card__body` и другие дочерние элементы.

**[Слайд 42 — «Компонент меняется от своей ширины»]**

```css
@container (min-width: 38rem) {
  .event-card__body {
    align-items: center;
    grid-template-columns: 9rem 1fr;
  }
}
```

До `38rem` изображение и текст идут друг за другом. Когда сама карточка становится шире `38rem`, изображение получает фиксированную колонку, а содержание — оставшуюся ширину.

Теперь две копии карточки могут иметь разную раскладку на одном viewport: одна находится в широком основном содержимом, другая — в узкой боковой колонке. Для повторно используемого компонента это точнее, чем viewport breakpoint.

**[Слайд 43 — «Media query и container query не конкурируют»]**

Выбираем условие по владельцу решения:

| Задача                                                      | Механизм                       |
| ----------------------------------------------------------- | ------------------------------ |
| Основные зоны страницы становятся одной или двумя колонками | `@media`                       |
| Карточка меняет внутреннюю композицию в разных родителях    | `@container`                   |
| Независимые карточки сами выбирают число колонок            | Grid с `auto-fit` и `minmax()` |

Container query не исправляет плохую HTML-структуру и не отменяет нормальный поток. Это ещё один способ выразить условие для уже правильно устроенного компонента.

**[Слайд 44 — «Практика: одна карточка в двух контейнерах»]**

[Разместить одинаковую `.event-card` в `main` и `aside`; у `main` и `aside` разная ширина. Попросить включить container query и проверить, что меняется только внутренность широкой карточки.]

Проверка:

- container query измеряет ширину карточки;
- query меняет потомка, а не измеряемый контейнер;
- без query карточка остаётся читаемой;
- правило относится к компоненту, а не случайно копирует viewport breakpoint.

## 0:26–0:39. Системная светлая и тёмная схема

**[Слайд 45 — «Палитра — это роли, а не переключение всех цветов»]**

Тёмная тема не означает «заменить белый на чёрный». Сначала нужны роли палитры:

```css
:root {
  color-scheme: light dark;
  --surface: #fffdf9;
  --surface-raised: #ffffff;
  --text: #1e1d1a;
  --border: #ded7ca;
  --accent: #b93f22;
}
```

`color-scheme: light dark` сообщает браузеру, что страница поддерживает обе схемы. Браузер может согласовать нативные элементы управления, полосы прокрутки и другие системные части со схемой страницы.

Значения должны выражать роль: поверхность, основной текст, граница, accent. Это продолжение custom properties из основной лекции, а не полная дизайн-система.

**[Слайд 46 — «Браузер сообщает предпочтение пользователя»]**

```css
@media (prefers-color-scheme: dark) {
  :root {
    --surface: #1d1b18;
    --surface-raised: #292621;
    --text: #f5efe5;
    --border: #514b42;
    --accent: #ff8b70;
  }
}
```

Это автоматическая реакция на системное предпочтение. Здесь нет кнопки темы, события и сохранения настройки. Ручное переключение появится только после JavaScript.

[Показать в DevTools эмуляцию светлой и тёмной схем. Проверить, что текст, поверхность, граница и фокус остаются различимы.]

Не считать тёмную тему проверенной только потому, что она выглядит эффектно. Минимальная проверка — контраст текста, заметность фокуса, различимость границы и состояние отключённой кнопки. Forced colors и полный доступностный аудит относятся к лекции 16.

## 0:39–0:49. Динамическая высота viewport и safe area

**[Слайд 47 — «На мобильном 100vh не всегда означает видимую высоту»]**

Мобильный браузер меняет доступную высоту, когда показывает и прячет адресную строку. Для блока, который должен быть не ниже видимой области, безопаснее задать минимум, а не фиксированную высоту:

```css
.hero {
  min-height: 100vh;
  min-height: 100dvh;
}
```

Первая строка — fallback для старых браузеров. Вторая использует dynamic viewport height: `dvh` следует за текущей видимой областью. Если браузер не знает `dvh`, он проигнорирует вторую декларацию и оставит `100vh`.

Не используем `height: 100dvh` для области с потенциально длинным содержимым. Фиксированная высота может создать обрезание или внутреннюю прокрутку. `min-height` даёт герою занять доступный viewport, но разрешает вырасти.

**[Слайд 48 — «Safe area — дополнительный отступ, не замена базового»]**

На устройствах с вырезом или индикатором жестов элементы у края могут попасть в небезопасную область:

```css
.mobile-actions {
  padding-bottom: calc(1rem + env(safe-area-inset-bottom, 0px));
}
```

Базовый отступ — `1rem`. Значение `env(safe-area-inset-bottom, 0px)` добавляет системный inset, если он есть; в остальных случаях используется ноль.

[В responsive-режиме DevTools выбрать устройство с safe area или разобрать значение схематично.]

Safe area нужен для закреплённой нижней панели, плавающей кнопки или полноэкранной панели действий. Он не нужен для каждого обычного абзаца на странице.

## 0:49–1:00. `@property`

**[Слайд 49 — «Не всякая custom property имеет известный браузеру тип»]**

Обычная custom property хранит последовательность токенов. Браузер может использовать её через `var()`, но не всегда понимает, как интерполировать значение при transition. `@property` регистрирует синтаксис, наследование и начальное значение:

```css
@property --card-accent {
  syntax: "<color>";
  inherits: true;
  initial-value: #ee5a36;
}
```

После регистрации браузер знает, что `--card-accent` — цвет. Это позволяет предсказуемо анимировать изменение значения там, где поддержка API доступна.

**[Слайд 50 — «Типизированная переменная: дополнительный эффект, не основа интерфейса»]**

```css
.event-card {
  --card-accent: #ee5a36;
  border-left: 0.3rem solid var(--card-accent);
  transition: --card-accent 180ms ease;
}

.event-card:hover {
  --card-accent: #16827a;
}
```

Если `@property` поддерживается, переход между цветами интерполируется. Без регистрации или в браузере без поддержки значение просто изменится без плавного перехода; граница останется видимой и интерфейс продолжит работать.

Именно поэтому `@property` — факультатив: это улучшение motion, а не зависимость, без которой пользователь теряет функцию. Не строим обязательную навигацию, подтверждение ошибки или смысловое состояние на одной только анимации custom property.

**[Слайд 51 — «Итог факультатива: условие должно принадлежать правильному уровню»]**

- Ширина страницы меняет крупную композицию — `@media`.
- Ширина компонента меняет его внутреннюю композицию — `@container`.
