> **Продолжительность основного занятия:** 90 минут.
>
> **Формат:** объяснение и короткие демонстрации преподавателя, без самостоятельных практик и Quiz-заданий.
>
> **Цель:** научить выбирать CSS-механизм по изменившемуся условию. Студент должен отличать ограничение содержимого от смены композиции, выбирать между `@media` и `@container`, использовать responsive images, именовать повторяющиеся решения пользовательскими свойствами CSS и добавлять движение без потери доступности.
>
> Текст рассчитан на произнесение. Пометки **[Слайд …]** обозначают переключение слайда; пометки в квадратных скобках — действия преподавателя. Демонстрации включены в тайминг.

## Границы темы

Лекция продолжает лекцию 3. Там были выбраны базовые модели раскладки: нормальный поток, Flexbox, Grid и позиционирование. Здесь эти механизмы не заменяются новыми. Мы рассматриваем условия, при которых уже выбранная раскладка, значение или визуальное состояние должны измениться.

В основную часть входят:

- viewport и подход «сначала узкая версия»;
- медиазапросы по ширине, высоте и возможностям ввода;
- адаптивность без запросов: ограничения медиа, Grid, `minmax()`, `clamp()` и перенос содержимого;
- responsive images через `srcset`, `sizes` и `<picture>`;
- краткая модель container queries;
- пользовательские свойства CSS, наследование, область действия и fallback;
- `transform`, `transition`, временные функции, `@keyframes` и `animation`;
- `prefers-reduced-motion` как обязательная часть разговора о движении.

Сознательно не разбираем в основных 90 минутах:

- архитектуру файлов, методологии именования, слои каскада, Sass, PostCSS и utility-first — это лекция 5;
- управление медиазапросами из JavaScript, `transitionend` и `animationend` — это последующие лекции JavaScript;
- системную цветовую схему, `dvh`, safe area, `@property` и подробную стратегию `@supports` — эти темы оставлены в приложении;
- профилирование layout, paint и compositing — это отдельная тема производительности.

## 0:00–0:08. От раскладки к условиям

### Слайд 1 — «Современный CSS»

На прошлой лекции мы собирали страницу из отношений между элементами. Нормальный поток задавал естественный порядок документа. Flexbox строил отношения на одной оси. Grid задавал строки и колонки. Позиционирование позволяло визуально наложить независимый элемент.

Сегодня исходная страница уже существует. Это демонстрационный сайт «Митап по фронтенду»: программа, карточки событий, область регистрации, кнопки и изображения. Но страница никогда не существует только в одном снимке экрана. Меняется ширина окна, размер текста, длина содержания, способ ввода и предпочтения пользователя.

Поэтому тема лекции — не каталог новых CSS-свойств. Мы будем выбирать правило по наблюдаемому условию. Для каждого решения задаём два вопроса:

1. что именно изменилось;
2. какое отношение, значение или состояние должно измениться в ответ.

Такой порядок защищает от CSS, состоящего из случайных breakpoint и исправлений отдельных снимков экрана.

### Слайд 2 — «Раскладка задаёт отношения. CSS задаёт условия, при которых они меняются»

В лекции 3 мы выражали отношения: «кнопки образуют группу», «карточки образуют сетку», «бейдж находится в углу карточки». В этой лекции появляется дополнительный вопрос:

> При каком условии выбранное отношение перестаёт выполнять задачу?

Расписание и регистрация могут находиться рядом, пока у каждой зоны остаётся полезная ширина. Когда обе зоны становятся слишком узкими, они переходят одна под другую. Это не означает, что Grid был выбран неправильно. Grid остаётся механизмом раскладки; меняется схема его колонок.

Важно не смешивать уровень механизма и уровень условия. `display: grid` отвечает на вопрос «как связаны элементы». `@media` отвечает на вопрос «когда использовать другую схему». Позже `@container` даст аналогичный ответ для внутренности компонента.

### Слайд 3 — «Четыре источника изменений интерфейса»

Удобно разделить причины изменений на четыре группы.

**Пространство.** Компонент получает больше или меньше места. Причиной может быть viewport, родительский контейнер или соседняя область страницы.

**Содержание.** Заголовок стал длиннее, пользователь увеличил текст, в ссылке появился длинный токен, браузеру нужно выбрать другой файл изображения. Это не всегда требует breakpoint: часто достаточно правильного ограничения содержимого.

**Состояние.** Элемент получил hover, focus, открылся или закрылся. Значение уже изменилось в CSS; `transition` может интерполировать это изменение, а `animation` — описать собственную последовательность.

**Предпочтение пользователя.** Пользователь может попросить уменьшить движение. CSS должен сохранить содержание, действие и видимый фокус без декоративного эффекта.

Пользовательские свойства CSS не являются пятым источником изменения. Они дают имя повторяющемуся решению и позволяют менять связанную роль в подходящей области каскада.

### Слайд 4 — «Одна страница, разные условия»

[Открыть `ResponsiveLayoutDemo`. Последовательно включить широкий режим, узкий режим и крупный текст.]

В широком режиме программа и регистрация помещаются рядом. В узком режиме та же композиция начинает сжимать содержимое. При крупном тексте проблема может появиться раньше, хотя внешняя ширина формально не изменилась.

Формулируем проблему без названия CSS-свойства:

- колонка стала слишком узкой для связанного содержания;
- кнопки перестали помещаться в одну строку;
- длинная строка расширяет потомка;
- изображению нужен предсказуемый кадр;
- крупный текст изменил полезную ширину компонента.

Фраза «нужен breakpoint для планшета» ничего не сообщает о причине. Мы ещё не знаем, нужен ли breakpoint вообще. Сначала фиксируем наблюдаемую поломку, затем выбираем самый простой механизм, который сохраняет смысл.

## 0:08–0:20. Содержание, компоненты и viewport

### Слайд 5 — «Не устройства ломаются — ломаются компоненты»

Устройства не образуют стабильный список. Один телефон может показывать страницу в широком окне, ноутбук — в узкой панели, а пользователь может увеличить масштаб до двухсот процентов. Одна и та же страница может быть встроена в iframe или открыта рядом с инструментами разработчика.

Поэтому название устройства не является надёжной причиной правила. Наблюдаем сам компонент. Если у карточки больше не хватает места для заголовка и действия, это причина пересмотреть её композицию. Если расписание и регистрация теряют читаемость рядом, меняется схема страницы.

Breakpoint — не марка устройства и не число из готового шаблона. Это граница, на которой конкретная композиция перестаёт выполнять задачу. В другом компоненте при той же ширине ничего может не измениться.

### Слайд 6 — «Базовая версия читаема уже в одну колонку»

Начинаем с безопасной версии для малого доступного пространства:

```css
.schedule {
  display: grid;
  gap: 1rem;
}
```

Без `grid-template-columns` явная сетка получает одну колонку. Сначала читается программа, затем область регистрации. Каждая зона занимает доступную ширину. Эта версия не зависит от догадки о модели устройства и не требует условия.

Важно не называть её урезанной мобильной версией. Это содержательная базовая версия документа. Когда появится достаточное место, мы добавим возможность расположить зоны рядом. Если расширенное правило не поддерживается или не сработало, пользователь всё равно получает полный документ.

Такой подход называют mobile first, но инженерный смысл шире названия: сначала рабочая композиция с минимальными требованиями к пространству, затем улучшение при появлении возможности.

### Слайд 7 — «Узкая версия проверяет структуру документа»

Одна колонка показывает, в каком порядке документ читается без декоративной композиции. Название события должно находиться рядом с его описанием. Действие регистрации должно следовать после контекста, к которому относится. Порядок клавиатурного фокуса должен оставаться предсказуемым.

CSS может изменить число колонок, направление группы действий, отступы и декор. Но CSS не должен маскировать бессмысленную HTML-структуру. Если документ становится непонятным при отключённой сложной раскладке, проблема находится не в медиазапросе.

Смена визуального порядка через `order` или произвольные grid areas также требует осторожности: визуальный порядок может разойтись с порядком чтения и фокуса. В этой лекции сохраняем документный порядок и меняем только композицию вокруг него.

### Слайд 8 — «Viewport задаёт область, относительно которой строится страница»

В HTML страницы нужен viewport meta:

```html
<meta name="viewport" content="width=device-width" />
```

Viewport — область, относительно которой браузер вычисляет размеры страницы и медиазапросы. Мобильный браузер без такого указания может использовать широкий виртуальный viewport, а затем уменьшить готовую страницу до размера экрана. В результате текст выглядит мелким, а медиазапросы срабатывают не при той доступной ширине, которую видит автор.

`width=device-width` связывает ширину layout viewport с шириной устройства в CSS-пикселях. CSS-пиксель не обязан совпадать с физическим пикселем экрана: браузер учитывает плотность и масштабирование.

Часто встречается запись `initial-scale=1`. Ключевая часть для нашей модели — `width=device-width`. Нельзя запрещать масштабирование через `user-scalable=no` или слишком жёсткий `maximum-scale`: увеличение страницы остаётся важной пользовательской возможностью.

### Слайд 9 — «Пять проверок — от геометрии к условию»

Перед добавлением запроса идём от простого механизма к более явному условию.

1. **Нормальный поток.** Одна колонка уже сохраняет смысл?
2. **Содержимое.** Потомок может сжаться? Длинный токен может перенестись? Изображение ограничено контейнером?
3. **Flexbox или Grid.** Раскладка уже умеет переносить группу или автоматически выбирать число колонок?
4. **Гибкое значение.** Достаточно `max-width`, `minmax()` или `clamp()`?
5. **Запрос.** Действительно меняется композиция страницы или компонента?

Это не абсолютный рейтинг производительности. Это диагностическая последовательность: сначала проверяем, выражена ли исходная геометрия, и только затем добавляем условное правило.

Если длинная ссылка расширяет колонку, breakpoint обычно лечит симптом. Правильнее разрешить потомку сжаться и токену перенестись. Запрос нужен, когда меняется само отношение: одна или две смысловые зоны, колонка или строка, компактная или расширенная внутренняя композиция.

## 0:20–0:35. Медиазапросы

### Слайд 10 — «Условие добавляет правило к базовой раскладке»

Медиазапрос не создаёт отдельную страницу. Базовый CSS продолжает действовать:

```css
.schedule {
  display: grid;
  gap: 1rem;
}

@media (min-width: 48rem) {
  .schedule {
    grid-template-columns: repeat(2, 1fr);
  }
}
```

До `48rem` сетка остаётся одноколоночной. Начиная с указанной ширины, появляется дополнительная декларация `grid-template-columns`. `display: grid` и `gap` не повторяются, потому что они уже действуют.

`48rem` не является универсальной шириной планшета. В этом примере именно на этой границе программа и регистрация могут находиться рядом, не теряя читаемости. В другом проекте и другом компоненте число будет другим.

Читаем код как условное продолжение базовой истории: «расположить зоны последовательно; если места достаточно — дать им две колонки».

### Слайд 11 — «Базовая версия работает; условие добавляет возможность»

Та же модель применяется к группе действий:

```css
.actions {
  display: flex;
  flex-direction: column;
  gap: 0.75rem;
}

@media (min-width: 36rem) {
  .actions {
    flex-direction: row;
  }
}
```

В базовой версии каждая кнопка получает собственную строку. Это устойчиво при узкой ширине и длинных подписях. При достаточном месте меняется конкретное отношение внутри группы: главная ось становится горизонтальной.

Цепочка запросов под отдельные модели телефонов часто превращается в набор исключений. Числа `375px`, `414px` и `768px` не объясняют, что произошло с содержимым. Здесь правило связано с наблюдаемой возможностью: подписи кнопок помещаются в строку без сжатия и переноса.

### Слайд 12 — «Точка смены раскладки»

Точка смены раскладки — ширина, на которой текущая композиция перестала выполнять задачу. Это определение важнее конкретного синтаксиса.

`rem` часто удобен для условий, связанных с текстом. Если пользователь увеличил корневой размер шрифта, значение в `rem` занимает больше CSS-пикселей, и условие для расширенной композиции срабатывает позже. Интерфейс раньше возвращается к безопасной одной колонке.

Это не делает `px` неправильной единицей. CSS-пиксель остаётся абстрактной единицей браузера и подходит, когда требование действительно выражается конкретным размером. Например, граница в `1px` — нормальное решение. Выбираем единицу по зависимости, которую хотим выразить, а не по запрету из памятки.

Главное: число breakpoint не переносится автоматически в другой компонент. У каждого отношения есть собственная граница полезности.

### Слайд 13 — «Медиавыражение может проверять не только нижнюю границу»

Медиазапросы не ограничены `min-width`. Современный range syntax позволяет записать диапазон в математическом порядке:

```css
@media (30rem <= width <= 60rem) {
  /* правило для диапазона */
}
```

Эквивалентная классическая запись использует `min-width` и `max-width`. Range syntax не меняет модель, а делает диапазон короче и ближе к формулировке условия.

Высота viewport тоже может быть существенной:

```css
@media (height < 30rem) {
  .site-header {
    position: static;
  }
}
```

Широкий, но низкий viewport встречается при горизонтальной ориентации, разделённом окне или открытой экранной клавиатуре. Закреплённая шапка может занимать слишком большую часть видимой области. Тогда условие связано с высотой, а не с названием устройства.

Не нужно создавать отдельный слайд и правило для каждой медиавозможности. Важно увидеть общую модель: запрос проверяет характеристику среды, которая действительно влияет на решение.

### Слайд 14 — «Медиазапросы описывают не только ширину»

Кратко рассмотрим четыре характеристики.

`orientation` сравнивает ширину и высоту viewport. Это не датчик поворота устройства и не гарантия конкретной модели экрана.

`hover` сообщает, может ли основной механизм ввода устойчиво наводить указатель. Сенсорный экран обычно не даёт такого состояния.

`pointer` описывает точность основного указателя. Значение `coarse` означает, что маленькие цели и тесные расстояния особенно проблемны.

`print` выбирает печатную среду. В ней могут быть не нужны интерактивные элементы, но содержание документа должно сохраниться.

Capability queries отвечают на возможность, а не на бренд устройства. Один компьютер может иметь мышь и сенсорный экран одновременно. Поэтому нельзя строить два полностью отдельных интерфейса «для touch» и «для desktop» только по предположению о железе.

### Слайд 15 — «Меняется представление, не документ»

[Вернуться к `ResponsiveLayoutDemo`. Показать только широкое и узкое состояния.]

При смене ширины сохраняются:

- один HTML-документ;
- семантика разделов;
- порядок чтения;
- базовый `display: grid`;
- содержание и действия.

Меняется только декларация, которая описывает количество колонок при достаточном пространстве. Это важный критерий хорошей адаптивности: условие не размножает страницу и не создаёт отдельную ветку содержания.

Если при каждом breakpoint приходится переставлять большой набор независимых элементов и скрывать половину документа, сначала следует проверить структуру. Возможно, исходные зоны слишком тесно связаны или HTML не отражает смысловой порядок.

### Слайд 16 — «Не скрываем основное содержание ради места»

Плохое условное решение:

```css
@media (max-width: 40rem) {
  .schedule {
    display: none;
  }
}
```

Если расписание нужно для задачи пользователя, ширина viewport не делает его ненужным. Можно сменить число колонок, плотность отступов, размер второстепенного декора или расположение действий. Нельзя молча убрать смысловую область только потому, что она не помещается в исходной композиции.

Скрыть допустимо повторяющуюся декоративную иллюстрацию, необязательный фон или подпись, полностью продублированную доступным именем. Но решение принимается по назначению элемента, а не по одному измерению экрана.

## 0:35–0:50. Адаптивность без медиазапросов

### Слайд 17 — «Сначала выразить ограничение напрямую»

Не всякая адаптивная задача требует запроса. Часто браузер уже умеет выбрать устойчивую геометрию, если автор задаёт правильные границы.

Изображение может быть ограничено контейнером. Grid может самостоятельно определить число колонок. `clamp()` может выразить минимальное, предпочтительное и максимальное значения. Потомку можно разрешить сжиматься, а длинной строке — переноситься.

Преимущество таких решений: они реагируют на реальное доступное пространство без списка состояний. Запрос остаётся для ситуации, в которой меняется композиция или поведение, а не только числовой размер.

### Слайд 18 — «CSS управляет рамкой, но не выбирает загружаемый файл»
[Сопоставить исходный кадр `4:3` и рамку `16:9`: `cover` заполняет рамку ценой обрезания краёв.]

```css
.event-card img {
  display: block;
  width: 100%;
  max-width: 100%;
  aspect-ratio: 16 / 9;
  object-fit: cover;
}
```

`width: 100%` связывает визуальную ширину изображения с карточкой. `max-width: 100%` не позволяет выйти за её границу. `aspect-ratio` резервирует рамку до завершения загрузки и уменьшает неожиданный сдвиг содержимого.

`object-fit: cover` заполняет рамку и при необходимости обрезает края. Это допустимо для декоративного фото, у которого край не несёт обязательной информации. Для схемы, текста на изображении или содержательного скриншота обрезание может уничтожить смысл.

Эти правила управляют отрисованной геометрией. Они не сообщают браузеру, какой файл загрузить. Если исходное фото имеет ширину несколько тысяч пикселей, `width: 100%` визуально уменьшит его, но сетевой ресурс уже будет загружен. Для выбора ресурса нужен HTML.

### Слайд 19 — «Размер слота и размер загружаемого ресурса — разные задачи»

```html
<img
  src="speaker-800.jpg"
  srcset="speaker-480.jpg 480w,
          speaker-800.jpg 800w,
          speaker-1280.jpg 1280w"
  sizes="(min-width: 48rem) 33vw, 100vw"
  alt="Докладчик выступает на сцене"
/>
```

`srcset` перечисляет варианты одного изображения и сообщает браузеру их intrinsic width через дескрипторы `480w`, `800w`, `1280w`.

`sizes` описывает ожидаемую ширину слота до того, как CSS полностью рассчитан. В широком представлении карточка занимает примерно треть viewport, в узком — всю ширину. Браузер сопоставляет слот с доступными файлами, учитывает плотность экрана и выбирает подходящий ресурс.

Автор не приказывает выбрать конкретный файл. Он предоставляет корректные данные для выбора. Это позволяет не загружать чрезмерно большой ресурс в маленький слот и не отдавать слишком маленькое изображение там, где нужна детализация.

Атрибут `src` остаётся обычным источником и fallback. `alt` описывает назначение изображения независимо от выбранного файла.

### Слайд 20 — «picture выбирает другой кадр для другой композиции»

Иногда недостаточно загрузить меньшую копию того же кадра. Широкая фотография докладчика может хорошо работать в баннере, но на узкой карточке лицо окажется слишком мелким. Тогда нужна art direction:

```html
<picture>
  <source media="(width < 40rem)" srcset="speaker-close.jpg" />
  <img src="speaker-wide.jpg" alt="Докладчик выступает на сцене" />
</picture>
```

`<source>` предлагает альтернативный ресурс при выполненном условии. Вложенный `<img>` остаётся обязательным: он задаёт fallback, собственные размеры и альтернативный текст.

Разделяем две задачи. `srcset` и `sizes` обычно помогают выбрать подходящий размер одного содержания. `<picture>` позволяет выбрать другой кадр или формат. CSS по-прежнему отвечает за размер слота и композицию, HTML — за доступные ресурсы.

### Слайд 21 — «Независимые карточки сами выбирают число колонок»
[Проследить три ширины на схеме: `auto-fit` без медиазапроса даёт одну, две и три колонки.]

```css
.cards {
  display: grid;
  gap: 1rem;
  grid-template-columns: repeat(auto-fit, minmax(16rem, 1fr));
}
```

`minmax(16rem, 1fr)` задаёт диапазон одной колонки. Карточка не должна становиться уже полезного минимума, но может занять долю свободного пространства. `auto-fit` создаёт столько таких колонок, сколько помещается в контейнер.

Здесь не нужен запрос на две, три и четыре колонки. Сетка выбирает количество по собственному доступному пространству. Это хорошо работает для независимых карточек одинакового уровня.

Если же две колонки имеют разные смысловые роли — например, основное расписание и боковая регистрация — автоматического числа колонок недостаточно. Тогда `@media` может явно сменить крупную композицию страницы.

### Слайд 22 — «clamp() задаёт допустимый диапазон, а не breakpoint»
[Провести по шкале от `2rem` через гибкую область `5vw` к максимуму `4rem`; крайние зоны больше не изменяют размер.]

```css
.page-title {
  font-size: clamp(2rem, 5vw, 4rem);
}
```

Первый аргумент — нижняя граница. Второй — предпочтительное гибкое значение. Третий — верхняя граница. Браузер выбирает предпочтительное значение, но не выходит за диапазон.

`clamp()` полезен, когда свойство может плавно изменяться: размер крупного заголовка, расстояние между секциями, ширина декоративной области. Он не заменяет медиазапрос, если меняется отношение между элементами. Нельзя плавным размером выразить переход от одной смысловой зоны к двум или колонку действий к строке.

Для основного текста следует избегать зависимости только от `vw`: текст не должен становиться слишком маленьким и должен уважать пользовательские настройки. Диапазон и единицы выбираются по реальной задаче чтения.

### Слайд 23 — «Переполнение потомка не всегда требует нового условия»
[Сравнить две карточки: без ограничения длинный URL расширяет Grid, после `min-inline-size: 0` и `overflow-wrap: anywhere` карточка сжимается, а токен переносится.]

Grid и Flexbox могут визуально выглядеть широкими, хотя доступного места достаточно. Частая причина — минимальный intrinsic size потомка. Он не хочет сжиматься меньше длинного содержимого.

```css
.event-card__body {
  min-inline-size: 0;
}
```

Это разрешает потомку сжиматься по inline-оси внутри Grid или Flexbox.

Если проблема создаётся длинным URL, идентификатором или другим токеном без удобных точек переноса:

```css
.event-card a {
  overflow-wrap: anywhere;
}
```

Оба правила выражают ограничения содержания. Они не создают новый дизайн. Добавлять breakpoint для каждого длинного токена опасно: при другом тексте поломка вернётся на другой ширине.

### Слайд 24 — «Сначала геометрия, затем условие»

Соберём диагностическую лестницу.

1. Нормальный поток сохраняет смысловой порядок.
2. Медиа, потомки и длинные строки имеют корректные ограничения.
3. Flexbox или Grid выражают базовые отношения.
4. `max-width`, `minmax()` и `clamp()` задают допустимый диапазон.
5. Только реальная смена композиции получает `@media` или `@container`.

Это не означает, что запросы нежелательны. Они нужны, когда условие действительно дискретно меняет решение. Лестница нужна, чтобы не использовать запрос как универсальный пластырь для ошибок содержимого и исходной геометрии.

## 0:50–0:56. Условие страницы и условие компонента

### Слайд 25 — «Viewport не всегда знает ширину компонента»
[Сравнить одну карточку в широком `main` и узком `aside`: viewport общий, но внутренняя композиция определяется шириной контейнера.]

Медиазапрос видит характеристики страницы и среды. Это правильный владелец решения, когда основные зоны страницы становятся одной или двумя колонками.

Но переиспользуемая карточка может одновременно находиться в широком `main` и узком `aside`. Ширина viewport для обеих копий одинакова, а доступное пространство компонента различается. Медиазапрос не может выразить эту локальную разницу без знания конкретного места использования.

Если условие относится к внутренней композиции карточки, измерять следует её контейнер. Это и есть задача container queries.

### Слайд 26 — «Медиазапрос и запрос к контейнеру не конкурируют»

```css
.event-card {
  container-type: inline-size;
}

@container (min-width: 38rem) {
  .event-card__body {
    align-items: center;
    grid-template-columns: 9rem 1fr;
  }
}
```

`container-type: inline-size` делает элемент контейнером для запросов по inline-размеру. В обычном горизонтальном документе это ширина.

До `38rem` внутренность карточки остаётся одной колонкой. После границы изображение и текст получают две колонки. Изменяется потомок `.event-card__body`, а не собственный размер измеряемой `.event-card`: это избегает циклического расчёта.

Выбираем владельца условия:

- крупная композиция страницы — `@media`;
- внутренняя композиция переиспользуемого компонента — `@container`;
- независимое число одинаковых колонок — Grid с `auto-fit` и `minmax()`;
- уже читаемая базовая версия — без запроса.

Подробные именованные контейнеры и стратегии progressive enhancement остаются за пределами основной лекции. Здесь нужна сама граница ответственности.

## 0:56–1:06. Пользовательские свойства CSS

### Слайд 27 — «Повторяющееся решение заслуживает имени»

До этого блока мы выбирали геометрию и условия. Теперь посмотрим на значения, которые повторяются внутри решений.

Если четыре карточки используют один внутренний отступ, это не четыре независимых числа. Это одна роль: внутренний отступ карточки. Если акцентный цвет используется бейджем, границей и состоянием фокуса, это связанное решение.

Пользовательское свойство CSS позволяет дать роли имя и разместить её в той области каскада, где она имеет смысл. Оно не требует отдельного препроцессора и участвует в обычном вычислении CSS.

### Слайд 28 — «Повторяющиеся значения становятся именованными ролями»

```css
:root {
  --space-2: 0.5rem;
  --space-4: 1rem;
  --surface: #ffffff;
  --border: #e7e1d6;
  --accent: #ee5a36;
}
```

Значение читается через `var()`:

```css
.event-card {
  background: var(--surface);
  border: 1px solid var(--border);
  padding: var(--space-4);
}
```

Имена описывают роль, а не случайный вид значения. `--surface` сообщает назначение лучше, чем `--white`. `--accent` допускает изменение темы или варианта компонента без переименования самой роли.

Не нужно превращать каждое число в переменную. Польза появляется, когда значение повторяется, имеет смысловую роль или ожидаемо меняется вместе с другими декларациями. Переменная для единственного случайного отступа добавляет имя, но не добавляет модели.

### Слайд 29 — «Значение карточки доступно её потомкам»
[Проследить два поддерева: `--accent` наследуется потомками `.event-card`, а `.workshop-card` переопределяет значение только локально.]

Пользовательские свойства принадлежат элементам и обычно наследуются:

```css
.event-card {
  --accent: #ee5a36;
}

.event-card__badge {
  background: var(--accent);
}
```

Потомок получает вычисленное значение ближайшего предка. Вариант компонента может локально его переопределить:

```css
.workshop-card {
  --accent: #16827a;
}
```

Теперь бейдж внутри workshop-карточки использует новый акцент, а соседние карточки не меняются.

Это не текстовая замена до запуска браузера и не JavaScript-переменная. Значение вычисляется для каждого элемента с учётом каскада, специфичности и наследования. Поэтому пользовательские свойства хорошо выражают локальные контракты компонентов.

### Слайд 30 — «Имя живёт у ближайшего общего предка потребителей»

Область определения является частью смысла.

- `:root` подходит значениям, которые действительно используются всей страницей.
- `.event-card` подходит роли карточки и её потомков.
- `.button` подходит значению, нужному только кнопке.

Не следует заранее создавать глобальный каталог `--blue-1`, `--blue-2`, `--gap-7`, если роли ещё не понятны. Такой набор хранит исходные значения, но не объясняет, почему они должны изменяться вместе.

В лекции 5 появятся системные правила именования и архитектура CSS. Здесь достаточно локального принципа: определить значение у ближайшего общего предка всех потребителей и назвать его по назначению.

### Слайд 31 — «Fallback не должен скрывать обязательную ошибку»

```css
.event-card {
  padding: var(--card-padding, 1rem);
}
```

`1rem` используется, если `--card-padding` отсутствует или не даёт допустимого значения для этой декларации. Это полезно, когда внешний контракт действительно необязателен: карточка принимает настройку, но имеет безопасное значение по умолчанию.

Если свойство обязательно, fallback способен скрыть опечатку. Автор ожидает `--card-padding`, ошибается в имени, а интерфейс молча использует резерв. В таком контракте лучше определить обязательное значение явно и заметить проблему в инструментах разработчика.

Fallback — не страховка, которую нужно добавлять к каждому `var()`. Это часть семантики контракта: значение может отсутствовать, и указанное поведение при отсутствии корректно.

## 1:06–1:20. Transform и transition

### Слайд 32 — «Визуально сдвинуть — не значит переложить»

Переходим от геометрии к обратной связи. Движение может подчеркнуть изменение состояния, но не должно незаметно брать на себя ответственность основной раскладки.

`transform` меняет визуальное представление элемента. Он не освобождает исходное место в нормальном потоке и не заставляет соседей заново расположиться так, будто элемент физически переместился в раскладке.

Эта граница связывает блок с лекцией 3: Grid, Flexbox, размеры и отступы строят геометрию документа; transform создаёт визуальное преобразование уже расположенной коробки.

### Слайд 33 — «Transform не изменяет место элемента в раскладке»
[Сначала указать пунктирное место карточки в потоке, затем её визуальный сдвиг и неизменившееся положение следующего элемента.]

Сравним два состояния:

```css
.event-card:hover {
  margin-top: -0.75rem;
}
```

Изменение margin участвует в геометрии. Соседние элементы могут сдвинуться, а сетка — визуально дрогнуть.

```css
.event-card:hover {
  transform: translateY(-0.75rem);
}
```

Карточка выглядит поднятой, но её место в раскладке сохраняется. Для краткого эффекта hover это обычно точнее: пользователь получает обратную связь, а соседние карточки не меняют положение.

Transform не является универсально более быстрым или правильным решением. Он просто отвечает на другой вопрос. Если элемент должен реально занять другое место, менять нужно раскладку.

### Слайд 34 — «Transform применяет последовательность функций»

```css
.event-card {
  transform:
    translateX(1rem)
    rotate(3deg)
    scale(1.05);
  transform-origin: center;
}
```

`translate()` перемещает визуальную систему координат элемента. `rotate()` вращает. `scale()` изменяет визуальный масштаб. Эти функции можно объединить в одном значении.

Порядок имеет значение: преобразования применяются последовательно, и последующая функция работает уже в преобразованной системе координат. `translate()` перед `rotate()` может дать другой результат, чем `rotate()` перед `translate()`.

`transform-origin` задаёт точку, относительно которой происходят вращение и масштабирование. Значение по умолчанию обычно находится в центре коробки. Для раскрывающейся панели или стрелки может понадобиться край или угол.

Матрицы, перспектива и 3D-преобразования в эту лекцию не входят. Для базовой обратной связи достаточно понимать координаты, порядок функций и сохранение места в раскладке.

### Слайд 35 — «Transition принадлежит базовому состоянию»

```css
.event-card {
  transition:
    box-shadow 180ms ease,
    transform 180ms ease;
}

.event-card:hover,
.event-card:focus-within {
  box-shadow: 0 1rem 2rem rgb(0 0 0 / 12%);
  transform: translateY(-0.25rem);
}
```

Псевдоклассы меняют вычисленные значения. `transition` сообщает браузеру, как интерполировать совместимые значения между состояниями.

Переход записан в базовом правиле. Поэтому он действует и при входе в hover или focus, и при возвращении в базовое состояние. Если разместить transition только внутри `:hover`, обратный переход после исчезновения hover может стать мгновенным.

Перечисляем свойства явно. `transition: all` заставляет браузер пытаться интерполировать любое изменившееся свойство и скрывает намерение. Здесь автор сознательно выбирает тень и transform.

`:focus-within` позволяет карточке реагировать, когда клавиатурный фокус находится на ссылке или кнопке внутри. Визуальная обратная связь не должна принадлежать только мыши.

### Слайд 36 — «Transition и animation отвечают на разные задачи»

`transition` не слушает событие hover. Он наблюдает изменение вычисленного значения свойства. Hover, focus, атрибут, класс или нативное состояние могут вызвать изменение — transition интерполирует его между двумя состояниями.

`animation` имеет собственную временную последовательность, заданную keyframes. Она может включать больше двух кадров, повторяться и менять направление. Она запускается, когда к элементу применяется соответствующее значение `animation`.

Практическое различие:

- hover и focus меняют уже существующее CSS-состояние — естественен transition;
- появлению уведомления нужен описанный эффект — может подойти animation;
- бизнес-состояние приложения всё равно должно существовать отдельно от анимации;
- animation не превращает CSS в полноценную модель состояния.

### Слайд 37 — «Длительность и кривая отвечают на разные вопросы»

В `transition: transform 180ms ease` значение `180ms` задаёт общую продолжительность, а `ease` — распределение скорости внутри этого времени.

- `linear` сохраняет постоянную скорость. Это уместно для равномерного технического прогресса или циклического индикатора, но не всегда естественно для объекта, который должен мягко остановиться.
- `ease` даёт спокойную базовую кривую с более мягкими краями.
- `ease-in` разгоняется и может подходить элементу, который уходит.
- `ease-out` замедляется к финалу и часто подходит появлению.
- `ease-in-out` связывает два устойчивых состояния.

Сначала выбираем смысл и продолжительность, затем кривую. `cubic-bezier()` нужен при конкретном требовании к характеру движения, а не для случайной уникальности.

### Слайд 38 — «Одинаковые начало и конец, разный темп»

[Нажать «Сначала», около середины — «Пауза». Перетащить шкалу «Позиция» к 20%, 50% и 80%, затем нажать «Продолжить».]

У всех дорожек одинаковы начальное и конечное значения `transform`, а длительность равна `3000ms`. Временная функция отображает долю прошедшего времени в долю выполненного преобразования. Поэтому в один и тот же момент маркеры находятся в разных точках, хотя обычные кривые завершаются одновременно в одном месте.

`linear` движется равномерно. `ease` смягчает начало и конец. `ease-in` медленно начинается и ускоряется, `ease-out` быстро стартует и замедляется, `ease-in-out` смягчает оба края. `steps(5, end)` не интерполирует положение непрерывно: значение меняется пятью скачками в конце интервалов.

У `cubic-bezier(.34, 1.56, .64, 1)` координата контрольной точки по оси прогресса больше единицы. Поэтому маркер временно проходит дальше конечной точки и возвращается. Исходные крайние значения не меняются, но фактическая траектория из-за перелёта становится длиннее — поэтому сравниваем не «пройденное расстояние», а положение при одинаковом времени.

Пауза фиксирует все семь CSS-анимаций в одной временной координате. Шкала меняет их `currentTime`, поэтому позволяет сравнить кривые без попытки поймать нужный кадр на глаз. Кнопка «Сначала» пересоздаёт дорожки и запускает общий цикл заново.

### Слайд 39 — «Hover — возможность устройства, а не обязательный путь»

```css
@media (hover: hover) and (pointer: fine) {
  .event-card:hover {
    transform: translateY(-0.25rem);
  }
}
```

Декоративный подъём включается там, где основной указатель умеет устойчиво наводиться и достаточно точен. Это progressive enhancement, а не отдельный «desktop layout».

Обязательное содержание нельзя показывать только по hover. Сенсорное устройство может не иметь устойчивого наведения, клавиатурный пользователь вообще не использует указатель, а устройство может одновременно поддерживать touch и мышь.

```css
.event-card:focus-within {
  box-shadow: 0 0 0 0.2rem var(--accent);
}
```

Клавиатурный фокус должен оставаться различимым. Для отдельной кнопки обычно используется `:focus-visible`; карточка может дополнительно реагировать через `:focus-within`. Движение усиливает состояние, но не заменяет фокусное кольцо, контраст и доступное имя.

## 1:20–1:27. Animation и reduced motion

### Слайд 40 — «Keyframes описывают временную последовательность»
[Сопоставить код с тремя кадрами схемы: `0%`, `50%` и `100%` показывают независимые промежуточные значения одной временной шкалы.]

```css
@keyframes reveal {
  0% {
    opacity: 0;
    transform: translateY(0.5rem);
  }

  50% {
    opacity: .6;
    transform: translateY(0.2rem);
  }

  100% {
    opacity: 1;
    transform: translateY(0);
  }
}
```

`0%` и `100%` можно записать как `from` и `to`. Кадр `50%` задаёт самостоятельное промежуточное состояние: к середине временной шкалы уведомление уже частично проявилось и приблизилось к конечной позиции.

Keyframes описывают визуальную последовательность. Они не являются состоянием приложения. Уведомление должно уже существовать в документе и иметь понятный текст; animation только дополняет его появление.

Если нужны лишь начальное и конечное значения, уже возникающие из hover или focus, transition обычно проще. Keyframes полезны, когда последовательность принадлежит самому эффекту.

### Слайд 41 — «Одна запись скрывает несколько независимых решений»

```css
animation: reveal 240ms ease-out both;
```

Эта shorthand-запись объединяет несколько параметров:

- `animation-name: reveal` выбирает keyframes;
- `animation-duration: 240ms` задаёт продолжительность;
- `animation-timing-function: ease-out` распределяет скорость;
- `animation-fill-mode: both` применяет подходящие крайние значения до и после активной фазы.

Также существуют `animation-delay`, `animation-iteration-count`, `animation-direction` и `animation-play-state`. Они нужны не в каждом эффекте, но важно понимать, что animation имеет собственный жизненный цикл.

Особенно осторожно используем `infinite`. Бесконечное движение требует функциональной причины и способа остановки, если оно не является необходимым индикатором текущего процесса.

### Слайд 42 — «Анимация не должна быть единственным носителем смысла»

Плохие примеры:

- ошибочное поле только трясётся, но не получает сообщение;
- подтверждение сохранения существует только как зелёная вспышка;
- содержимое невозможно прочитать до завершения декоративного появления;
- карточка постоянно движется без действия пользователя.

Рабочий вариант начинается с доступного состояния. Ошибка связана с полем и описана текстом. Уведомление имеет `role="status"` и понятное сообщение. Фокус виден. Цвет и движение являются дополнительными каналами.

Хорошее назначение animation — помочь заметить уже понятное изменение: появление уведомления, завершение действия, переход между визуальными состояниями. Если отключение эффекта уничтожает функцию или смысл, на animation возложена чужая ответственность.

### Слайд 43 — «Reduced motion отключает эффект, а не интерфейс»

```css
@media (prefers-reduced-motion: reduce) {
  .event-card {
    transition: none;
  }

  .notice {
    animation: none;
  }
}
```

Операционная система передаёт пользовательское предпочтение браузеру, а медиазапрос позволяет адаптировать движение. Мы не скрываем `.notice`, не отключаем кнопку и не удаляем состояние hover или focus. Исчезает только необязательная интерполяция.

После отключения должны сохраниться:

- содержание уведомления;
- доступное действие;
- видимый клавиатурный фокус;
- порядок документа;
- контраст и различимость состояния.

Не следует автоматически добавлять глобальный сброс вида `* { animation: none !important; }`. Он может затронуть сторонние компоненты и функциональное движение, не учитывая контекст. В учебном примере отключаем конкретные эффекты, которые сами добавили.

### Слайд 44 — «От изменившегося условия к CSS-механизму»

Финальная карта начинается не с названия свойства, а с владельца условия.

- Изменилась крупная композиция страницы — `@media`.
- Изменилась доступная ширина переиспользуемого компонента — `@container`.
- Содержимое переполняет коробку — ограничения медиа, `min-inline-size`, `overflow-wrap` и гибкие размеры.
- Независимые карточки должны сами выбирать число колонок — Grid, `auto-fit` и `minmax()`.
- Повторяется смысловое значение — пользовательское свойство в подходящей области каскада.
- Псевдокласс изменил вычисленное значение — transition.
- Нужна собственная временная последовательность — keyframes и animation.
- Пользователь просит меньше движения — `prefers-reduced-motion`, при этом функция остаётся.

Одна страница может использовать все эти механизмы, потому что они отвечают на разные вопросы. Современный CSS здесь — не набор трюков, а способ точно выразить причину изменения.

Сегодня мы выбирали условие и механизм. Мы сознательно оставляли решения локальными и наблюдаемыми: одна страница, один компонент, одна роль, один эффект.

# Приложение. Дополнительные условия современного CSS

> Материал ниже не входит в основные 90 минут и не является обязательным предварительным условием для лекции 5. Это справочное продолжение той же модели «условие → CSS-правило → наблюдаемый результат».

## A1. Дополнительные условия современного CSS

В приложении рассматриваются пять дополнительных случаев:

- системное предпочтение цветовой схемы;
- динамическая высота мобильного viewport;
- безопасная область у физического края экрана;
- типизированное пользовательское свойство через `@property`;
- проверка поддержки возможности через `@supports`.

Они не заменяют базовую раскладку и не требуют нового фреймворка. Сначала остаётся рабочая версия, затем добавляется поддерживаемое улучшение.

## A2. Палитра начинается с ролей, а не с замены цветов

```css
:root {
  color-scheme: light dark;
  --surface: #fffdf9;
  --text: #1e1d1a;
  --border: #ded7ca;
  --accent: #b93f22;
}
```

Тёмная схема не означает механическую замену белого на чёрный. Сначала значения получают роли: поверхность, текст, граница и акцент.

`color-scheme: light dark` сообщает браузеру, что документ поддерживает обе схемы. Браузер может согласовать нативные элементы управления, полосы прокрутки и другие системные части.

## A3. `prefers-color-scheme` меняет значения ролей

```css
@media (prefers-color-scheme: dark) {
  :root {
    --surface: #1d1b18;
    --text: #f5efe5;
    --border: #514b42;
    --accent: #ff8b70;
  }
}
```

Здесь нет кнопки темы, события и сохранения настройки. CSS автоматически реагирует на системное предпочтение. Ручной переключатель потребует состояния приложения и JavaScript.

Проверяем не только эстетическое впечатление, но и контраст текста, видимый фокус, различимость границ и отключённые состояния.

## A4. Длинному содержимому нужен минимум видимой высоты

Мобильный браузер меняет видимую высоту, когда показывает и скрывает панели интерфейса:

```css
.hero {
  min-height: 100vh;
  min-height: 100dvh;
}
```

Первая строка остаётся fallback. Вторая использует текущую динамическую высоту viewport. `min-height` позволяет блоку вырасти при длинном содержимом; фиксированный `height` мог бы создать обрезание или внутреннюю прокрутку.

## A5. Системный отступ дополняет базовый

```css
.mobile-actions {
  padding-bottom: calc(
    1rem + env(safe-area-inset-bottom, 0px)
  );
}
```

`1rem` — обычный отступ интерфейса. `env(safe-area-inset-bottom, 0px)` добавляет системное значение, если оно существует. Механизм нужен закреплённой панели или действию у физического края экрана, а не каждому обычному блоку.

## A6. Регистрация сообщает браузеру тип пользовательского свойства

```css
@property --card-accent {
  syntax: "<color>";
  inherits: true;
  initial-value: #ee5a36;
}
```

Обычное пользовательское свойство хранит последовательность токенов. После регистрации браузер знает, что значение является цветом, как оно наследуется и какое начальное значение использовать. Это позволяет предсказуемо интерполировать изменение цвета.

Без поддержки регистрации интерфейс не должен терять функцию: граница или акцент просто изменятся без дополнительной плавности.

## A7. Сначала рабочая базовая версия, затем `@supports`

`@media` и `@container` проверяют условия среды или пространства. `@supports` проверяет, понимает ли браузер конкретную возможность:

```css
.event-card__body {
  display: grid;
  gap: 1rem;
}

@supports (container-type: inline-size) {
  .event-card {
    container-type: inline-size;
  }
}
```

Progressive enhancement строится в таком порядке:

1. создать функционально достаточную базовую версию;
2. проверить поддержку необязательной возможности;
3. добавить улучшение;
4. не дублировать содержание и не создавать ложный fallback, который невозможно проверить.
