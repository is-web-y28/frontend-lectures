# План лекции 12. Архитектура Vue-приложения и управление состоянием

План реализован в [презентации](../slides/12-vue-architecture.md). Подготовка и контрольные точки описаны в [маршруте преподавателя](12-vue-architecture.md).

В лекции 11 разложили Frontend Meetup на компоненты и выделили логику поиска. Теперь у приложения три страницы, а форма нужна в карточке события и расписании. Сначала рисуем границы страниц и общего действия по FSD. По этой схеме реализуем адрес, время жизни состояния, чтение данных и локализацию. В главе о FSD проверяем границу на переносе формы, а в главе о загрузке — на изменении ответа поставщика.

**Главный вопрос лекции** — кто отвечает за часть сценария и где заканчивается изменение? К ЛР 5 студент сможет обосновать структуру по потребителям, указать публичный вход модуля, назначить владельца состояния и проследить путь от URL или действия до результата на экране.

## Сквозной пример

- Расписание открывается на `/schedule`. Карточка события и список из API получают `eventId` из адреса. В списке переключатель «От двух мест» соответствует `?minSeats=2`.
- В карточке Frontend Meetup начальные локальные заявки — Анна на два места и Борис на одно, как в лекции 11. Форма добавляет, а список позволяет удалять записи в памяти приложения. Общая сводка показывает количество мест по локальным заявкам. Подписи «Локальные заявки» и «Заявки из API» обозначают происхождение данных.
- Для чтения по HTTP используются знакомые JSON-образцы из лекции 10. Для `frontend-meetup` это Анна на одно место, Борис на два и Вера на одно. Для `css-workshop` — пустой массив. Отправка формы обслуживается локальным хранилищем. Задержка и ошибка 503 задаются в демонстрационном источнике.
- Интерфейс переключается между русским и английским. После перезагрузки приложение берёт экран и фильтр из URL, читает список по HTTP и заново инициализирует локальные заявки и язык.
