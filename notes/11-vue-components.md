### Слайд 1. Vue: компоненты и переиспользование логики

В лекции 09 мы связали состояние Frontend Meetup с шаблоном. В 10 научились получать проверенный список, различать ошибки и не принимать устаревший ответ. Теперь вопрос не в том, работает ли форма. Нужно понять, как разделить её и список, не потеряв согласованность данных и управление начатой работой.

Сегодня все примеры запускаю я. Вам не нужно устанавливать пакеты или писать код: перед действием будем прогнозировать результат, после — объяснять причину. Основной маршрут: вступление 3 минуты; главы 1–5 — 15, 12, 30, 10 и 10 минут; общий сценарий и вопросы — 10. Всего 90 минут, приложения после заключения необязательны. Это план репетиции, а не измеренная длительность занятия. Внутри глав уже учтены показы и обсуждения.

### Слайд 2. Форма работает. Почему её трудно перенести?

Это сокращённая карта App.vue из лекции 09, а не новый исполняемый исходник. В одном файле живут черновик формы, коллекция, поиск, итог и обработчики. Чтобы перенести форму на другой экран, приходится выяснять, какие из этих переменных ей действительно нужны. Разделение на файлы само по себе этого ответа не даёт.

Спросим аудиторию: должен ли новый компонент формы получать весь массив заявок? Для редактирования имени и количества массив не нужен. Ей нужно сообщить результат отправки тому, кто хранит коллекцию. Эта потребность приводит к договору компонента, а не к механическому разрезанию шаблона.

### Слайд 3. У данных и начатой работы должен быть владелец

Владелец — не специальный API Vue, а наше решение о том, где создаётся состояние и кто имеет право его менять. Форма может владеть черновиком, а общий родитель — подтверждёнными заявками. Если родитель запустил загрузку для своего экрана, нужно также решить, что происходит при его удалении.

Нам понадобятся две связанные границы: договор обмена данными и срок жизни работы. Компоненты помогут описать первую; хуки, наблюдатели и composable — обслужить вторую. Общая переменная на весь проект пока не требуется.

### Слайд 4. Какие границы сделают интерфейс понятнее?

Начнём со списка: кнопка внутри него должна изменить коллекцию владельца. Затем отделим черновик формы и содержимое общей панели. Когда захотим вернуть фокус после отправки, появится вопрос о DOM и сроке жизни экземпляра. Автоматическая загрузка — побочный эффект (side effect), для которого нужны явная причина запуска и очистка. Только после этого вынесем повторяющиеся связи в функцию.

Этот порядок важен: composable будет собирать уже разобранные механизмы. Мы не начинаем с большой универсальной функции, внутреннюю работу которой пока невозможно объяснить.

## Глава 01. Кто имеет право менять заявки?

Слайды 5–20.

### Слайд 5. Кто имеет право менять заявки?

В одном App обработчик удаления мог напрямую обратиться к массиву. После выноса списка в дочерний компонент такая неявная связь должна стать договором. Сначала передадим данные вниз, затем вернём намерение пользователя вверх.

В конце главы проверим не только исчезновение строки, но и общий итог мест. Именно два согласованных представления покажут, где действительно изменилась исходная коллекция.

### Слайд 6. Граница проходит по обязанности

У каждого компонента должна быть причина измениться. Поле имени и кнопка отправки меняются вместе с правилами формы, поэтому им удобно оставаться внутри RegistrationForm. Список не должен знать, как очищается черновик, а форма — как список фильтруется.

Мы не превращаем каждый div в компонент. Небольшая связная часть может оставаться в родителе. Главное — иметь короткий ответ на вопрос «что этот компонент принимает и о чём сообщает». Итог пока достаточно вычислять в App: отдельный файл для одной строки текста не обязателен.

### Слайд 7. Импорт связывает файл с тегом в шаблоне

Это первый шаг выноса: обычный import из лекции 07 делает компонент доступным в script setup и его шаблоне. RegistrationList — определение компонента, а его тег создаёт экземпляр в дереве интерфейса. На этом шаге список ещё можно оставить статическим: новые props и события пока не нужны.

Расширение .vue обрабатывает уже знакомый Vite-плагин. Импорт не означает, что компонент смонтирован прямо во время выполнения этой строки. Место и условия появления экземпляра задаёт шаблон.

[Порядок разбора по кликам: Импорт определения → создание экземпляра тегом.]

### Слайд 8. Два экземпляра — два локальных состояния

[Нажмите «Начать заново». У A и B по одному месту. Спросите, что случится с B после нажатия «Ещё место» в A.]

Нажмите кнопку A: у A два, у B одно. Здесь два настоящих экземпляра одного компонента. В каждом setup вызывается одна и та же функция создания локального состояния; переменные создаются заново. Пока не разбираем её реализацию: к useSeatCount вернёмся в главе 5.

Одинаковый исходник не означает общие данные. Если вынести ref на уровень ES-модуля, договор будет другим: импортеры получат одну общую ссылку. Пока сохраняем независимость экземпляров.

### Слайд 9. Родитель передаёт данные через props

[Первый кадр — только RegistrationList.vue, подсвечено объявление defineProps. Не переключаться к родителю, пока не прочитан договор.]

Ребёнок объявляет вход rows: массив Registration. DefineProps — макрос script setup, его не импортируют. Значение ещё не создано ребёнком: указано, что должен предоставить использующий его компонент. Первый клик переводит внимание на props.rows в v-for. Именно этот вход читает шаблон. Здесь props написан явно; в шаблоне допустимо и короткое rows.

[Следующий клик меняет показанный файл на LocalMeetup.vue. Подсвечено создание rows. Затем подсветка переходит на использование RegistrationList.]

Теперь мы у родителя: ref создаёт исходную коллекцию здесь. В :rows="rows" слева от равно стоит имя входа ребёнка, справа — выражение родителя. Совпадение имён необязательно: позже справа будет visible, отфильтрованное computed. Двоеточие заставляет вычислить выражение, а не передать текст. Родитель выбирает значение, Vue обновляет вход, ребёнок читает его при отображении. Последний клик показывает весь короткий фрагмент целиком. Это учебная выдержка из дерева, поэтому import ref и initial опущены, а фильтр добавляется позже.

### Слайд 10. Привязанный prop следует за родителем

В первом использовании SeatLabel без двоеточия передаётся строка «2». Во второй выражение 2 даёт число. В третьей вход получает текущее значение seats и обновится при его изменении. Это не отдельная копия, которую Vue однажды положил в ребёнка.

Нужно различать передачу prop и собственный источник состояния. Если ребёнок создаст ref(props.count), он создаст локальное значение с начальным содержимым, а не постоянную связь со входом. Такая копия иногда нужна как черновик, но требует отдельного договора. Сейчас цель — отображать актуальное число родителя.

[Оба блока видны всё время. Подсветка: договор ребёнка → строка → число → живая привязка и кнопка родителя.]

### Слайд 11. Необязательный вход требует явного значения по умолчанию

Новый вопрос: что получит поле, если родитель не передаст count? Вопросительный знак описывает необязательность, но сам не выбирает начальное значение. WithDefaults связывает default 1 с отсутствующим или undefined входом. Null не заменяется этим default; если его допустили извне, это отдельное значение.

По клику сравнить с runtime-объявлением: type Number описывает проверку типа в разработке. Это две альтернативные формы defineProps, их нельзя написать вместе в одном setup. Типовой макрос компилируется в доступные runtime-метаданные; некоторые сложные типы невозможно перенести полностью. Предупреждение о неверном prop не является валидатором API и не исправляет значение. Для массива или объекта в withDefaults нужна фабрика, например rows: () => [], чтобы не разделить изменяемое значение между экземплярами. У списка основной программы rows остаётся обязательным; пример defaults относится к маленькому PropsProbe.

[Две альтернативы остаются рядом, а не выполняются вместе в одном setup. Выделить типовой default, затем соответствующий runtime-договор.]

### Слайд 12. Props не передают право менять источник

Readonly у props защищает присваивание самого входного свойства. Вложенный массив остаётся объектом со своей ссылкой: push может изменить коллекцию родителя. Поэтому формулировка «props вообще невозможно изменить» была бы неверной. Техническая возможность вложенной мутации не делает её хорошим договором списка.

Мы выбираем, чтобы RegistrationList только читал rows. Тогда любое изменение полной коллекции можно найти в операциях её владельца. Это правило структуры приложения; Vue не превращает переданный объект в глубоко замороженный снимок.

[Порядок разбора по кликам: Договор → запрещённая замена входа → возможная вложенная мутация.]

### Слайд 13. Начальная копия prop и живое чтение — разные договоры

Сначала восстановить источник: props.count обновляется от родителя. Затем при выполнении ref(props.count) аргумент уже вычислен и равен числу 1. Новый ref не знает, откуда взяли число; это осознанно отдельное состояние. В computed передаётся функция, и чтение props.count выполняется при вычислении с отслеживанием зависимости.

Спросить, какие из трёх чисел изменятся после обновления родителя. Prop и computed станут 2, initial останется 1. Не надо чинить начальную копию watcher-ом, если задача — только показывать живое значение. В Vue 3.5 деструктурированные имена defineProps внутри того же script setup могут реактивно переписываться компилятором; это особое преобразование не делает произвольное число реактивной ссылкой. Для объяснения передачи в другие функции здесь оставляем явное props и getter. Следующий стенд проверит именно эти три разных связи.

### Слайд 14. Изменим родителя и сравним три значения у ребёнка

[Начать заново. Родитель count=1, у ребёнка три единицы.]

Спросить, что произойдёт с initial, затем нажать «Увеличить у родителя». Prop и computed станут 2, ref(props.count) останется 1. Нажать ещё раз: 3, 1, 3. Это реальные withDefaults, ref и computed из показанного PropsProbe.vue.

Выключить «Передавать count»: родитель сохраняет 3, но вход становится undefined и применяется default 1. Начальная копия тоже 1, однако уже по другой причине — её не меняли. Вернуть передачу, дождаться 3, затем нажать «Новый экземпляр»: все три значения станут 3, потому что setup выполнен заново. Key используем пока как контроль пересоздания; механизм идентичности отдельно разберём после v-if/v-show. Время этого показа входит в главу, самостоятельного запуска нет.

### Слайд 15. Событие сообщает о намерении пользователя

DefineEmits описывает исходящие сообщения компонента и возвращает функцию emit. Событие remove несёт число id — устойчивую идентичность записи. Позиция в отфильтрованном списке не подходит: Борис может стать первой видимой строкой, сохранив прежний id.

Клик — DOM-событие кнопки, а remove — уже сообщение компонента. Emit не удаляет ничего автоматически. Он вызывает подключённый родителем listener; если listener отсутствует, коллекция останется прежней. В следующем фрагменте покажем эту вторую половину договора.

[Договор и место вызова emit видны одновременно. Сначала выделить remove с payload, затем строку @click; row получен из v-for.]

### Слайд 16. Обработчик владельца изменяет коллекцию

[После исходящего remove на предыдущем слайде открыть родителя. Начальная подсветка — @remove="remove".]

Слева имя события ребёнка, справа обработчик LocalMeetup. Первый аргумент, отправленный через emit, становится id в remove. Следующий клик показывает место записи: filter строит новый полный массив без этого id. Список передал намерение; коллекцию меняет её владелец. В настоящем LocalMeetup коллекция тоже называется rows, а наружу передаётся visible.

[Перевести подсветку на вычисления: сначала visible, затем seats.]

Оба computed читают изменившийся источник. Фильтр по поиску ограничивает только visible, поэтому удаление — это не просто исчезновение DOM-строки. Если убрать обработчик владельца, сообщение не приведёт к изменению ни списка, ни итога. В полном приложении remove ещё возвращает фокус после nextTick; этот шаг добавим после объяснения DOM.

[Все части остаются видимыми. Listener → id и операция над полной коллекцией → visible → seats. Слева template и setup имеют отдельные языковые блоки.]

### Слайд 17. События компонентов соединяют явно

Если кнопку выделили ещё и в RegistrationRow, её emit увидит непосредственный родитель RegistrationList. App не начнёт автоматически слушать всех потомков. События компонентов не всплывают по дереву подобно нативному click по DOM.

В списке нужно явно принять remove строки и переслать id дальше. Такой промежуточный договор оправдан, если у строки есть самостоятельная роль. Если цепочка становится длинной и все только пересылают данные, это повод пересмотреть границу; способы общего состояния оставляем следующей лекции.

[Порядок разбора по кликам: Данные строки и ключ → явная пересылка remove следующему родителю.]

### Слайд 18. Два представления читают один источник

Visible и seats отвечают на разные вопросы к одной коллекции. Visible зависит ещё и от поиска, а seats считает все заявки независимо от фильтра. Поэтому после поиска Бориса на экране одна строка, но итог всё ещё включает Анну.

Не создаём второй изменяемый ref для количества мест и watcher, который вручную его поддерживает. Это производное значение, для него подходит computed из лекции 09. Подъём коллекции к родителю нужен двум читателям и общей операции изменения, а не потому, что любое состояние должно жить наверху.

[Порядок разбора по кликам: Источник → выборка → итог по полному массиву.]

### Слайд 19. Почему событие ещё не удаляет заявку?

[Сбросить. Флажок «Подключить обработчик владельца» выключен. Открыть журнал. Попросить прогноз и нажать «Удалить заявку: Борис».]

Журнал показывает emit remove(2), но список и итог прежние: две заявки и три места. В учебном стенде listener фиксирует сообщение, а выполнение операции владельца управляется флажком — это диагностическая развилка, не особенность emit.

Включить флажок и повторить удаление Бориса. Теперь одна заявка и два места. Следом указать исходник на предыдущем слайде: изменение делает filter внутри операции App. Этот показ и короткое обсуждение занимают три минуты; студентам не нужно запускать проект.

### Слайд 20. Состояние поднимают к тому, кто согласует изменения

Мы вынесли список, не передав ему право скрытно менять коллекцию. Общий родитель хранит подтверждённые заявки, список сообщает id, а итог читает тот же источник. Место записи теперь можно найти по договору.

Но поднимать все поля в App не требуется. Имя и количество до отправки нужны только форме. Если считать любой ввод готовой заявкой, одно движение курсора начнёт менять список. Разделим черновик и подтверждённый результат.

## Глава 02. Как переиспользовать форму и оболочку?

Слайды 21–33.

### Слайд 21. Как переиспользовать форму и оболочку?

Список уже сообщает действия владельцу. У формы другая граница: она собирает несколько полей и только при отправке передаёт согласованный результат. Внутри неё можно повторно использовать поле, которое сообщает каждое новое значение.

Сравним эти два ритма — изменение поля и отправку целой формы. Затем отделим повторяющуюся оболочку от её содержимого с помощью слотов.

### Слайд 22. Черновик ещё не является заявкой

Это локальные переменные RegistrationForm. Пользователь может ввести половину имени или очистить число — коллекция App пока не меняется. Для числового поля оставляем number | string: пустое поле с v-model.number может дать строку. Проверка должна учитывать фактическое значение.

CanSubmit описывает допустимость черновика, а не готовность сервера принять заявку. Disabled помогает пользователю, но обработчик всё равно проверяет данные перед emit. Серверная отправка в этом локальном примере намеренно отсутствует.

[Порядок разбора по кликам: Черновик → нормализация имени и тип числа → диапазон.]

### Слайд 23. При отправке форма передаёт проверенный результат

Submit — логическое сообщение формы с обычным объектом name/count. Черновик не получает id, пока родитель не создаст подтверждённую запись. В рабочем шаблоне используется form с @submit.prevent: Enter из поля и нажатие кнопки приходят к одному обработчику, стандартная перезагрузка страницы предотвращена.

Emit синхронно вызывает подключённый обработчик. В нашем локальном договоре тот сразу добавляет допустимую запись, поэтому затем можно очистить форму. ### Слайд 33. Три договора решают разные задачи

На Frontend Meetup эти роли видны одновременно. Список читает rows через prop и сообщает id через remove. Поле количества использует договор prop плюс событие модели. Панель получает заголовок и кнопку как содержимое слотов.

## Глава 03. Когда компонент обновляет DOM?

Слайды 34–49.

### Слайд 34. Когда компонент обновляет DOM?

После props и событий у нас есть дерево компонентов. Теперь нужно вернуть фокус в поле и понять, что произойдёт при скрытии формы. Сначала восстановим короткую цепочку от изменения состояния до DOM и проверим, сохраняются ли настоящие узлы и экземпляр компонента.

Затем схема жизненного цикла расположит хуки вокруг создания, обновления и удаления. Подробности Virtual DOM остаются в необязательном приложении E: основной маршрут опирается на наблюдаемое поведение, доступность DOM и ответственность за ресурсы.

### Слайд 35. Изменение состояния не сразу изменяет DOM

После props и событий важно понять, когда новые данные становятся видны в браузере. При отображении Vue отслеживает используемые реактивные значения. Когда такое значение меняется, Vue планирует обновление. Несколько синхронных записей могут объединиться: состояние уже новое, а DOM ещё прежний. Позже проверим этот промежуток в журнале хуков и научимся ждать обновления через nextTick.

Vue повторно вычисляет описание нужного интерфейса и согласует с ним настоящий DOM. Дерево таких описаний называют Virtual DOM. Оно не является второй копией браузерных элементов: это данные о желаемом результате. Для работы с компонентами сейчас достаточно этой роли; render-функции, VNode и алгоритм согласования вынесены в необязательное приложение E.

Обновление представления не запускает setup заново и не означает обязательную замену всех элементов. Запись в ref, который не участвует в отображении, сама по себе не требует обновления этого компонента. Проверим настоящие ссылки: что сохраняется при новом тексте, другом корневом теге и смене key компонента?

### Слайд 36. Проверим сохранение настоящего DOM-узла

[Начать заново. Начальное count=1, тип корня p. Зафиксировать исходный идентификатор экземпляра в строке состояния.]

Нажать «Изменить текст и атрибут». Count становится 2, текст и атрибут меняются. В журнале root before === after равно true, ссылка на статический span тоже та же, экземпляр тот же. Наблюдатель фиксирует фактические изменения атрибутов и дочернего текста. Конкретный способ обновления текста может дать characterData или childList: количество таких записей не является количеством пересозданных компонентов.

Нажать «Сменить p ↔ section». Тип корня другой, поэтому root и вложенный span теперь новые, но идентификатор экземпляра сохранён. Компонент продолжил жить, изменив свой корневой элемент. Нажать «Сменить key компонента»: теперь меняется и экземпляр, и root. Родительское count при этом сохраняется — оно не принадлежит удалённому ребёнку.

Текст обновился без нового экземпляра; другой HTML-тег заменил DOM, но сохранил компонент; новый key создал другого владельца состояния. Теперь расположим хуки вокруг этих событий на схеме жизненного цикла.

Диагностика сравнивает ссылки после nextTick и использует useId экземпляра, а не условную надпись с заранее выбранным результатом. MutationObserver установлен только на сцене; журнал вне неё не загрязняет результаты. Наблюдатель отключается при удалении стенда. Код отражает реальные Vue-компоненты RenderProbe и RenderMechanismLab; template ref компонента и defineExpose используются внутри измерительного стенда, их не требуется осваивать для понимания результата.

### Слайд 37. Три этапа жизни одного экземпляра

[Сначала пройти верхнюю строку слева направо, затем петлю обновления, после — нижнюю строку справа налево. Схему можно открыть отдельно нажатием. Связать верхнюю строку с первым появлением DOM, а повторяемую петлю — с обновлением уже существующего экземпляра из предыдущего опыта.]

Setup создаёт состояние и регистрирует callbacks. OnBeforeMount вызывается перед первым рендером: DOM этого экземпляра ещё не создан. Vue строит и вставляет DOM, после чего вызывает onMounted. Затем экземпляр продолжает жить. Его setup не запускается повторно от каждого нажатия кнопки.

Средняя строка — повторяемый путь. Когда изменяется состояние, используемое при отображении, Vue планирует обновление. В onBeforeUpdate мы можем увидеть новое состояние вместе с прежним DOM. Затем Vue применяет изменения и вызывает onUpdated. Изменение ref, который не использует рендер, само по себе не обязано запускать этот цикл. Несколько синхронных записей могут объединиться в один проход.

При удалении через v-if или смену идентичности включается нижняя ветка. В onBeforeUnmount экземпляр ещё работоспособен; затем Vue удаляет дерево и останавливает связанные эффекты. OnUnmounted приходит после удаления потомков. Если компонент снова появился, это новый экземпляр и новый setup. Схема описывает обычный клиентский цикл без KeepAlive, SSR и асинхронных потомков: специальные режимы остаются в приложении B.

### Слайд 38. Template ref указывает на конкретный элемент

Name хранит ввод пользователя, а nameInput — ссылку на объект input в браузере. UseTemplateRef появился в Vue 3.5; строка совпадает с атрибутом ref. Параметр HTMLInputElement описывает доступные методы, включая focus.

До монтирования и после удаления элемента ссылка может быть null. Optional chaining не создаёт элемент, а лишь пропускает вызов, если ссылки ещё нет. Поэтому одного знака вопроса недостаточно, когда по сценарию фокус обязательно должен перейти: нужно выбрать правильный момент.

[Все три коротких фрагмента видны. Слева создание ссылки, справа привязка к input и вызов focus. Условие существования элемента разберём на следующем слайде.]

### Слайд 39. onMounted запускает работу после появления DOM

В onMounted доступен DOM синхронно смонтированного дерева этого компонента. Для нашего обычного input этого достаточно. Это не обещание, что завершились все запросы, загрузились изображения или смонтировались любые асинхронные потомки.

Регистрируем хук при выполнении setup, а не после произвольного await или таймера: Vue должен связать callback с активным экземпляром. Не фокусируем каждую появившуюся панель автоматически — два одновременно открытых компонента начали бы бороться за внимание пользователя.

[Порядок разбора по кликам: Создание ссылки → момент доступа после mount.]

### Слайд 40. В beforeUpdate состояние новое, а DOM ещё прежний

Начальное count равно нулю, в output тоже ноль. В обработчике два синхронных увеличения. После них состояние уже два, но Vue ещё не применил обновление DOM. OnBeforeUpdate видит пару 2 / 0. После рендера onUpdated видит 2 / 2. Setup и mounted не повторяются.

[Подсветка: два присваивания → beforeUpdate → updated.]

Это один пакет обновления, а не два обязательных прохода на две записи. Наблюдаем зависимость рендера от count; произвольный ref, который шаблон не читает, отдельно проверим в стенде. OnUpdated сообщает об обновлении DOM владельца в целом, а не о конкретном пользовательском действии. Если нужен DOM после определённого присваивания, nextTick выразит намерение точнее. Не изменяем здесь count: новое присваивание, влияющее на рендер, может создать бесконечный цикл. В стенде журнал хранится снаружи наблюдаемого дерева; запись в него не меняет состояние родителя или ребёнка.

### Слайд 41. Наблюдаем хуки родителя и ребёнка

[Начать заново. Дерево закрыто, журнал пуст. Нажать «Создать дерево».]

Сначала у родителя setup и beforeMount; затем setup, beforeMount и mounted ребёнка; после него mounted родителя. Для синхронных потомков mounted родителя означает, что они уже смонтированы. Не распространяем эту гарантию на все асинхронные компоненты и запросы. В колонке DOM до mount будет «нет», после — 0.

[Очистить журнал и нажать «Два изменения count».]

Получим четыре записи: родитель beforeUpdate 2/0, ребёнок beforeUpdate 2/0, ребёнок updated 2/2, родитель updated 2/2. Два присваивания дали один цикл; setup и mounted не повторились. Очистить журнал и нажать «Изменить неиспользуемый ref»: останется только диагностическая строка команды, без update-хуков. Неиспользуемый ref не читается рендером дерева.

[Очистить журнал, затем нажать «Удалить дерево».]

BeforeUnmount родителя идёт перед beforeUnmount ребёнка, а unmounted ребёнка — перед unmounted родителя. В beforeUnmount DOM ещё показывает 2, в unmounted ссылка уже null и журнал выводит «нет». Новое «Создать дерево» создаёт другой экземпляр со state=0 и новым setup. Журнал остаётся у внешнего владельца, поэтому удаление дерева не стирает наблюдения. Реальный порядок проверяется приложением, не задаётся списком ожидаемых строк. Все действия выполняет преподаватель.

### Слайд 42. Состояние изменилось, DOM обновится следом

Vue группирует обновления DOM. Присваивание open уже изменило состояние, но создание input выполняется при обработке запланированного обновления. NextTick ждёт его завершения, поэтому после await мы обращаемся к элементу новой версии интерфейса.

NextTick не ждёт загрузки HTTP и не гарантирует, что браузер уже нарисовал следующий кадр на экране. Мы ждём именно обновления DOM Vue. В стенде подписок этой главы журнал покажет наличие поля сразу после изменения и после nextTick.

[Порядок разбора по кликам: Начальные условия → изменение state → ожидание DOM и focus.]

### Слайд 43. Фокус следует за действием пользователя

Это полный успешный путь submit нашей локальной формы. После синхронного добавления у владельца форма сбрасывает собственный черновик. Затем возвращает фокус в имя, чтобы можно было ввести следующую заявку. Связь с пользовательским действием делает перемещение фокуса ожидаемым.

Мы не вызываем focus после каждого изменения состояния и не используем onUpdated для такого правила. При удалении строки возникает другой случай: сфокусированная кнопка исчезает, поэтому владелец списка после обновления переводит фокус в поиск. В обоих случаях выбираем доступную цель, а не потерянный DOM-узел.

[Порядок разбора по кликам: Проверка → событие → сброс → фокус после обновления.]

### Слайд 44. v-if удаляет экземпляр, v-show сохраняет его

Сравним одинаковое визуальное исчезновение. При false у v-if компонент удаляется, отрабатывает unmount; следующее true создаёт новый setup с новым черновиком. V-show оставляет экземпляр и DOM, меняя отображение через CSS.

Поэтому черновик при v-show сохранится, а mounted второй раз не вызовется. Скрытая подписка тоже продолжит существовать, если мы её явно не остановили. Выбор между v-if и v-show касается не только затрат на переключение, но и желаемого срока жизни локальных данных и работы.

### Слайд 45. Тот же тип компонента может продолжить жить с другим prop

V-if ответил на вопрос удаления и появления, но при смене выбранной записи условие может оставаться true. Если тип компонента и key прежние, Vue переиспользует экземпляр и обновляет prop. Локальный ref(props.record.name) тогда не превратится в черновик новой записи автоматически. Это тот же эффект, который уже наблюдали в стенде props.

По клику добавить key selected.id. Смена идентичности заставляет Vue удалить старый экземпляр и создать новый со свежим черновиком. Но вместе с этим теряются несохранённый ввод, фокус и ресурсы прежнего экземпляра. Поэтому key не универсальная кнопка обновления данных. Если нужно сохранять редактор, следует явно решить, когда синхронизировать его черновик и как предупредить о потере правок. Для проверки вернуться к кнопке «Новый экземпляр» стенда props: число родителя не меняется, но initial заново читает текущий вход.

[Сравниваем код без key и с key одновременно. Подсветка указывает на использование компонента и условие идентичности, а не на поясняющий комментарий.]

### Слайд 46. Внешняя подписка требует явной очистки

Window живёт дольше нашей панели. Он хранит callback независимо от того, остался ли компонент на экране. Для удаления нужно передать ту же функцию onPulse, а не новую стрелочную функцию с похожим телом.

Vue убирает свои обработчики вместе с DOM и останавливает связанные реактивные эффекты, но не знает, какие внешние ресурсы мы создали вручную. Для таймера понадобился бы clearTimeout, для подписки — её unsubscribe. Здесь одна явная пара установки и снятия показывает общий принцип.

[Порядок разбора по кликам: Одна функция → установка подписки → снятие той же функции.]

### Слайд 47. До удаления и после удаления нужны разные действия

В beforeUnmount ещё доступны DOM и работающий экземпляр. Если сторонний редактор или график требует свой контейнер для корректного destroy, его освобождают здесь. Хук не является возможностью отменить размонтирование: return false не сохраняет компонент. Для подтверждения несохранённых правок нужен отдельный договор управления действием.

В unmounted потомки уже удалены и связанные эффекты setup остановлены. Для ручного таймера, слушателя window или соединения нужно наше освобождение; Vue не знает об их происхождении. Можно снимать ресурс и раньше в beforeUnmount, если это соответствует договору, — нет правила, что любая очистка обязана ждать unmounted.

Синхронно созданные в setup watchers останавливаются вместе с владельцем. Ожидание Promise и внешний listener от этого сами не исчезают: для них нужны signal, invalidate либо unsubscribe. Подробно разделим очистку одного запуска и завершение всего владельца в следующей главе. Главная проверка здесь: требуется ли освобождению живой DOM и когда ресурс перестаёт быть нужен?

### Слайд 48. Повторное открытие не должно умножать callbacks

[Сбросить подписки. Оставить v-show выключенным, очистку включённой. Нажать «Открыть».]

Сразу после изменения поле отсутствует, после nextTick существует и получает фокус. Ввести «Вера», скрыть и открыть: новый экземпляр имеет пустой черновик. Затем скрыть, включить «Сохранять через v-show», открыть, ввести имя и повторить скрытие: черновик сохраняется, поле остаётся в DOM.

Для опыта подписок снова выбрать v-if, сбросить. С выключенной очисткой трижды открыть и скрыть; одно «Отправить событие» даст три записи. Это настоящий dispatchEvent в window. Нажать «Сбросить подписки», включить очистку и повторить: в открытой панели одно событие даёт один callback, в закрытой — ни одного. Сброс снимает и намеренно оставленные учебные подписки.

### Слайд 49. Ресурс завершает тот, кто создал его для своей работы

Теперь можно отдельно спросить о данных и о ресурсе. Коллекция в App переживает скрытие формы, а черновик удалённой формы — нет. Подписка window должна завершиться с экземпляром, который её использовал; одного исчезновения HTML недостаточно.

У запроса будет ещё одна граница: прежняя операция может стать ненужной, хотя сам компонент продолжает жить. Смена запроса и удаление владельца — разные причины очистки. Для их объяснения вернёмся к поиску из лекции 10.

## Глава 04. Как связать побочные эффекты с состоянием компонента?

Слайды 50–58.

### Слайд 50. Как связать побочные эффекты с состоянием компонента?

Мы уже умеем завершать подписку при удалении компонента. Теперь усложним условие: сам компонент продолжает жить, но значение, для которого он начал работу, меняется. Нужно связать побочный эффект — side effect — с актуальным состоянием, а затем отдельно обслужить удаление владельца. Такие задачи возникают у загрузки данных, синхронизации с внешним виджетом или записи настроек.

Для конкретного наблюдения используем уже готовый клиент и алгоритм лекции 10. Сначала покажем, почему обработчик одного DOM-события не покрывает все способы изменить состояние. Затем введём watch, один начальный запуск и две границы завершения: новая операция и удаление панели. Сетевые проверки, номера запросов и AbortController заново не реализуем. В конце получим связанную обязанность, которую следующая глава вынесет в composable.

### Слайд 51. Состояние изменилось, а обработчик поля не вызван

В лекции 10 загрузку можно было явно вызвать в обработчике выбора. Слева показан упрощённый вариант такого подхода во Vue: v-model меняет query, change вызывает готовую actions.search. Пока пользователь меняет именно select, эта связь выглядит достаточной.

Теперь кнопка «Выбрать Бориса из кода» или восстановление состояния присваивает query.value. Значение select обновится через v-model, но браузер не отправляет событие change из-за программного присваивания. Привязанный к change вызов не произойдёт. Мы получили новое выбранное имя при прежнем списке — наблюдаемый разрыв между состоянием и работой.

[Выделить обработчик change, затем присваивание справа; оба фрагмента остаются видны. Спросить: что изменилось, а чего не произошло?]

Можно вручную вызывать search в каждом месте изменения query. Но тогда каждое новое место обязано помнить о второй операции. Требование здесь другое: данные должны соответствовать текущему query независимо от способа его изменения. Это задача наблюдения за состоянием. Computed подходит для вычисления значения из уже имеющихся данных; HTTP-запрос — внешняя работа. Для отправки формы по кнопке явный обработчик остаётся подходящим решением: не всякий эффект нужно превращать в наблюдатель.

### Слайд 52. watch отделяет источник от действия

В первом аргументе ref — реактивный источник. Callback получает новое и предыдущее значение. По умолчанию watch не вызывает callback при регистрации: он ждёт изменения источника. Присваивание Бориса вызывает запланированный callback, но повторное присваивание той же строки не является новым значением.

Начинаем с console.log, чтобы сеть и await не скрыли сам механизм. Обычные callbacks watch сгруппированы: несколько синхронных изменений не обещают отдельный вызов на каждое промежуточное значение. Теперь можно заменить диагностическую запись вызовом нужной операции.

[Порядок разбора по кликам: Источник → callback → изменение, которое его запускает.]

### Слайд 53. watch реагирует на новое значение из любого источника

Слева два способа изменить один ref: выбор в поле и программное присваивание в обработчике кнопки. В template ref разворачивается автоматически, поэтому присваивание выглядит как query = 'Борис'; в script это query.value. Справа одна связь с готовой операцией actions.search. Вызов HTTP остаётся внутри знакомого алгоритма; watch решает только, когда передать ему новое значение.

[По кликам: поле → кнопка → ref и watcher → весь договор. На экране одновременно два фрагмента: template и setup до выноса в composable.]

Старый @change с вызовом search убрали: иначе одно действие могло бы запустить загрузку дважды. Повторное присваивание той же строки не считается новым значением. Кнопка «Обновить», напротив, выражает отдельную команду пользователя и вызывает refresh даже при прежнем query. Не заставляем такую команду менять строку ради запуска watcher.

Пока watcher ждёт первого изменения. Но панель должна показать исходный список сразу после создания: это следующая маленькая задача, которую решит immediate.

### Слайд 54. У первой загрузки должен быть один инициатор

Immediate вызывает callback и для начального query. Поэтому компонент загружает исходный список без дополнительного onMounted. При смене поля v-model изменяет ref, watcher вызывает search; отдельный change-handler повторил бы тот же запуск.

Кнопка «Обновить» остаётся явным действием: значение query может вообще не измениться, но пользователь просит принудительное повторное чтение. Её handler передаст force=true. Разделяем повторную команду и синхронизацию с условием, чтобы одна операция не имела двух случайных инициаторов.

[Сначала один корректный immediate watcher. Затем выделить конкретный лишний onMounted: вместе эти строки создадут два запуска. Нижняя строка — намеренная ошибка для сравнения, её не добавляем в приложение.]

### Слайд 55. Новая операция и удаление владельца — разные границы

Здесь новая связь с главой о жизненном цикле. Анна сменилась Борисом, но панель не удалялась: её локальное состояние и экземпляр продолжают жить. Нужно сменить операцию внутри того же владельца. Готовая search из лекции 10 уже отменяет или обесценивает прежний результат перед новой загрузкой. Сам watcher этой защиты не создаёт.

Закрытие панели — другая граница. Её экземпляр завершается, поэтому больше не нужны ни текущая операция, ни возможность начинать следующие. Для этого фабрика предоставляет окончательный dispose. Вызвать dispose при каждом изменении query означало бы закрыть живой сервис вместо замены операции.

Vue остановит синхронно созданный в setup watcher вместе с компонентом. Но остановка наблюдения не отменяет произвольный Promise или сетевой ресурс сама по себе. Внешнюю работу завершаем по договору её владельца. Подробная самостоятельная реализация onCleanup и отмены находится в приложении C; здесь подключаем готовые операции к двум нужным событиям.

### Слайд 56. Смена состояния запускает работу, unmount завершает её владельца

Теперь две границы видны в короткой законченной связке. Watch запускает готовую search с актуальным query, включая первое чтение через immediate. OnUnmounted передаёт фабрике окончательный dispose. Refresh остаётся явной командой принудительного чтения, потому что новое значение query для неё не требуется. Actions и query уже созданы в setup; здесь показаны только связи, а не вся конфигурация клиента.

[Выделить запуск по состоянию, завершение владельца и отдельную команду refresh. Фрагмент остаётся виден целиком.]

Гарантии разделены: watch замечает изменение, search из лекции 10 управляет сменой операции и актуальностью результата, dispose закрывает фабрику при удалении панели. Не добавляем ещё один AbortController поверх готового алгоритма. Синхронно созданный watcher остановится автоматически, но ресурс фабрики требует вызова dispose.

Следующий стенд покажет все три случая на настоящем приложении: изменение поля, присваивание из кода и закрытие панели во время ожидания. Код пока показан до извлечения в composable: следующая глава соберёт именно эту связь вместе с состоянием и подписью.

### Слайд 57. Проверим изменение состояния и удаление владельца

[Начать заново и дождаться исходных трёх заявок в обеих панелях. Все действия выполняет преподаватель.]

В A выбрать Анну через поле «Имя»: query меняется и watcher запускает готовый алгоритм. Прежде чем медленная Анна завершится, нажать в A «Выбрать Бориса из кода». Кнопка присваивает ref, не вызывает search и не отправляет change. Поле переключится на Бориса; после завершения быстрого чтения список A содержит Бориса. Это доказывает, что работу запускает изменение состояния, а не только событие select. B сохраняет свой список.

Нажать ту же кнопку ещё раз: query уже равен Борису, нового запуска нет. Для повторного чтения нажать «Обновить»: это явная команда, которая работает при прежнем условии. Настоящий журнал различает эти действия; задержки и кеш управляются клиентом из лекции 10. Здесь не повторяем устройство HTTP и проверку payload.

Затем сбросить стенд, дождаться исходного списка и начать Анну в A. Сразу нажать «Закрыть A». Внешний журнал показывает dispose, панель не возвращается после позднего завершения. B продолжает жить. Открыть A: новый экземпляр начинает с исходного query и первой загрузки. Удаление завершило прежнего владельца, а не сохранило его в паузе.

После опыта спросить, где находятся три ответственности: watch реагирует на query; search заменяет текущую операцию и защищает результат; onUnmounted вызывает окончательный dispose. В следующей главе вынесем эти уже понятные связи в функцию. Управляемые задержки и HTTP 503 остаются имитациями, fetch и проверка JSON настоящие.

### Слайд 58. Состояние задаёт работу, компонент — срок её жизни

У нас есть несколько разных гарантий. Watch видит изменение query. Клиент проверяет статус и поля. Алгоритм решает, какой результат ещё актуален. Unmount завершает экземпляр поиска. Ни одна из этих обязанностей не исчезла из-за добавления реактивности.

Теперь в каждом компоненте панели повторяются создание state, вызов фабрики, computed-подпись, watcher и очистка. Появилась конкретная повторяющаяся связь — её и вынесем в composable. Сетевой алгоритм заново писать не потребуется.

## Глава 05. Как повторить логику без случайной общей памяти?

Слайды 59–71.

### Слайд 59. Как повторить логику без случайной общей памяти?

Два экземпляра панели должны иметь одинаковое поведение и независимые запросы. Копирование setup с watcher и очисткой создаёт риск, что в одной версии забудут обслуживание. Но перенос ref на уровень модуля случайно объединил бы состояния.

Нужна функция, которую каждый setup вызывает заново и которая создаёт принадлежащие ему реактивные связи. Сначала увидим её на маленьком счётчике, затем обернём фабрику поиска.

### Слайд 60. Повторяется связь состояния и работы

Этот фрагмент связывает обычный алгоритм с Vue. CreateRegistrationSearch не импортирует Vue и не знает о шаблоне. Reactive даёт ему отслеживаемый объект, computed формирует подпись, watcher выбирает запуск, hook завершает владение.

Именно эту связку хочется повторно использовать вместе. Если вынести только одну строку reactive, остальная повторяющаяся обязанность останется в компонентах. Но и превращать всю страницу в универсальный сервис не требуется: форму и разметку панели оставляем компонентам.

[Порядок разбора по кликам: Реактивная оболочка и алгоритм → подпись → источник запуска → завершение.]

### Слайд 61. Composable — обычная функция с реактивной логикой

Composable не является новой конструкцией языка: это обычная функция JavaScript. Мы называем её composable, когда она собирает переиспользуемую реактивную логику через Composition API: состояние, вычисления, наблюдение или обслуживание ресурсов. Не каждый composable обязан создавать собственный ref или регистрировать хук; это зависит от задачи.

Префикс use помогает узнать такой договор в коде, но Vue не ищет функции по этому имени и не запускает их автоматически. Когда setup вызывает функцию, её обычный код выполняется сразу. Зарегистрированные callbacks выполнятся позже, в свой момент жизненного цикла или при изменении источника.

В наших примерах вызов синхронный, внутри setup: эффекты и хуки получают компонент-владелец. У composable нет собственного компонента и отдельной разметки. Сначала посмотрим маленькую функцию без внешней работы, затем проверим, как хуки нескольких функций подключаются к одному владельцу. Более общая область эффектов находится в приложении D.

### Слайд 62. Начнём с composable без сети

Это исходник useSeatCount.ts, который уже работает в двух счётчиках первой главы. Каждый вызов создаёт новый ref count и computed, читающий именно его. Increment сохраняет доступ к этому ref через замыкание — тот же механизм языка, который разбирали в 07.

Функция возвращает объект с живыми ссылками и операцией. Она не рисует кнопку, поэтому один и тот же договор можно использовать в разных представлениях. Ограничение пять проверяется и в операции; disabled в шаблоне лишь отражает canAdd.

[Порядок разбора по кликам: Локальное значение → вычисление → операция → возвращённый договор.]

### Слайд 63. Компонент получает refs и связывает их с шаблоном

Слева setup вызывает useSeatCount один раз и получает count, canAdd и increment. Функция уже выполнилась, но возвращённые refs и замыкание increment продолжают связывать компонент с созданным состоянием. Деструктуризация здесь переносит ссылки на ref-объекты, а не извлекает числа из их value.

Справа тот же шаблон счётчика, который уже видели в первой главе. Template автоматически разворачивает refs: пишем count и canAdd без value. При нажатии increment меняет count.value, computed пересчитывает canAdd, а Vue обновляет текст и disabled. В script для чтения ref нужен count.value. Импорты и обёртки script/template опущены, чтобы два небольших фрагмента оставались видны вместе.

[По кликам: вызов и возвращённые значения → их использование в шаблоне → обе стороны.]

Функция не рисует кнопку и не создаёт ещё один компонент. SeatCounter владеет представлением, useSeatCount собирает его логику. Следующий вопрос: если второй SeatCounter вызывает ту же функцию, получит ли он тот же count? Проверим это до перехода к более сложной загрузке.

### Слайд 64. Одна функция, два вызова, два состояния

[Начать заново. В A и B по одному месту. Сначала спросить, изменится ли B после нажатия кнопки в A.]

Дважды нажать «Ещё место» в A: в A три, в B одно. Затем один раз нажать в B: теперь A три, B два. В каждом SeatCounter setup вызвал useSeatCount отдельно; строка ref(1) внутри функции создала отдельный объект. У каждого increment своё замыкание над своим count.

Довести A до пяти: его кнопка отключена, B остаётся доступным. Ограничение находится и в операции, а не только в disabled. Это настоящие refs, computed и обработчики, а не заранее нарисованные значения. Кнопки доступны с клавиатуры.

Одинаковый исходник функции не означает общую память. Если перенести ref за пределы функции на уровень модуля, договор изменится: вызовы могут получить одну ссылку. Composable не гарантирует независимость автоматически — в этом примере её обеспечивает место создания состояния. Теперь отделим независимость данных от другого вопроса: кто владеет зарегистрированными внутри функциями хуками?

### Слайд 65. Хуки composables принадлежат вызывающему компоненту

UseLifecycleTrace выполняется как обычная функция во время setup. Каждый вызов onMounted или onUnmounted добавляет callback к текущему экземпляру компонента. У функций A и B нет собственных компонентов и отдельных циклов монтирования: обе подключаются к тому владельцу, в setup которого их вызвали.

Здесь для одного экземпляра обычные регистрации идут последовательно. При mounted журнал получает A, B, Компонент. При unmounted — снова A, B, Компонент: это порядок регистрации callbacks данного хука, не обратный порядок освобождения стека. Второй onMounted не заменяет первый. Порядок родителя и ребёнка — другой вопрос; его разбирали в главе 03.

[По кликам: объявление функции → регистрация mounted → регистрация unmounted → вызовы и собственные регистрации компонента → оба фрагмента.]

Callbacks вызываются последовательно, но Vue не ждёт завершения произвольного async callback перед запуском следующего. Если A делает await, B может начать работу раньше, чем A завершит ожидание. Зависимость операций нужно выразить явно в одной последовательности. У composable нет отдельного автоматического вызова при каждом обновлении: функция вызывается нашим setup, а callbacks — механизмом Vue.

Это выдержка из useLifecycleTrace.ts и ComposableHookOwner.vue: типы и импорты опущены. Report пишет во внешний журнал, поэтому удаление компонента не уничтожит наблюдения. Следующий стенд проверит обе последовательности настоящими хуками.

### Слайд 66. Несколько composables добавляют хуки одному владельцу

[Начать заново. Компонент ещё не создан, журнал пуст. Спросить, сколько mounted-callbacks появится после одного создания.]

Нажать «Создать компонент»: видим один компонент, в журнале A: mounted, B: mounted, Компонент: mounted. Это два composables и собственный callback одного экземпляра, а не три компонента. Нажать «Удалить компонент»: появятся A: unmounted, B: unmounted, Компонент: unmounted. Журнал хранится у внешнего стенда, поэтому результат удаления остаётся виден.

Повторить создание: добавятся три новых mounted-записи для нового владельца. Старые callbacks не переносятся в него; его setup снова вызвал обе функции и зарегистрировал новые. «Очистить журнал» стирает наблюдения, но не создаёт и не удаляет компонент и не запускает хуки. Все кнопки можно нажать клавиатурой.

Стенд использует настоящие onMounted/onUnmounted; ожидаемые строки не подставляются вместо выполнения Vue. Хуки регистрируются синхронно в setup. Теперь можно вернуться к внешней работе главы 04: вынесенный в функцию onUnmounted по-прежнему завершит ресурс вызывающей панели. Рефакторинг не должен потерять эту связь.

### Слайд 67. Знакомая связка переезжает в composable

Слева уже знакомые обязанности: состояние, готовая фабрика, вычисленная подпись, запуск и завершение. Мы не заменяем алгоритм запросов и не убираем hook. Эти строки вместе с существующей настройкой клиента становятся телом useRegistrationSearch. Справа панель получает нужные ей состояние, подпись и команду refresh через один вызов. Это изменение места кода, а не новое поведение загрузки.

[По кликам: создание данных и операций слева → реактивные связи и hook слева → вызов справа → обе стороны. Короткие фрагменты одновременно остаются видны.]

Query и file — refs, которые принадлежат панели; base задаёт адрес файлов, trace сохраняет внешний журнал после удаления. Это параметры существующего примера, а не обязательные параметры любого composable. В основном маршруте не читаем настройку клиента построчно. Полный исходник функции с load и параметрами находится в приложении D и examples/11-vue-components/src/composables/useRegistrationSearch.ts.

State и actions создаются внутри функции. Если вынести их на уровень модуля, независимость A и B изменится. OnUnmounted внутри composable зарегистрируется у вызывающей панели — только что проверили это на маленьком стенде. Следом уточним договор входного ref, посмотрим шаблон потребителя и проверим сохранение поведения двух панелей.

### Слайд 68. Реактивный вход сохраняет источник изменений

Договор этой функции намеренно узкий: query должен быть Ref<string>. Это позволяет точно знать, как читать текущее значение и как наблюдать изменения. Query.value — текущая строка; она не содержит связи с ref, за изменениями которого должен следить watch из главы 04. Передаём сам ref, чтобы сохранить эту связь. Пример getter для props находится отдельно в приложении C.

Мы могли бы принять также getter или обычное значение и нормализовать через toValue. Но универсальный вход нужен только при реальных разных способах использования. Для двух панелей с собственным ref такое расширение пока не решает проблемы; необязательный вариант есть в приложении D.

[Договор Ref<string> → передача ref → конкретная ошибочная передача строки. Остальные параметры опущены в этой выдержке; альтернативные вызовы не выполняются вместе.]

### Слайд 69. Панель описывает представление и команды

После выноса панель всё ещё выбирает свои поля и отображение. Она владеет ref query и file, вызывает composable, показывает state и message. Обновление кнопкой остаётся явной командой, а изменение query запускает работу через уже установленную связь. Кнопка программного выбора Бориса также остаётся в полном исходнике; она только меняет ref, как в главе 04.

В полном файле RegistrationSearchPanel.vue также находятся список, ошибка и журнал. Они не исчезли из приложения после сокращения setup. Рефакторинг должен сохранять наблюдаемый договор: одинаковые поля, начальная загрузка, кеш, отмена и отказ обновления. Именно это проверим на двух экземплярах.

[По кликам: setup панели и вызов composable → поле шаблона → команда и сообщение. Это выдержка: imports, объявление props и trace находятся в полном исходнике RegistrationSearchPanel.vue. Границы script/template сохранены для корректного чтения и подсветки.]

### Слайд 70. Два вызова — две независимые операции

[Начать заново. Дождаться загрузки A и B. В A выбрать Бориса, B оставить на всех.]

Только A меняет список. Состояние, controller и кеш созданы внутри отдельного вызова composable и фабрики. Закрыть A, пока он ждёт медленную Анну: внешний журнал отмечает dispose. Нажать «Обновить» в B — он продолжает работать.

Открыть A заново: создаётся новая фабрика, снова выполняется начальная загрузка. Удалённый экземпляр не оживает. После этого показать первые строки composable: state создаётся внутри функции. Если вынести эту строку наружу, два вызова получат одну ссылку и договор независимости изменится.

### Слайд 71. Компонент повторяет интерфейс. Composable — реактивную логику

Мы повторно использовали и форму интерфейса, и механизм работы, но разными средствами. Компонент хранит шаблон и определяет обмен с окружением. Composable соединяет реактивные данные, операции и обслуживание ресурсов без собственной разметки.

Одинаковый код не означает общую память. Если два удалённых участка должны разделять один набор заявок, нужен отдельный ответ на вопрос о владельце общего состояния. Это задача лекции 12. Пока локальное дерево и независимые экземпляры решают показанные потребности.

### Слайд 72. Проверим границы в одном сценарии

На следующие два демонстрационных слайда выделено пять минут вместе с этим ориентиром. Начинаем с локальной регистрации: Анна — два места, Борис — одно, фильтр и черновик пустые. Затем переходим к отдельному чтению API, где нет серверной записи.

Сейчас важно проследить не названия API по очереди, а полный путь. Поле меняет черновик, форма сообщает результат, владелец меняет коллекцию, DOM следует за состоянием. Во второй части query запускает работу, алгоритм выбирает актуальный исход, удаление панели завершает владельца.

### Слайд 73. Поле, форма и владелец согласуют одно изменение

[Сбросить. Начальные данные: Анна — два, Борис — одно.]

Ввести Веру и два места. До Enter получить прогноз: пока две заявки и три места. Отправить форму: теперь три заявки и пять мест; черновик пуст, фокус в имени. Заголовок панели показывает актуальный seats родителя через слот. Открыть журнал и сопоставить submit с одной записью App.

### Слайд 74. Закрытие панели завершает её работу

[Переключить на «Загрузку списка». Напомнить: другой read-only источник, локальная форма ничего сюда не отправляла. Дождаться начального чтения A и B.]

В A выбрать Анну и сразу Бориса: остаётся Борис, B не меняется. Выбрать ответ HTTP 503 и нажать «Обновить»: старый успешный список остаётся вместе с ошибкой обновления. Вернуть корректный ответ, выбрать Анну и закрыть A до окончания чтения. Внешний журнал показывает dispose; поздний исход не открывает A и не меняет B.

Нажать «Обновить» в B, затем открыть A: B работает независимо, A создаётся заново. Условие кеша — пять секунд; для обязательного чтения использовать «Обновить». Задержки и 503 имитируются, чтение JSON и проверки настоящие. Отмена чтения не является откатом записи сервера.

### Слайд 75. На какой границе искать причину?

Если число мест неверное, сначала найдём коллекцию и вычисление, а не будем менять классы интерфейса. Если remove виден в журнале, но строка остаётся, проверим listener владельца. При двойном запросе ищем двух инициаторов, при накоплении callbacks — неснятую внешнюю подписку.

Порядок помогает сузить причину. Реактивность не исправит неверный договор и не превратит снимок в источник. По этой карте разберём три небольших поломки устно; среда студентов для этого не требуется.

### Слайд 76. Где возникла каждая из трёх поломок?

Поочерёдно раскрывать фрагменты и ответы, не просить студентов писать код. На обсуждение и объяснение трёх минут достаточно. В первом случае спросить, изменится ли local после нового prop. Нет: ref взял начальное число; для живого представления читать prop или использовать computed.

Во втором случае immediate уже сделал первую загрузку, затем onMounted повторяет её. Убрать второго инициатора. В третьем ref создан на уровне модуля, поэтому оба вызова возвращают одну ссылку. Перенести создание внутрь функции, если договор требует независимости. Сначала получить одну-две устные версии, затем раскрыть причинное объяснение.

### Слайд 77. Компоненты договорились. Как организовать всё приложение?

Сегодня договорили, кто хранит коллекцию и кто имеет право её менять. Отделили черновик от результата, значение поля от отправки формы и содержимое панели от её оболочки. Затем связали DOM и внешние ресурсы со сроком жизни экземпляра, а автоматический запуск — с явной причиной.

Composable собрал повторяющиеся связи, сохранив независимость двух панелей. Следующий вопрос возникает, когда данные нужны разным страницам, а выбор должен быть доступен по прямой ссылке. В 12 перейдём к структуре проекта, Router и общему состоянию. Сейчас оставим время на вопросы о границах сегодняшних решений.

## Приложение A. Редактор с сохранением и отменой

### Слайд 78. Дополнительно: как сохранить или отменить изменения?

Основной маршрут завершён. В нём копия prop была ошибкой, когда от неё ожидали живого отображения. Теперь появляется другая задача: пользователь редактирует заявку, но должен иметь возможность отменить изменения. Для этого нужен независимый черновик и явный момент подтверждения.

Сначала отделим черновик от исходной записи и разберём сохранение, отмену и внешнее обновление. Затем посмотрим, как вынесенные поля меняют имя и количество мест через две именованные модели. Редактор владеет черновиком; владелец коллекции принимает подтверждённую запись. Это разные границы изменения.

### Слайд 79. Копия нужна, когда изменение можно отменить

BeginEdit получает снимок плоской записи и создаёт отдельный контейнер. Cancel закрывает редактор, не записывая черновик в коллекцию. Save проверяет данные и передаёт результат владельцу. Для вложенных объектов один spread не создаёт независимые вложенные копии — глубину решения нужно выбирать по модели.

Внутри редактора draft — ref с копией записи, editing — признак открытого редактирования; объявления опущены. Следующий слайд вынесет поля в RegistrationFields: они будут менять только draft редактора через именованные модели. Save уже передаёт итог владельцу коллекции, поэтому изменение поля не становится сохранением заявки.

[Начало редактирования и копия → отмена → проверка и подтверждение.]

### Слайд 80. Несколько моделей получают разные имена

Именованная модель name связывает prop name с update:name, а count — с update:count. Это два независимых договора, а не автоматическая отправка всей формы. ### Слайд 87. watch задаёт источник, watchEffect собирает чтения

Слева watch получает источник query отдельно от callback. Vue отслеживает этот источник; чтение diagnostic внутри callback не добавляет ещё один источник. ### Слайд 89. watchEffect собирает чтения только до первого await

В предыдущем сравнении оба значения читались синхронно, поэтому оба становились зависимостями watchEffect. Здесь вводим одно новое условие: функция приостанавливается на await. Query читается до приостановки и входит в автоматически собранные зависимости. Diagnostic читается после возобновления; его изменение само по себе не запускает этот эффект.

Это не означает, что diagnostic заморожен или недоступен: console.log прочитает значение, актуальное в момент выполнения строки. Отслеживание причины повторного запуска и обычное чтение значения — разные вещи. Если diagnostic действительно должен определять новую операцию, его нужно прочитать в синхронной части либо явно назвать источники через watch. Служебное чтение не нужно автоматически превращать в причину загрузки.

[По кликам: чтение query → граница await → чтение diagnostic → весь фрагмент. Load — условная асинхронная операция, не реализация клиента приложения; обработка ошибок и отмена здесь опущены ради одного механизма.]

Сам watchEffect не решает гонки и не отменяет незавершённый Promise. Здесь показана граница отслеживания; следующие слайды приложения отдельно рассматривают отмену и регистрацию очистки. Официальная справка: https://vuejs.org/guide/essentials/watchers.html#watcheffect .

### Слайд 90. Новый запрос лишает старый права на запись

Перед нами знакомая защита из лекции 10 в сокращённой форме. Запуск B увеличивает latest и сообщает об отмене A. Если старая операция всё же дошла до результата, номер не позволяет ей записать свои данные поверх B. Catch требует такой же защиты: старый отказ тоже может испортить экран.

Watcher только решает, когда вызвать search. Он не гарантирует порядок сетевых завершений. Отмена помогает прекратить ненужное чтение, но не заменяет право на запись, особенно для последующей обработки, которая может не поддерживать signal.

### Слайд 91. Очистка запуска и остановка watcher — разные вещи

Это самостоятельный минимальный вариант одной операции, не код полной фабрики. OnCleanup регистрирует освобождение работы текущего запуска перед его заменой и при остановке watcher. Active лишает поздний callback права писать, controller передаёт отмену. Catch также проверяет active, чтобы отменённый запуск не показал ошибку поверх нового.

Watcher, созданный синхронно в setup, автоматически останавливается при unmount. Но сам Promise не является управляемым Vue ресурсом: его код завершает зарегистрированная очистка. Это альтернатива готовой фабрике основного маршрута: у неё уже есть собственные latest и controller. Две системы отмены поверх друг друга не добавляем.

### Слайд 97. toValue нормализует вход внутри реактивного чтения

ToValue принимает обычное значение, ref или getter. Вызов находится внутри getter наблюдателя, поэтому реактивное чтение ref либо props.query попадает в отслеживание. Если нормализовать один раз до регистрации watch и сохранить строку, связь снова потеряется.

Обычная строка даёт фиксированный источник и только начальный запуск. Такой договор удобен для разных потребителей, но требует объяснять различия. В основном примере Ref<string> проще и достаточен.

### Слайд 98. Таймер и область эффектов тоже имеют владельца

Debounce ждёт паузу между изменениями и снимает ещё не сработавший таймер при следующем запуске. Если таймер уже запустил запрос, clearTimeout его не отменит: потребуется отдельное обслуживание операции. Число 300 здесь часть механизма ожидания, а не учебная длительность слайда.

OnScopeDispose привязывает освобождение к активной области эффектов. Setup компонента выполняется в такой области; отдельная effectScope может владеть ресурсом без компонента. Это расширение срока жизни, а не способ автоматически получить общее состояние. Router и Pinia по-прежнему остаются в 12.

## Приложение E. Virtual DOM и renderer

Слайды 99–108. Необязательные материалы после основного маршрута.

### Слайд 99. Дополнительно: как Vue согласует описание и DOM?

Основной маршрут завершён: мы умеем различать обновление DOM и смену экземпляра, выбирать момент доступа к элементу и завершать внешнюю работу. Эта необязательная ветка объясняет внутреннюю модель уже наблюдавшегося поведения. Она не требуется для понимания хуков, watch или composable.

Сначала разделим экземпляр, VNode и DOM, затем пройдём от шаблона к render, первому монтированию и обновлению. В конце уточним роль type/key и сведений компилятора, затем свяжем реактивные зависимости render с диагностическими хуками. Писать render-функции вручную или запоминать внутренние helpers студентам не требуется.

### Слайд 100. Экземпляр, VNode и DOM — три разные сущности

После передачи нового prop ребёнок может обновить интерфейс без нового setup. Чтобы объяснить это, разделим три сущности. Экземпляр компонента владеет состоянием и связями. Render-функция описывает желаемый интерфейс через VNode. Настоящий DOM — объекты браузера, которые имеют textContent, attributes, фокус и методы.

Один экземпляр за время жизни создаёт много результатов render. При этом браузерный элемент может оставаться тем же объектом. И наоборот: экземпляр может сохранить состояние, но заменить свой корень с p на section. Значит, вопрос «обновился компонент?» недостаточен: нужно уточнить, пересчиталось ли описание, изменился ли DOM или был создан новый владелец состояния. Эти различия уже наблюдали в основном маршруте по ссылкам и идентификатору настоящего экземпляра.

### Слайд 101. Шаблон компилируется в функцию описания

Слева знакомая привязка атрибута и интерполяция текста. Справа эквивалентное по смыслу описание через публичную функцию h. Её первый аргумент — тип узла, второй — свойства, третий — дочернее содержимое. Вызов h создаёт VNode; он не означает немедленного создания p в DOM.

[Выделить шаблон, затем сигнатуру вызова h и его три аргумента. Оба фрагмента остаются видны.]

Важно назвать степень упрощения: это учебный эквивалент, а не буквальный вывод компилятора Vue. Настоящий компилятор использует внутренние helpers и информацию о динамических участках. Код справа показывает результативную роль render-функции без необходимости вручную писать такие функции в приложении. Шаблон компилируется при сборке SFC; render вызывается при работе приложения и читает текущий count. Компиляция и выполнение render не являются одной стадией.

### Слайд 102. Virtual DOM — дерево описаний интерфейса

Сначала h получает p, объект атрибутов и строку. Ниже показана читаемая проекция нескольких полей созданного VNode. Type задаёт тип, props — входные свойства узла, children — содержимое. Настоящий VNode содержит дополнительные служебные поля, поэтому этот литерал не нужно выдавать за полноценный объект, который можно передать renderer вместо h.

[Подсветка: создание → type → props → children.]

Virtual DOM — дерево таких описаний. В children могут быть строки или массивы других VNode, а type может указывать на Vue-компонент, а не только на HTML-тег. У описания пока нет роли сфокусированного input и оно не является результатом document.createElement. Наличие VNode само по себе не доказывает появление DOM: создавать, связывать и удалять реальные узлы будет renderer.

### Слайд 103. Mount впервые связывает описание с DOM

На первом проходе ещё нет старого результата этого экземпляра, с которым нужно согласовывать новые данные. Vue выполняет render, получает дерево VNode и монтирует его: создаёт элементы и текст, устанавливает свойства и обработчики, вставляет узлы в контейнер. Это mount, а не patch уже существующего дерева.

Границы нужны для следующего наблюдения. Сначала компонент настроил состояние в setup; затем render прочитал нужные ему значения; renderer создал представление в браузере. Callback mounted вызывается после монтирования в соответствии с правилами жизненного цикла из основного маршрута. Асинхронные потомки и SSR здесь исключены: исследуем обычное синхронное клиентское дерево. Отдельное имя mount не означает ручной вызов этого алгоритма в пользовательском компоненте — работу выполняет Vue.

### Слайд 104. Реактивный эффект планирует новое описание

В лекции 9 мы уже отслеживали чтения computed. Render тоже выполняется в реактивном эффекте. Когда он читает count, Vue связывает эффект с этим источником. Изменение используемого значения планирует обновление; несколько синхронных записей могут объединиться.

Новое выполнение render даёт актуальное описание. Оно не означает повторный setup или повторную компиляцию шаблона. И не всякая запись в ref обязательно приводит к обновлению этого компонента: значение должно участвовать в зависимости рендера, напрямую или через вычисление. При props возможна проверка необходимости обновления ребёнка; изменение любого состояния родителя не означает обязательное пересоздание каждого потомка.

Теперь у renderer есть прежнее и новое описания. Следующий вопрос относится уже не к системе зависимостей, а к согласованию этих описаний с настоящими узлами. Так отделяем причину повторного вычисления от механизма изменения DOM.

### Слайд 105. Patch изменяет DOM, сохраняя подходящие узлы

Оба описания имеют тип p и ту же идентичность в текущем месте дерева. Изменились data-count и текст. Renderer сопоставляет старый и новый VNode и применяет необходимые операции к DOM. Для этого примера он может сохранить p и обновить атрибут и содержимое.

[Слева прежнее описание, справа следующее. Последовательно выделить type, затем props и children.]

Новые объекты VNode не означают новые DOM-элементы. Упрощённо этот процесс называют diff или reconciliation, а применение согласования — patch. Не обещаем, что Vue всегда обходит целиком все узлы и сравнивает каждое поле: компилятор помогает пропускать статические части. Не обещаем и минимального числа операций для любого случая. В опыте основного маршрута реальные ссылки и MutationObserver позволили отличить обновление текста от замены элемента.

### Слайд 106. Тип узла и key определяют сохранение идентичности

Таблица объясняет три случая из демонстрации основного маршрута. Новое значение при прежнем типе сохраняет p. Смена корневого HTML-тега требует другого элемента, но не обязательно другого экземпляра компонента. Смена key на самом RenderProbe выбирает другую идентичность компонента: прежний экземпляр завершается, новый создаётся.

Key — специальная подсказка renderer, а не обычный prop ребёнка и не требование заменить всё дерево при каждом изменении. В списке ключи связывают описания с логическими записями; Vue может перемещать прежние узлы и обслуживать добавления/удаления. Индекс позиции не выражает такую идентичность при перестановке записей. Этот механизм уже наблюдали в 09; здесь связываем его с VNode и сроком жизни владельца.

Из этого не следует, что Virtual DOM всегда быстрее ручных операций или является полной копией DOM. Это модель описания и согласования, у которой есть цена создания объектов и выполнения кода. Vue использует сведения компилятора для сокращения работы; измерение производительности оставляем 16. Теперь уточним, как сведения компилятора сокращают работу согласования. Источники автора: https://vuejs.org/guide/extras/rendering-mechanism.html , https://vuejs.org/api/render-function.html , https://vuejs.org/api/built-in-special-attributes.html#key .

### Слайд 107. Статическое содержимое не требует одинаковой работы каждый раз

Статический заголовок не зависит от состояния, а текст strong зависит от count. Компилятор может кешировать статическое содержимое, помечать динамические свойства и организовывать быстрые пути обхода. Patch flags сообщают тип ожидаемого обновления, а block tree помогает фокусироваться на динамических потомках. Это описание ролей оптимизаций, не буквальная распечатка сгенерированного кода текущей версии.

По кликам отделить заголовок от динамического текста. Возможность оптимизации зависит от конкретного шаблона и режима компиляции; не обещаем один и тот же набор инструкций для всех случаев. Само наличие Virtual DOM не гарантирует меньшую стоимость, чем у любой другой реализации. Когда интерфейс тормозит, нужно измерять источник нагрузки — вычисление, обновление компонентов, DOM, layout или paint — и только затем выбирать изменение. Свойства браузерного рендеринга не являются частью diff VNode.

Справка: https://vuejs.org/guide/extras/rendering-mechanism.html .

### Слайд 108. Что render прочитал и что вызвало обновление?

Мы отделили вычисление описания от изменения DOM. Теперь можно точнее поставить диагностический вопрос: что render прочитал и какое изменение вызвало его повтор? Оба хука регистрируются синхронно в setup; импорты из vue здесь опущены. OnRenderTracked получает событие отслеживания зависимости эффектом рендера, onRenderTriggered — событие, которое вызвало повторное выполнение этого эффекта.

Например, шаблон читает count из ref. В событии чтения можно увидеть type get и key value; изменение count связано с событием set для value. По одному имени value нельзя определить исходный ref: для этого у события также есть target. Неиспользуемый ref не становится зависимостью render только от того, что объявлен в setup. Эти callbacks позволяют исследовать причину обновления, но не показывают список выполненных DOM-операций и не измеряют layout или paint.

[По кликам отделить tracked от triggered, затем показать обе регистрации вместе. Это чтение диагностического кода; live-стенд и консоль на данном слайде не встроены.]

Хуки работают только в development и не вызываются при SSR. Их нельзя использовать для обязательной логики приложения, загрузки или синхронизации данных. В callback выводим сведения в console, не меняя отображаемое реактивное состояние: иначе сама диагностика может создавать дополнительные обновления. Официальная справка: https://vuejs.org/api/composition-api-lifecycle.html#onrendertracked и https://vuejs.org/api/composition-api-lifecycle.html#onrendertriggered .
